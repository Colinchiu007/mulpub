# Design: 重算在飞 PR 的债务结论，并把陈旧那一格点名

## D1 怎么造出"PR + 当下主干"的合并态——不动任何在用工作树

| 方案 | 结论 |
|---|---|
| A. 在 runner 的 checkout 里 `git merge` 每个 PR | **否决**：30 次串行合并会把 CI 自己的 `origin/main` 引用与 index 搅浑，一次冲突就让后续 29 笔全在错的状态上量；且与 `actions/checkout` 的 detached HEAD 语义打架 |
| B. 每笔 PR `git clone` 一份再合 | **否决**：30 次整仓克隆（本仓体量）在 5 分钟预算里必挂，且克隆出来的仓库与 runner 的凭据/浅历史配置又是一处新假设 |
| C. `git merge-tree --write-tree` 拿合并树 ⇒ `git commit-tree` 封成一个合成提交 ⇒ `git worktree add --detach <临时目录> <合成提交>` 后在其中跑判据 | **采纳**：全程不碰 runner 自己的 checkout；`merge-tree` 失败（真冲突）天然给出 `UNJUDGEABLE` 那一档的现场；worktree 是只读检出，用完 `worktree remove`，对象只活在本地、永不 push |

补充三条实现约束（**两条由本机 primitives 实测改写，原写法被否证**）：

① runner 必须 `fetch-depth: 0`（或显式 `--unshallow`）。实测浅历史里 `git merge-tree --write-tree` 给的是 **`rc=128` + `fatal: refusing to merge unrelated histories`**（临时仓库探针：`clone --depth 1` 后 `main` 只可见 1 个提交）——它**不是**"这个 PR 有冲突"，而是"CI 检出配置坏了"。所以这一格必须单独归因（见 D3 的 `reason` 词表），否则一次 `fetch-depth` 配错会在 30 个 PR 上刷出 30 条"这些 PR 都合不进主干"的假结论。

② 冲突的判据**不能看 stderr，也不能看首行**。实测真冲突（主干与 PR 都改同一行基线）的形状是 **`rc=1`、stdout 首行仍是 40 位树 oid（那个冲突树）、第 2 段起是 stage 条目 + `Auto-merging …` + `CONFLICT (content): …`、stderr 完全为空**。⇒ 顺序必须是：**先看 `rc`**（0 才算成功），再看 `CONFLICT`/`Auto-merging` 字样归 `conflict`；两者都没有而非零 ⇒ `unknown-shape`。⚠ 本条是**改写我自己先前写的形状**：初稿写"首行不是 40 位 oid ⇒ 冲突"，实测证明那样会把真冲突判成"合并成功并拿到树"——正好是这条链最坏的静默失效（拿冲突树当合规树去量，指标一定"在基线内"）。同理，测试夹具必须按实测形状造（首行是 oid），否则会把错误形状钉成契约。

③ 本地路径 `git clone --depth 1` **会忽略 `--depth`**（实测 warning：`--depth is ignored in local clones; use file:// instead`）。这条与 CI 无关，但与本仓的**测试夹具**有关：任何想用"浅历史"做负控的用例都必须走 `file://`，否则测的是深历史而自以为浅。

④ 每笔 PR 取 `refs/pull/<n>/head`，不依赖 fork 分支名——fork 贡献者的 PR，其 head 分支在 `origin` 里根本不存在，按 `head.ref` 取会 fetch 失败，而那会被 D3 误归成 `UNJUDGEABLE`（看起来像"这 PR 合不动"，实际是"我们取错了 ref"）。

## D2 用哪一份基线——不做特例，靠合并态本身

判据读的是**它所在工作树里的** `scripts/debt-baseline.json`。于是 D1 的合并态天然把两种情况都对：

- PR **没有**动基线 ⇒ 合并态里躺的是主干当下那份（收紧后的）⇒ 拿新红线量它，这正是本刀要的那件事。
- PR **自己**改了基线 ⇒ 合并态里是它提议的那份 ⇒ 按它提议的规则量它（这是既有 PR 语义，不能被"主干当下基线"覆盖，否则等于没收一个正在还债的 PR 的还债动作）。

所以本刀**不**实现"取主干 blob 覆盖之"的特殊分支。**Why 记进代码注释**：这个"不特例"是设计而非遗漏，否则下一个会话会以为忘了。

## D3 四档结论与"空集出行"

`IN_BASELINE` / `VIOLATES` / `UNJUDGEABLE`（构造不出合并态）/ `CHECKER_FAILED`（判据自身非零且不是违规输出）。后两档**不得折叠进"通过"**，也不得与 `VIOLATES` 混为一谈——`UNJUDGEABLE` 的正确读法是"没量到"，处置是留现场而不是留结论。这一档与 `check-branch-merged.js` 的 `rc=2（判据自身故障）` 同源。

`UNJUDGEABLE` 还必须带一个**封闭的 `reason` 词表**（不是自由文本），否则"CI 检出配错"会伪装成"这批 PR 都合不动"：

| reason | 触发形态 | 现场依据与处置 |
|---|---|---|
| `conflict` | **`rc≠0`** 且 stdout 含 `CONFLICT`/`Auto-merging`（**首行仍是树 oid**，stderr 零字节） | 实测形状见 D1 补②；只看"首行是不是 oid"会把真冲突判成成功，只看 stderr 会完全失明 |
| `unrelated-histories` | rc=128 且 stderr 含 `refusing to merge unrelated histories` | 实测浅历史就是这个形状；处置是修 `fetch-depth`，**不是**去 30 个 PR 上点名 |
| `ref-missing` | fetch `refs/pull/<n>/head` 失败 | fork PR 若按 `head.ref` 取就落这里（D1 补④）——看起来像"这 PR 有问题"，实际是我们取错 ref |
| `worktree-setup` | `commit-tree` / `worktree add` 非零 | 合成提交或只读检出建不起来 |

前两类里 `unrelated-histories` 与 `ref-missing` 属**工具侧故障**：整轮遇到它们时作业必须以非零码结束、只打印一次归因（见 D6），不得逐条刷 PR 评论——把配置错误包装成 30 条"你的 PR 有问题"是这类缺陷最坏的可见形态。

## D6 作业的退出码语义（外部评审 Warning#2 的处置）

| 情形 | 退出码 | 理由 |
|---|---|---|
| 每笔 PR 都量到了（无论 `IN_BASELINE` 还是 `VIOLATES`） | **0** | 本刀是**报告**不是闸门；把"有债"判成 CI 红会诱导人去修评论而不是修债 |
| 个别条目 `UNJUDGEABLE(reason=conflict 或 worktree-setup)` | **0**，但计数行必须逐档出声 | 某个 PR 真合不动是被测对象的实际状态，不是工具坏了 |
| 出现 `unrelated-histories` / `ref-missing`，或评论写入失败 | **非 0**，且只打印一次归因、不逐条刷评论 | 这些是工具失明；静默通过等于下一轮继续假装量过 |

⚠ 该作业**不进 required**（本刀刻意不碰守门，见 proposal「不做」），所以"非 0"不卡任何人合并，只让**这次重算本身**在 Actions 里可见地失败。

评论表格每笔一行，并**逐档打印计数行**（含 0）：`rows=<n> IN_BASELINE=<a> VIOLATES=<b> UNJUDGEABLE=<c> CHECKER_FAILED=<d>`。本仓已有实测教训：`gh api ... /check-runs` 返回空数组被读成"检查已通过"，而实际是探针坐标坏了；空集出行是唯一能把"没有"与"没量"分开的写法。

## D4 幂等：更新而不叠加

一次基线变更会给最多 30 个 PR 各留一条评论；近 30 天基线变更 12 次 ⇒ 每季度约千条。正解是**按标记更新**：正文首行放机器标记

```
<!-- debt-baseline-recheck:v1 base=<main sha> judged=<ISO> -->
```

`findMarkerComment(comments)` 按标记命中既有条目 ⇒ `PATCH`，否则 `POST`。标记带 `base=` 与 `judged=`：既让人一眼看出这条结论是对着哪次主干量的是什么时刻量的，又保证"同一标记形状"只有一个真源（渲染函数），不是散在 shell 里的字符串。

⚠ 一条自我约束：本刀的判据**不能**写成"评论里必须出现 `base=<当下 sha>`"——那样每次主干前进都会把自家历史评论判成过期。判据只认标记前缀 `debt-baseline-recheck:v1`，`base=` 是给人看的。

## D5 可测性：无网络、可注入、真 git

本仓 `network-egress-guard` 会拦真实出站（且 packages 侧测试面各自装配），所以：

- `check-debt-recheck.js` 的一切外部依赖（`runGit`、`runChecker`、`http`）都**由调用方注入**，生产装配点在 workflow 里；
- 单元测试注入假 `runGit`/假评论列表，锁的是**决策与渲染**（四档映射、空集出行、标记幂等、D2 的"不覆盖"语义）；
- 一条**真 git 集成用例**在 `os.tmpdir()` 建临时仓库：造一个"主干收紧基线 + PR 未动基线"的现场，跑 D1 的 merge-tree→commit-tree→worktree 全链，断言合并态里读到的是主干那份新基线（这条是 D2 的行为证明，读源码证明不了）；
- 反证与 tasks 3.7 共用同一张表（外部评审 Warning#4 命中：本节原先只写两条，任务表却要求五条 ⇒ 两处各说一套）。下表 M1–M5 是本节初稿的五条；实现层外部复核之后又加了 M6–M8（见 D8），**仍算同一张表**，不得另立第二份清单：
  - **M1** 把 `UNJUDGEABLE` 折进 `IN_BASELINE` ⇒ 计数行断言 + 「量不到必须单列」那条用例红；
  - **M2** 用主干 blob 覆盖 PR 提议的基线 ⇒ **真 git 集成用例**红（这一格只能由集成用例抓，读源码看不出）；
  - **M3** `rows=0` 时整行缺失计数行 ⇒ 「空集出行」用例红；
  - **M4** 把标记里的 `base=` 纳入判定 ⇒ 幂等用例红（它会把自家历史评论全判成过期，反复叠评论）；
  - **M5** 在重算脚本里自行复算某项指标（制造第二份度量）⇒ 结构锁 + 判据退出码映射用例各红一条。
  M1–M5 跑完必须把判据文件按字节还原并打印 md5；驱动必须先自证"这一跑真跑了几条用例"（只看有没有红，会把"整片没跑"读成"变异未被抓住"）。

## D7 写入面门闩：默认关，严格 `"1"` 才开（外部复核 i3，`highRiskDomains=["auth"]`）

实现层深审的 i3 指出：workflow 声明了 `pull-requests: write`，`live()` 用 `GH_TOKEN` 直接对**别人的**在飞 PR 发评论，除权限声明外没有任何授权判定；而 CI 侧评论速率与耗时**未测**。这一格被引擎标记为高危域 `auth`，明打「高危域必须外部复核」，**不得**用自扮演裁决豁免。

处置不是"加个说明"，而是把写入从默认路径上摘下来：

- 纯函数 `shouldCommentOn(env)` **严格只认字符串 `"1"`**（`true`/`"01"`/空串/`0` 都不算，避免"看着像开"）；
- workflow 里显式 `MP_RECHECK_COMMENT: "0"` —— 首轮只打印结论与"本来会写谁"（`would-comment pr=<n>`），不动任何人的 PR；
- 开启需**人**改 workflow 里那一行，且前置条件是"本文件已回填一次真实运行的四段实测读数"；
- 两道防装饰断言：`live()` 里必须真的调用门闩（导出没人调 = 装饰性开关），workflow 里那行必须显式存在。

## D8 预算与写前二次核查（同一格的外部复核后续 W3/W4）

紧随其后的外部复核（claude，直接派发、载荷内联三段被测代码）认可门闩关得住（无第三条旁路、权限精确匹配），但给了两条 Warning，都已落码：

- **W3 写入面在开启后仍缺边界** ⇒ 新增 `commentBudget(env)` / `commentBudgetDefect(env)`：`MP_RECHECK_MAX_COMMENTS` 默认 10，`0` 是**合法**上限（只点名不写，不得被 `||` 之类的假值回落吃掉），非负整数以外的取值回落默认并**出声**；workflow 里显式写 `"10"`，并由锁要求脚本真的读它（读写两处都在，防止"workflow 设了、脚本没接"）。
  同时每次写入前重新 `gh pr view --json state`：`state≠OPEN` 或**读不到**都跳过并打印实际状态值（`unreadable`）——清单是几分钟前拉的，把工具的失明读成"它大概还 open"是本仓同型错误。
  **未采纳的一条修法**：评审建议再加"写入间隔"。理由：本作业只在两份守门输入变化时触发（实测近 30 天 12 次），单轮上限 10 条，距 GitHub 二级速率限制差两个数量级；加 sleep 只会把一个已有 15 分钟预算的作业拖长，而它挡的不是本刀会遇到的失败形态。
- **W4 结构断言冒充行为断言** ⇒ 评审原文：「结构测试保证'被调用'，行为测试保证'无旁路可绕过'」。为此 `live(deps)` 现在把 `env/git/gh/runChecker/log` 全部做成可注入（默认值就是真实实现），并新增三条**行为级**用例：同夹具两档 env 断言写调用次数差、触顶后不多写、状态非 OPEN 不写。夹具纪律：每条先断言"注入的 `gh` 收到了 `pr list`"，否则实现退回真实进程时，"零次写调用"会因为网络被守卫拦死而**假绿**。
- 变异面因此从 M1–M5 扩到 **M1–M8**：M6 摘上限判据、M7 摘写前复查、M8 把门闩退回 truthy 判定。三条各红一条**指名**用例，且红集互不相同。

## D9 第 3 轮复核的三格处置（写入资格 / 拒写可归因 / 绝对硬顶）

- **W5 夹具同一个答案**：`recheckWorld` 原先对所有 PR 回 `rc=1`，于是"`IN_BASELINE` 的条目没有写路径"这一资格**从未被表示过**——夹具对所有输入给同一个响应，这类缺陷对它结构性免疫（本仓同款先例见「兜底/回退类选址」与「恢复类夹具」两条）。修法是把判据响应改成**按输入可变**：注入 `worktreeAdd` 得到 `wt-<seq>` 目录串，再由 `rcOf(dir)` 逐笔给不同答案；「写入资格」用例断言三笔中只有一笔违规时**写调用 1 次、`pr view` 也只有 1 次**（合规那两笔连写前复查都不该占用）。
- **TOCTOU 只做到"可归因"，不做到"可消除"**：状态复查与写入之间那一刻 PR 仍可能被合并，这是任何"先读后写"都消不掉的窗口。处置是让拒写有**自己的归因行**（`gh api` 回 404/410 ⇒ "该 PR 在复查之后已不可写"），不重试、不改判、不把整轮升级成工具故障。预算口径同步写明：**按尝试计而不按成功计**——失败的一次同样占额度，重试会把"逐条继续"变成重试风暴。
  这条差点写成装饰性锁：第一版断言取 `/拒绝|404/`，而摘掉归因分支后通用尾巴日志 `评论新增 rc=1 :: …404…` 里**照样含 404** ⇒ 用例不会红。变异 **M11** 就是为抓这一格而存在（把归因分支改成恒假 ⇒ 指名红），它证明的不是"代码对"，而是"这条断言有牙"。
- **绝对硬顶被拒绝**：评审建议再给 `MP_RECHECK_MAX_COMMENTS` 加一个代码内硬顶（如 30）。否决理由：该值本就写在**受评审的 workflow 文件**里，多加一个魔法数并不取消"由人决定写多少"这件事，只是把同一个决策摆到两处、并制造"已经封顶"的错觉；真正兜风险的是门闩默认关 + 触顶出声 + 逐条写前复查，三者各有行为锁。将来要加硬顶的前提是出现"人设了过大值并真造成损害"的现场，而不是"以防万一"。

## D10 第 4 轮复核抓到一处 Critical：更新端点少一层 `issues/`

幂等更新的分支拼的是 `repos/<repo>/comments/<id>`，而 GitHub 的"更新 issue 评论"是 `repos/<repo>/issues/comments/<id>`。这条的价值有两层：

1. **真缺陷**：每一轮 PATCH 都会 404，"更新而不叠加"这个承诺实际从未生效。
2. **被自家诊断洗白**：D9 新加的拒写归因（404/410 ⇒ "该 PR 在复查之后已不可写"）会把这个拼写错误读成**平台侧时间窗竞争**——诊断能力越强，越容易把自家错误解释成外部现象。所以归因行的文案必须限定在它真正覆盖的那一格，且这类"新增归因"必须配一条"它能区分两种成因"的用例（本轮补的是 D10 下面的夹具改造）。

为什么 19 条全绿照不出来：夹具的 `comments?per_page` 恒回空数组 ⇒ `findMarkerComment` 永不命中 ⇒ **PATCH 分支在测试面根本没被执行过**。这是「夹具对所有输入给同一个答案」的同型落点：不是断言写错，是那条路径压根没被表示。修法两件：① 两个端点按语义分开写死并加注释（新增 `issues/<n>/comments`，更新 `issues/comments/<id>`）；② 夹具加 `existingComment` 让标记命中真的发生，断言 PATCH 次数与 URL 形状，并另加一条"不得出现缺 `issues/` 层的形状"的反向断言（按端点位置切，不是整串扫，见 AGENTS「禁令与存在性判据必须按语义位置切」）。变异 **M12** 把端点退回原始错误形态，实测指名红第 16 节那条用例。

同轮三条 `verified=true` 的 Info（认可四条机制合起来无旁路、认可 11–15 节确实是行为锁、认可"拒绝硬顶"成立）**不写进闭合结论**：它们与 Critical#4 出自同一次派发，同一次派发既能认可也能漏判，能当证据的只有 M12 那条指名红。

## D11 守门输入的归属：从"人抄一份"改为从 debt-guard.yml 派生（前端轴 W-FE1/FE2/FE3）

**先记一条被否证的自我豁免**。本刀起初把「新增第三份基线文件时不会有任何东西变红」写成**刻意不做**，理由是"为未知目录布局建判据属猜需求"。前端轴当场把它否证了：`debt-guard.yml` 的阻断 step 除 `check-debt-budget.js` 外还跑 `.github/scripts/check-max-lines.js`（读 `.github/scripts/max-lines-baseline.json`）——**已存在的一格**，不是猜出来的未来形态。教训口径：写下"不锁是因为场景未知"之前，先去执行面量一遍，"未知"必须是量过的结论。

**派生规则（`blockingGateInputs(debtGuardYml, readScript)`）**：

- 按 step 块切（`- ` 起始），块内含 `continue-on-error: true` 的一律排除 —— 软门禁改了不会让任何 required check 由绿变红，把它算进来会让触发面无谓变宽；本仓现场就是死代码检测那一步。
- 保留的块里收 `node <path>.js`；再对每个脚本读它自己的源码，按 `path.join(__dirname, '<file>.json')` 字面量把**账本文件**一起收进集合。收紧账本与收紧判据本体是同一件事的两半，只列脚本名等于漏掉一半。
- `readScript` 由调用方注入（夹具给假文件系统），真实对账读仓库 ⇒ 规则本体可测。
- workflow 的 `paths:` 与派生集合由锁双向对账：夹具精确集合（顺序、成员）+ 真实 `debt-guard.yml` 的覆盖检查 + 一条"派生集合长度下界"的反退化断言（空集合会让覆盖判断恒真）。

**M13 与 M14 必须能分开**：两条变异（无视 `continue-on-error`、不再派生账本）第一版都撞在同两条用例上 ⇒ 红集逐字相同，锁分辨不了这两种退化。解法不是放宽判据，是**加一条夹具里没有软门禁 step 的用例**，让 M14 独红 —— 判据分辨率的单位是用例名，不是断言条数。

**另外两格同源错误的形状**：`head || 'HEAD'`（fetch 失败时拿主干跟自己合并，一定"成功"，并把假读数当真判决报出去；当场实测两条 PR 都返回 `VIOLATES`）与 `evaluateMergedBaseline` 回 `verdict:'IN_BASELINE'`（从不跑判据却自称判决，且与真判决同前缀同批导出）。共同点是**名字与返回值都在声称"我判过了"**。口径：只构造现场的东西，返回值只能叫 `built`，动词不能是 evaluate/verify/judge；封闭词表里每一个成员都必须有产出路径，否则它就是给下一个读者看的假承诺（`ref-missing` 本轮就是这么被抓出来的）。
