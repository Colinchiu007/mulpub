# Design: subtitle-sidecar-parity-lock

## 1. 问题形状：三类静默失效

三个子问题都不是 bug，而是「没有任何判据会红」的失效面。设计目标不是「多写测试」，
而是**让每一类失效都有一个能指名它的判据**，并且每条判据都要证明自己会红（变异反证）。

| 失效面 | 谁看不见它 | 判据 |
| --- | --- | --- |
| 单仓改了数据没改锁 | 两仓单测 | `sidecar-parity.lock.json` + 两仓各自的断言 |
| 两仓各改各的（各自内部自洽） | 任何单仓判据 | `scripts/check-sidecar-parity.js` + 定时 workflow |
| 本地实现与线上 sidecar 行为漂移 | 共享向量（只覆盖 44 例） | Python 金标 + TS/JS 逐字复现 |
| 权限声明比实现大（ops-center） | 文档与测试都看不出来 | 声明常量 + 声明/源码互证锁 |

## 2. 口径选择：为什么是「LF 归一化字节哈希」而不是 JSON 语义比较

候选口径三种：

| 口径 | 问题 |
| --- | --- |
| JSON 语义比较（解析后深比） | 放过键序/缩进/行尾差异；而这些正是跨语言生成时最容易漂的东西 |
| 各语言自己做 canonical JSON 再比 | Python `json.dumps(sort_keys=True)` 与 JS `JSON.stringify` 在浮点格式、转义规则、非 ASCII 转义上不同 ⇒ 用两套规范化再互相比较，等于在判据里埋一个自己就会漂的组件 |
| **字节级 + 只抹平 CRLF** | 最小、无歧义，Python/JS 各三行可实现 |

取第三种。两侧实现逐字对齐：

```js
sha256(readFileSync(p, 'utf8').replace(/\r\n/g, '\n'))
```
```python
hashlib.sha256(path.read_bytes().replace(b"\r\n", b"\n")).hexdigest()
```

代价：数据文件里**任何**格式差异都会红（哪怕是某个实现重新序列化时换了缩进）。这是有意的：
两仓副本本来就该逐字节相同，「格式不同但语义相同」在跨语言场景下是漂移的温床。

## 3. 锁文件的两半与它缺的那一格

`sidecar-parity.lock.json` 在 mulpub 与 smart-sentence-splitter **逐字相同**。每个仓库的
CI 只断言「**本仓**数据 == 锁登记值」。由此：

- ✔ 改了本仓数据没改锁 → 本仓红
- ✔ 改了两仓数据但只更新一仓的锁 → 那一仓红（另一仓的数据没动，它的锁仍匹配）
- ✘ **A 仓同时更新「数据 + 锁」（CI 全绿），B 仓数据+锁仍是旧的** → 两仓都绿，跨仓已漂

第二类是三份文档里最容易写成「已经闭合」的形态，所以本次专门给了它一条判据：
`scripts/check-sidecar-parity.js` 同时读两个 checkout，逐个比较**四份共享产物**
（规则表 / 向量 / 语料 / 金标）与两个锁文件。

> 为什么是四份而不是两份：`corpus` 与 `golden` 同样是两仓各存一份副本，而金标只在 mulpub
> 侧被消费、sidecar 侧不读它。若这两份漂了，**单仓判据里没有任何一只眼睛看得见**——
> 过期金标仍会被复制过去并通过对方的测试，只是它描述的是旧行为。缺一侧时判据如实报
> 「只在一侧存在」，不读成一致（那通常意味着忘了复制）。

**为什么不挂 PR**：它要 clone 另一个仓库。把第三方仓库可用性变成每个 PR 的红点，
结局一定是这条判据被加进豁免或被跳过（本仓已有多次同型先例）。所以它挂 `schedule` +
`workflow_dispatch`，并且**判据本身的检出能力**用 `check-sidecar-parity.test.js` 锁住、
挂在每个 PR 都跑的 Gate 12f —— 区分「判据会跑」和「判据本身没坏」两件事。

### 3.1 锁文件的比较也必须走同一口径（真实运行抓到的假红）

第一版比较锁文件用的是**原字节**。真实跑立刻红了：四条数据哈希明明全等，只有锁文件报不一致。
原因是两仓**检出行为不同**——mulpub 的 `.gitattributes` 是 `text=auto`（Windows 工作树 CRLF），
sidecar 检出为 LF；同一份登记表的原字节必然不同。

教训不是「再小心一点」，而是：**一份判据里只要有一处口径与其余部分不一致，它会在最不该红的地方
稳定假红，然后被当成噪声关掉**。现在锁文件与数据文件走完全相同的口径（只抹平 CRLF），并补了
一条专门的回归测试（同内容/不同行尾 ⇒ 必须不报；内容真不同 ⇒ 必须报）。

## 4. Python 金标：定位与 provenance

### 4.1 它不是真值

本仓向量测试写明「禁止直接把实现输出写入向量（自证陷阱）」。金标是「实现输出快照」，
形式上就是那句话禁止的东西。区别在**回答的问题不同**：

| 机制 | 回答 | 权威 |
| --- | --- | --- |
| `subtitle_segmentation_vectors.json` 手工向量 | 这样切**对不对** | 人 |
| `subtitle_python_golden.json` | 本地实现与线上 sidecar **是不是同一份行为** | sidecar（一致性参照） |

互补性：三端一起漂移时金标不红（它只比一致性），手工向量红。所以金标**只叠加、不替代**，
且这段说明必须写在代码里（`sidecar-golden.test.ts` 与生成器 docstring 各一份），
否则下一个读代码的人会拿它当 truth 去改。

### 4.2 参照系为什么是 Python

生产链路是 `StageExecutor.SPLIT → 8002 /v1/split → sidecar`，TS/JS 只在 sidecar 不可用时兜底。
真正的风险是「降级后行为悄悄变了」，所以参照系取线上跑的那一份。

### 4.3 provenance 的四个字段

`rulesLfSha256` / `vectorsLfSha256` / `corpusLfSha256` / `commit`。

前三个是**承重**的：金标测试断言它们分别等于「当前锁登记的规则表/向量哈希」与「当前语料的
LF 哈希」。含义：改了任一方就必须重生成金标，否则即使输出没变也会红。这是有意的摩擦——
「数据变了但参照没重取」是这类快照机制最常见的失效。`commit` 只是可追溯的元信息，不做断言
（合并后它会立刻过时，断言它等于每天造一次假红）。

### 4.4 语料只放输入；生成器不接受路径参数

`subtitle_parity_corpus.json` 只含 `{id, why, text}`；期望值 100% 由生成器产出。
理由：手写一半期望值会让「谁才是参照」说不清——人写的那部分是真值，生成的那部分是一致性快照，
两种语义混在一个文件里以后没人分得清。语料本身也是两仓副本（与规则表/向量同规格对待）。

**生成器没有 `--corpus` / `--out`**：它读 `tests/vectors/subtitle_parity_corpus.json`、
写 `tests/vectors/subtitle_python_golden.json`，两个路径都由 `__file__` 推出。

这样改有两个原因，第二个才是硬约束：
1. 一个只做「读固定输入 → 写固定输出」的脚本，接受任意路径本身就缩窄了安全面；
2. 提交时 CCG 安全扫描器把「`Path(` + 同行出现 `args`」判为**路径遍历高危并阻断提交**，
   而该扫描器**没有任何抑制机制**（源码核对：只有 `isComment` 跳过注释行）。可以靠改名变量
   躲过这条正则，但那是「为通过判据而改代码」，与本案要建立的东西相反；去掉参数是让**设计**
   变对，而不是让判据闭眼。

`sanitize` 式的校验放这里没有意义：调用者是开发者本人、在本机、用自己的权限、往自己的另一个
仓库写文件，没有跨越任何权限边界。真正有价值的是「只有一条固定路径」，于是顺手拿到。

### 4.5 生成之后仍有一处人工步骤（不假装自动化）

sidecar 侧的 `tests/vectors/` 里同时放语料与金标（这样 sidecar 自己的测试能断言金标没过期），
再由人把这两个文件复制到 mulpub 的 `packages/story2video-engine/tests/fixtures/`。
跨仓复制**故意不自动化**：它是唯一需要人判断「这次改动是否该跨仓同步」的节点；
复制是否做对，由 `check-sidecar-parity.js` 的四条产物比较兜住。

18 例的选择偏向**现有向量没覆盖的形态**：无标点长块、保护短语内部、引号未闭合、小数点、
顿号枚举、短块合并、全/半角空白、纯标点、超 200 字、满块停在「了」、中英混排、数字单位、
空串/纯空白/单字，以及一段真实用户文案（v1.3 那次坏切的来源）。默认字幕配置一套，
不掺多套配置——三端选项键名不同，掺进来会让「对账失败」到底是行为漂移还是配置映射错变得分不清。

## 5. ops-center「假锁」的处置

三个候选：

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| 把简化移植补齐到与 TS 同构 | 大（整个词边界子系统 + 语料扩建） | 不在本切片 |
| 给 `ops-center-ci.yml` 加 `packages/story2video-engine/**` 触发 | 小，但该 job 已长期卡 10 分钟超时临界（7 次里 3 次 cancelled），加触发会加剧取消率 | 不加，记录理由 |
| **把声明改诚实 + 声明与源码互证** | 小 | 采用 |

互证锁的三条断言（写在既有测试文件里，不新建文件、不新增接线）：
① `PORTED_SURFACE` / `NOT_PORTED_SURFACE` 存在且不重叠；
② 未移植清单必须点名 `word_good_lead` / `word_good_tail` / `word_semantic_lead` /
   `word_no_cut_bigrams` / `phrase_boundary_v1_3`（漏点名 = 悄悄扩大声称的覆盖面）；
③ 源码里必须确实没有那些实现标识。

**③ 的判据形状要注意**：只扫「代码形态」标识（`def _word_safe_split`、`WORD_GOOD_` 等），
不能用裸词匹配——模块 docstring 里刻意写了这些名字用于说明缺口，裸词匹配会把说明本身判成实现，
那是把判据写成永假两端的经典形态。

## 6. 数据校验

| 检查 | 判据 |
| --- | --- |
| 两仓规则表 LF 归一化一致 | `07c14ae2…`（本次对齐后两侧同值） |
| 两仓向量 LF 归一化一致 | `c6072781…` |
| 锁字段完整 | `schema` / 两个 64-hex / `howToUpdate` 含生成器路径 |
| 语料与金标用例集一一对应 | 双向排序相等 + 两侧各自无重复 id |
| 金标 provenance 与锁一致 | 两字段严格相等 |
| 金标覆盖非空与空输入两类 | 非空 > 10、空 > 0（防语料退化成全空导致判据空转） |
| 哈希口径对行尾不敏感 | CRLF 与 LF 同值；且未归一化时必须不同（防空转） |

## 7. 功能逻辑与交互逻辑

本切片**不改变**任何运行时行为，因此无 UI/交互变化；改变的是「谁能发现什么」：

- 开发者改了规则表却没同步另一边 → 提交时本仓测试红，错误信息直接给出四步修法与
  「不要只把锁改成新值」的告警。
- 开发者改了规则表并同步了两仓数据，但忘了重生成金标 → 金标测试红，信息里给出完整重生成命令。
- 有人在 A 仓自洽地改了数据+锁而 B 仓没跟 → 次日 `Sidecar Parity (cross-repo)` 红。
- 有人试图把 ops-center 说成「完整移植」→ 声明与源码互证锁红。

## 8. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 锁变成「每次改数据都要跑三处」的摩擦点，最后被绕过 | 修法写进错误信息与 `howToUpdate`；五步命令可直接复制；摩擦点是设计意图（数据变更本应跨仓同批） |
| 金标与实现共同漂移 | 手工向量兜住正确性；金标只在「一致性」维度说话，且文档/代码双处声明 |
| 金标在两仓之间漂（sidecar 侧不消费它，故单仓看不见） | 语料/金标纳入跨仓对账的四条产物比较；sidecar 侧另加「金标 provenance 与本仓数据版本一致」断言，防过期 |
| 定时跨仓 workflow 依赖第三方仓库可用性 | 只 `schedule` + `workflow_dispatch`；失败不阻塞任何 PR |
| `.gitignore:106 scripts/*.js` 静默忽略判据本体 | 加 negation 并在注释里写明症状（本地绿、CI MODULE_NOT_FOUND） |
| 新 `scripts/*.test.js` 未被任何 workflow 点名 | 接进 `quality-gate.yml` Gate 12f（`check-unwired-tests.js` 的棘轮会兜底） |
| 生成器的路径参数被安全扫描器判高危并阻断提交（无抑制机制） | 去掉路径参数（见 §4.4）；不是绕过判据而是缩小安全面 |

## 9. 变异反证（每条判据必须证明会红）

| 变异 | 期望 |
| --- | --- |
| M1 改本仓规则表一个字符（不更新锁） | 锁判据红 |
| M2 改锁登记值（数据没动） | 锁判据红 |
| M3 改金标里一个 block | TS 金标 + JS 金标都红 |
| M4 删金标一条用例 | 一一对应红 |
| M5 篡改金标 provenance 哈希 | 版本对账红 |
| M6 语料新增一条但金标不补 | 一一对应红 |

实测结果记入 `openspec/records/subtitle-parity-locks.md`。
