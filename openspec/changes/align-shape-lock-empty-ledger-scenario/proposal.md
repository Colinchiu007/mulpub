# 提案：把「真仓形状锁」的空集 Scenario 对齐到该 Requirement 自己的正文

## Why

`openspec/specs/quality-gate-execution-record/spec.md` 里那条 `欠账登记项只允许承载原因，不得承载可腐化的第二份事实`（今天由 `normalize-debt-ledger-entry-shape` 归档而来）**自相矛盾**：

- 正文写：「**键数本身不设数字下限**——欠账被合法销账后条数必然变少，写死的下限会腐烂成必须"为通过而调低"的常量；真正拦"清空账本变绿"的是既有「未登记欠账」判据」；
- 最后一个 Scenario 却写：「**WHEN** 真仓形状锁读到的键数为 0 → **THEN** 该用例 MUST 红（规模下界）」。

两条一句在禁下限、一句在设下限。`openspec validate --all --strict` 判它通过——它查结构与必需段，**不查同一条 Requirement 内部是否自洽**，所以这个矛盾当天就进了主干。

## What Changes

只改那个 Scenario，把它要防的东西写清楚：**反的是"扫描器失明"，不是"被测对象恰好为空"**。三件事分开：

1. 读不到账本（文件缺失 / JSON 坏 / `loadLedger` 返回面不是普通对象）⇒ MUST 红（这才是反失明）。
2. 文件里确实一条登记都没有 ⇒ MUST NOT 红——那是本 Requirement 正文承认的**合法终态**（每条原因都写着"回填后删除本条"），把它钉成禁态就是自己正文里骂过的"常量红"。
3. "清空账本不得变绿"由**行为判据**承担：载体仍有未收口行 + 注入 `ledger:{}` ⇒ `r.open` 非空且进阻断出口，且该机制锁 MUST 与真实账本此刻条数无关、并对其做变异反证。

## 与代码的关系

同一天开的 PR #4001 摘掉了两条用例里的 `assert.ok(keys.length > 0)`，并把防清空交给夹具机制锁（C-F1/M-F1 双向复现、M6/M7 证明牙还在）。那刀改的是**代码**，本 change 改的是**规格里那句与之相反的 Scenario**——两者是同一件事的两半：没有这份 delta，代码就是在违反主干规格；有了它，规格与代码同向，且矛盾被记录成"当天写过又当天改掉"而不是留着让下一个会话猜。
