|---|-----------|------|------|------|
| i1 | Critical / security | 白名单拷贝未防 `../` 路径穿越；源文件名如 `../../x` 可写到 staging 外 | **成立·已改**：白名单里有 `prompts/tasks/**` 这类**含目录名**的条目（任务名来自源目录）⇒ 拼出的相对路径可能带 `../`。⇒ 新增 **S9**：每条相对路径 `path.normalize` 后必须以「staging 根 + 分隔符」开头，否则**拒绝** | 设计 §二 S9、§二白名单形状约束、判据 ⑨ |

## ⚠ 修订环节的如实声明（proposer 受输入上限所阻）

**事实**：轮 1 结束后引擎调用 proposer=opencode 逐条回应并修订，**失败**：

```
修订失败: 输入超长：10858 字符，超过 opencode 后端上限 7800 字符（实测边界 (8125, 8145]，非文档承诺）。
长度构成: 角色提示 147 + 任务提示 10704 = 10858 字符
```

**这意味着什么**：本轮的「逐条回应」这一步**没有由 proposer 完成**；
上表 8 条的处置**全部由作者（我）外科式落地**。

**为什么这么判**：这是**后端能力边界**，不是方案质量结论 ——
opencode 单次输入上限实测 7,800 字符，而本方案 10,858 字符 ⇒ 输入根本进不去。
（PR-3 的 19 轮里同样撞过这堵墙，见 `ccg-plan-review-record-pr3.md` §四之9：**结论照采、改动由作者外科式落地、并在记录里显式声明**。）

**因此**：第 2/3 轮改用 **proposer=codex**（输入上限大得多）继续跑，
让「逐条回应」这一环真的由跨家族后端执行，而不是由作者自问自答。

**留痕要求**：本批**不改** `scripts/ccg-review-backends.list`（那是仓内单一定义，改它会影响所有会话）；
覆盖**只在本命令里显式指定**，且在此记录。
