## 一、评审后端与跨家族校验

| 轮次 | critic（挑刺方） | proposer（修订方） | 跨家族 | 判定器 |
|------|-----------------|------------------|--------|--------|
| 第 1 轮 | `claude`（anthropic） | `opencode`（deepseek/hy3） | ✅ 通过 | DUAL |
| 第 2 轮 | `codex`（openai） | `claude`（anthropic） | ✅ 通过 | DUAL |

**为什么第 2 轮换后端**：`opencode` 后端单次输入上限 **7800 字符**（实测值，`model-call.js` 的 `BACKEND_INPUT_LIMIT`），而第 1 轮方案正文 18,088 字符 ⇒ proposer 修订环节被**同步拒绝**（~120ms、exit 1、无任何错误信息）。引擎预检已明确提示："把方案拆到 7800 字符以内"。`codex` 与 `claude` 均**无长度上限**（`BACKEND_INPUT_LIMIT` 只列了 `opencode`），且分属 openai / anthropic 两族 ⇒ 换用 `codex` 作 critic、`claude` 作 proposer，既保住跨家族又保住方案完整性。

> 换后端是**显式参数覆盖**（`plan-review.sh --critic/--proposer`，机制由 `scripts/plan-review.sh` 与 `scripts/ccg-review-backends.list` 头部注释共同声明），非绕过。

**第 1 轮的实际结局**（如实记录，不掩盖）：critic 成功产出 8 条问题（2 Critical），但 **proposer 的 `edits` 机械应用失败**——`before` 字段未能在方案原文中逐字定位（长中文串复现失真），引擎以 `Revision校验失败` 退出 rc=1，**未进入裁决**。
⇒ 处置：**不重跑、不降标准**，改为由方案作者按两轮意见**逐条外科式人工修订**（每条都有明确依据与落点），再重跑评审让 critic 对修订稿重新打分。

| i5 | Warning / feasibility | PR-6b 一上线即 fail-closed ⇒ 未配 `assetDownloadHosts` 且素材走独立 CDN 的**存量用户下载整体失败**，方案只有提示文案，**无迁移与灰度路径** | **采纳**：补「上线前必做」三条——① **实测各视频 provider 的素材域名与 API 主机是否同源**（逐 adapter 真实出片并记录素材 URL 主机，产出同源比例清单）；② 对非同源 provider **上线前预置** `assetDownloadHosts` 与端口；③ 仍不确定的给**一次性引导**（确认卡直达「去配置可信域」）。**不做「默认放开」来图省事**——那正是第 2/3 轮连续打回的点 |
| i6 | Warning / completeness | `project.json` 新增 `revision`，但**旧项目文件缺 `revision`** 时的读值与**首次并发写**（两进程都读到缺失）如何取舍未定义 | **采纳**：**缺失即读作 0**（不判损坏），**锁内自增**保证首次并发写（持有者 0→1，另一方在锁内读到 1 后判冲突）；补用例 |
| i7 | Warning / clarity | 验收多处把既有用例**条数**（23、19+7、20+2、14、13 例）当门禁判据 ⇒ 条数变动会被误读为回归，且条数**不证明覆盖** | **采纳**：判据改为「**该测试文件全绿 + 关键断言清单齐备**」，**条数降级为参考信息**。这一条对全节判据口径做了统一修正 |
| i8 | Info / completeness | 方案给出 PR 列表与 `openspec validate` 命令，但未声明运行时任务须经 `session-init`/`start-mp-task` 的**独立 worktree** 与 **openspec 五件套**落地步骤，与项目 SOP 入口脱节 | **采纳**：新增 §5.0「每个 PR 的落地路径」——建隔离 worktree、worktree 内改码+跑门禁、commit 后跑 `classify-docs-only`、推分支开 PR、CI 全绿自动合并；并写明**五件套归属**（PR-1 一次落全，后续 PR 只更新 `tasks.md` 勾选与执行记录）与**归档时机**（全部实现 PR 合并后） |

## 四、跨五轮的独立结论（两个家族共挑五次，结论一致的部分）

| 结论 | 第 1 轮（claude） | 第 2 轮（codex） | 第 3 轮（codex，复评） |
|------|------------------|-----------------|---------------------|
| 出站安全的**主机约束**必须补 | i1：解析器/劫持 | i2：**放开出站面** | i3：**仍不够，要缺省 fail-closed** |

| 提示词三分的**收益面** | — | — | i1：**存量上不成立** |
| 就绪度的**状态语义** | — | — | i5：**锁镜不该是阻止类** |
| PR 拆分粒度 | i4 | i6 | i8：**抽取方向要先定** |
| 证据可核验性 | i6 / i8 | i7 | — |

**三轮的 Critical 全部落在同两处**：①**出站合同**（claude 说"解析器来源不明确"、codex 说"主机约束太宽"、codex 复评说"仍不够，要缺省 fail-closed"）；②**并发写的原子性**（第 3 轮 i2）。这不是巧合——**G-3 是本方案里唯一真实存在且已上线的攻击面**（`video-gen.js:116-145` 裸 http + 无限跟随 + 无私网拦截），而**乐观锁的写入窗口是同一个 TOCTOU 模式在写侧的镜像**。两处最终口径：

- **出站**：协议 https + 端口集（缺省 443）+ 私网段 + DNS 校验 + **IP pinning** + 逐跳重校验 + 体积上限 + `.part`/ffprobe→rename + **可信主机（缺省 fail-closed，放宽需显式勾选 → 运行期一次性令牌，不落盘）**。
- **写入**：`revision` 自增与内容替换在**同一次原子替换**内完成。
