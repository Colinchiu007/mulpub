## Context

接线本身不难，难的是三件既有约束同时成立：

1. **`useTheme()` 今天是"每次调用各建一份"**：`theme` ref、`matchMedia` 监听、`persist`、`applyTheme` 都在函数体内新建。这在只有一个调用方时看不出来，一旦有第二处入口就会漂移（A 切色、B 仍显示旧值），且宿主监听按调用方数量重复注册——本仓「全局单例事件监听器生命周期」那条 QM 规则管的就是这个形状。
2. **首帧与异步读回相互冲突**：持久真源是 electron store，读取是异步 IPC；而 `data-theme` 决定首帧颜色。等读回再落色 ⇒ 偏好暗色的用户每次冷启动先看到一帧浅色（FOUC）。本仓 QM-2 已明文「首屏渲染不得阻塞在 IPC 返回之后」。
3. **暗色第一次真的对用户开放**：此前暗色只在视觉 runner 注入 `data-theme` 时被渲染过（`test-runner.js:519`）。也就是说"暗色可用"这件事的既有证据全部来自测试侧，而不是来自生产态。

约束：不动主进程协议；不新增依赖；文案必须 zh/en 成对；设置页在像素判定域内（`settings-general` 浅暗两档），基线只能取同一次 CI 渲染。

## Goals / Non-Goals

**Goals:**
- 用户能在设置里选「跟随系统 / 浅色 / 暗色」，即时生效、跨会话持久、重进应用保持。
- 主题状态应用级唯一；消费方增减不放大宿主监听；无测试专用后门。
- 冷启动不闪色，且真源始终优先于首帧缓存。
- 控件满足本仓既有无障碍合同（可访问名、键盘、焦点环），并留下可机械核对的锁。

**Non-Goals:**
- 不在本批逐个适配暗色下暴露出来的具体视图缺陷（按文件登记欠账，归各自批次）。
- 不做主题相关的 IPC 协议扩展、不动 `cohere-design-system.css` 的令牌定义。
- 不引入"自定义强调色"等第三态主题能力（本批只做 light/dark/system）。

## Decisions

### D1 单例形态：模块级共享状态 + 对称注册/注销，不引入 store 也不留测试后门

`useTheme.js` 内把 `theme` / `loaded` 提为模块级，`useTheme()` 返回同一份 refs；宿主监听以**引用计数**注册（首个消费者注册、最后一个卸载时注销），`init()` 幂等。

- 备选 A：放进 Pinia store。**否**——主题不是业务数据，store 化会把"谁写 data-theme"变成又一处需要接线的真相，且现有 composable 的调用方面貌要重写。
- 备选 B：导出 `_resetForTest()`。**否**——AGENTS 明文不得为测试开后门；改成"注册/注销对称"后，测试直接挂载/卸载组件即可复现监听器数量不变（本仓全局单例监听那条规则的正解形态）。

### D2 首帧：挂载前用同步镜像落色，镜像只服务首帧，真源永远优先

新增 `applyKnownThemeBeforeMount()`，在 `main.js` 创建应用之前调用：从 `localStorage` 读上次已知**用户偏好**（`ui:theme.mirror`，仅缓存 `light|dark|system` 三值）并落 `data-theme`；随后 `init()` 从 electron store 异步读真源，**若与镜像不同则以真源为准改写界面并同步镜像**。镜像不可读/坏值 ⇒ 按"跟随系统"处理。

- 为什么不是"等 IPC"：FOUC 是用户可见缺陷，不是优化项。
- 为什么不是"每次都用镜像、根本不读真源"：那会把缓存升格为第二份事实，多设备/清理 store 的场景会漂移。
- 锁的口径（必须能机械核对，不靠注释）：①镜像与真源不一致时终值 == 真源；②镜像缺失不产生第三种命名；③真源读失败时界面仍确定（跟随系统），且落一条可观测痕迹——**"没读到"不得被读成"偏好是浅色"**（本仓「观察者必须报告自身失明」的同型）。

### D3 持久化取值：闭合词表 `light|dark|system`，零迁移

`ui:theme` 新语义：`system` = 无用户偏好、跟随系统。兼容性：`null` / 键缺失 / 空串一律解释为 `system`（与旧实现"preferredTheme 为 null 才跟随系统"逐字等价，因此不需要数据迁移）。词表外的值 ⇒ 归一为 `system` 并出声，**不得**原样写入。

- 备选：继续用"缺失键"表达跟随系统。**否**——那让界面无法把"我要跟随系统"表达成一个可写值（用户从 light 改回跟随只能靠"删除"，删除在存储面上与"从未设置"不可区分）。

### D4 入口控件：`role="radiogroup"` + `role="radio"` 的自绘三态，不用 `el-radio-group`

选 radio 语义而非三个 toggle：三态互斥且单选，radio 语义能让读屏念出"当前选中"与组名；`<label>` 承载可访问名（不得用 placeholder）。键盘走 radiogroup 惯例（方向键移焦并选中），Tab 只进组一次。

- 为什么不复用 Element Plus：本仓 UI 框架是**按需引入**，新增 `<el-*>` 必须同步登记组件清单与**样式闭包**（`plugins/element-plus.js`），且样式导多导少都会造成像素回归——本仓有实测事故记录（`el-reset.css` 那一条）。为三个按钮引入一条新的样式闭包，代价大于收益。
- 代价如实写：radiogroup 的键盘/焦点行为由我们实现并自带锁（焦点环、`aria-checked`、方向键），不是免费的。

### D5 Tab 落点：`SettingsDialog` 左侧导航新增「外观」，默认 Tab 仍为「模型」

新 Tab 插在「通用」之后，`disabled: false`。默认停留 Tab 不变 ⇒ 打开设置页的首屏语义不变，但**左栏多一项 ⇒ `settings-general` 浅暗两张基线必然改动**。

基线刷新口径（不可绕）：CI 渲染 → 取 `quality-gate-visual-reports` / `QG Visual` 同一次 run 的 `-current.png` 入库 → 自证"新基线 vs 同一次 CI 渲染 == 0 px"。**禁止**本机 `test:visual:update-baseline`，**禁止**用 `--update-baseline` 消化差异（AGENTS 视觉规则 7）。

### D6 更正 `test-runner.js:511` 注释

接线存在后该句才第一次成为真话；改写为"生产侧写入者是 `useTheme` 的单例，runner 的注入只用于拍摄暗档、不落用户偏好、不写持久层"，避免下一个会话把 runner 注入误当成"用户能切主题"的证据——这正是本批要消灭的那种混淆。

## Risks / Trade-offs

- **R1 暗色首次对用户开放会暴露未适配视图**。这是**收益的代价而不是风险**：不接入口，那些缺陷连被发现的机会都没有。处置口径：以判定域暗档 + `contrast-audit` 为验收面，发现的具体缺项按文件登记欠账并写明归属批次，不在本批顺手改（顺手改会让像素基线与代码改动失去对应关系）。
- **R2 `localStorage` 镜像与 electron store 双写**。取舍见 D2：镜像只在首帧读取一次，写路径以真源成功为先、镜像随后跟进；两者不一致时真源赢。已知残余：多窗口/多分区场景下镜像可能滞后一帧，属可接受（终值仍由真源决定），并在测试里锁"收敛到真源"。
- **R3 首帧同步落色发生在 i18n/Pinia 之前**，因此该函数只允许碰 DOM 属性与 `localStorage`，不得调用任何需要应用上下文的 API。锁的形态：结构判据 + "在 `mount()` 之前被调用"的行为断言。
- **R4 radiogroup 自实现 a11y 可能不如组件库稳**。缓解：直接复用本仓既有无障碍合同锁的判定手法（`role`/`aria-checked`/可访问名/焦点环三格各自出声），并做反向对偶（合规形态必须绿）。
