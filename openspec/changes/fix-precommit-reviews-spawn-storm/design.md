## Context

钩子 L156–161 的原始意图（`#3396`，由 2026-10-12 一次排查触发）是：**把本次提交产生的判定记录 stage 进同一个提交**，因为 `ccg-review-decider.js` 以「提交前的 HEAD sha」命名记录，squash 合并会换掉 sha，使这些文件永远不会因「被某处引用」而入库，只能靠有人记得 `git add`。

意图本身成立，实现选错了候选集的**来源**：它用 shell glob 从**文件系统**取全集，再逐个问 git「这个在 index 里吗、变了吗」。于是每加一条记录到树上，全仓每一次提交都要多问两次。到 2026-10 中旬，origin/main 树里已有 609 个 `.json` 记录，且每个 worktree 检出即全量继承——**单次提交的进程创建数 ≈ 1,218**。

## Decisions

### D-1 候选集必须由 git 的视图派生，而不是由文件系统 glob 派生（核心）

`未跟踪 = git ls-files --others --exclude-standard`、`已改动 = git diff --name-only`，两者**按定义互斥**（前者不在 index，后者在 index 且工作树 ≠ index），拼接即得「需要 add 的全集」，无需去重，且集合大小与树上总记录数**无关**。

- **拒绝「只 stage 本次 HEAD sha 那一本」**：`sha=$(git rev-parse HEAD)` 后只 add `.ccg/reviews/$sha.json`。它同样 O(1)，但会把此前任何一次「钩子被中断 / 门禁改宽后补跑 / 判定器换了文件名规则」留下的未跟踪记录**永远留在未跟踪区**——那正是 `#3396` 要消除的形态（实测 22 小时内 300+ 条堆积）。本方案对同一目标更稳：无论历史欠下多少条，一次提交内全部收口。
- **拒绝「保留逐文件循环但用 `xargs -P` 并行」**：并行会把 1,218 次串行等待压成若干并发，但**总进程创建数不变**，而本机的瓶颈正是进程创建路径本身（每次约 1 秒，且被实时拦截层放大）。并发提交互撞时，这把成本转嫁给整机而非摊平。属症状缓解，不是根因修复。
- **拒绝「`git add .ccg/reviews` 整目录」**：会把该目录下**非 `.json`** 的 50 个 `.md` brief 一并纳入候选，属未经评审的作用域扩大；旧 glob 只覆盖 `*.json`。等价性优先于简洁性。

### D-2 pathspec 保持 `*.json`，与旧 glob 逐字同域（**本条原判有误，第三轮 QM-6 已更正：裸 pathspec 的 `*` 跨 `/`，必须加 `:(glob)`**）

候选扫描一律带 pathspec `'.ccg/reviews/*.json'`（**必须加引号**，否则被 shell 先展开：无匹配时留字面量、有匹配时展开成 N 个参数，两种走法都不是「git 侧匹配」）。这样新旧实现覆盖的文件集合可逐字对账，回归锁才测得出「只改了成本、没改语义」。

### D-3 批量 add 用 `--pathspec-from-file=- --pathspec-file-nul`，不走 argv

Windows `CreateProcess` 的命令行上限约 32k 字符。609 条 `.ccg/reviews/<64位sha>.json`（每条约 75 字符）已逼近上限，加上 `git add --` 与分隔符必然溢出 ⇒ 会出现「记录越多越容易突然失败」的二阶故障，且失败信息在 PowerShell 侧被截断、难以归因。走 stdin + NUL 分隔无长度限制，同时天然兼容含空格与中文的文件名（实测夹具里 `with space 和中文.json` 在新旧两侧回显同一形态）。

- 附带收益：NUL 分隔避开了「按换行拆名」这一整类缺陷（文件名可含换行的系统上会把一个文件拆成两次 add）。

### D-4 批量失败必须回退逐个并出声（保留 fail-open）

旧写法每个文件独立 `|| true`，任一文件 add 失败不影响其余、也不阻断提交。一次性批量 add 把这个语义换成「一败全败」，因此：批量失败 ⇒ 打印回退通知 ⇒ 退回逐个 `|| true`。

- **回退路径本身也是 O(N)**，这是有意的：它只在异常时出现，且必须**出声**，否则「批量恒失败、静默退回逐个」会把本次修复变成没发生而无人知道。回归夹具用注入型 shim 让第一次批量必然失败来测这条。

### D-5 规模锁的三向约束，以及「子 shell 吞 FAIL」这条实现陷阱

单看「调用数不随 N 增长」不足以构成锁——把那段循环整块删掉也满足。故三向同时断言：

1. **同成本**：N=2 与 N=200 时钩子的 git 调用总数逐字相等；
2. **有预算**：argv 含 `.ccg/reviews` 的调用 ≤3；
3. **仍有效**：200 条记录确实进入该次提交（`git show --name-only HEAD` 计数 == 200）。

计数用 PATH 前置的 shim 包住 git，**测试驱动自己的 git 一律用绝对路径**调用——否则驱动自身的调用会被计入，基线虚高使「同成本」永远不等。另：探针函数只许打印，不许调 `ok/bad`，因为命令替换是子 shell，`FAIL` 计数会丢（本仓同族踩过多轮）。

还有一条测的是判据而非实现：**批量 add 的 argv 里不含 `.ccg/reviews` 字样**（路径从 stdin 走），所以只按该字样过滤会「看不见正确形态」。判据取向必须是**能看见错误形态**——逐文件 add 一定带该字样；「总调用数不随 N 增长」这条兜住两个方向。

### D-6 结构锁的宿主选 CI `changes` job，不选 pre-commit

`scripts/check-precommit-spawn-budget.js` 解析钩子正文，断言「按 glob 逐文件 fork git」这一形态不再出现，落 `quality-gate.yml` 的 `changes` job（Gate 2b，`shell: bash`，fail-fast）：

- 不选 pre-commit：钩子自己就是被约束对象，让被约束物携带约束会随分支漂移；且本仓同日另一会话已实测「判据挂 pre-commit 两刀都不拦」。
- 选 `changes` 而非 `static-gates`：后者整体被 `docs-only != 'true'` 门控，一条只认钩子文本形态的锁若落在被短路的 job 里，等于给自己关掉校验（AGENTS.md 的进白名单前提锁）。该 job 无 Install deps ⇒ 新脚本只能 require node 内置模块。
- 新脚本与其测试必须各补一条 `.gitignore` negation：第 106 行 `scripts/*.js` 会把它们静默排除在 git 之外 ⇒ 写了也永远不会被 CI 跑到（实测 `git check-ignore -v` 已命中，属本仓点名过的陷阱）。

### D-8 pathspec MUST 带 `:(glob)` 路径魔法（第三轮 QM-6 i1，upheld）

D-2 的原判「逐字同域」只在扁平目录成立。同一临时仓库、四类成员齐备（扁平/嵌套 × 未跟踪/已改动）实测：
裸 pathspec 的候选并集 = `mod.json, new.json, inner/modn.json, inner/newn.json`；
加 `:(glob)` 后 = `mod.json, new.json`，与旧形态逐项一致。根因是两套 `*` 的语义不同——
旧形态用 shell pathname expansion（POSIX：`*` 不跨 `/`），新形态交给 git wildmatch（未置 `FNM_PATHNAME`：`*` 跨 `/`）。
现实爆炸半径已量：origin/main 该目录 696 个文件，路径段数分布 {3:696}，嵌套 0 ⇒ 当下无可观测差异；
但规格写的是「恰好等于旧集合」，「现在没有」不等于「合同允许扩大」。
两条锁各测一格：行为锁 scenario17 `nested-out-of-domain`（M7 去掉魔法 ⇒ 只红这条），
结构绊线 `GLOB_SCOPED_PATHSPEC`（夹具退回裸串 ⇒ violations 精确等于该一条，不连带噪音）。

### D-9 预算棘轮的作用域 = 暂存段（第三轮 QM-6 i3，upheld）

原实现按整份钩子文本数 `git add`，预算 `≤3` 恰好等于现状（余量 0），而其中一条属于无关的 `[sync-version]` 段
（`git add apps/desktop/package.json`）。后果不是"漏判"而是"必假红"：任何人在别的段落加一条正常 add 都会收到
一条与本判据语义无关的红，而维护者面对假红的真实反应是抬高预算数字——每抬一次，棘轮对该段的约束就自弱一分。
取舍：禁止形态与 required 写法**保持全文**判定（"别处复活逐文件 git 调用"正是这一维要看的东西，与段落无关）；
只有**预算**这一维改为按暂存段计（3→2），全文计数保留为 metrics 出声不判（`gitAddCallsWholeFile:3`），观测面不丢。
段边界靠起止锚点，各要求恰好命中一次；解析不出即判自身故障并与"违规"分档（本仓先例：终点锚被搬走时
负终点被 `slice` 解释成"从末尾倒数"，区间静默放大到接近整份文件，守卫照绿却不再测量它声称的那一段）。
两向锁：段外新增不红 / 段内新增必红 / 锚点缺失判 SELF_FAULT 且 CLI 退 2。

609 个 `.json` 是已入库的审计留痕。删除受轨文件必须走 `git rm` 评审，且会让 38 个 worktree 同时出现大规模 `D`、与在飞提交正面撞车；`safe-delete.js` 对受轨文件也一律拒绝。改为：本 PR 只解除「删除会反过来惩罚提交速度」这条耦合，堆积本身作为独立治理项登记（该目录每月增量 2026-10 已达 607，且当前无回收机制）。

## Risks / Trade-offs

- **守门件被改坏 ⇒ 全体 worktree 每次提交受影响**。缓解：改动面严格限于那 6 行；分支守卫 / 版本同步 / 质量节拍 / CCG 门禁四段一行不动；`pre-commit.test.sh` 全 16 个场景必须全绿（含既有 15 个防回归），另有 5 条变异反证必须**指名**变红。
- **一次 `git add` 的原子性取代逐次 add**：极端情形（某路径此刻正被别的进程独占）下旧写法只丢那一条、新写法整批失败后回退，回退路径已保留逐条语义并出声，因此不比旧行为更差。
- **不闭合机器级 ~1 秒/进程**：本 PR 后单次提交回到秒级量，但「所有 agent 工具链都慢」仍在。若只合本 PR 而不做排除清单，下一次出现「多会话共同变慢」时，本仓没有 O(N) 这条可归因，容易被误判成「又是钩子」。因此排除清单文档必须同 PR 交付。
- **规模锁的预算数字（≤3）与钩子总调用数会随其他段变化而漂移**：锁只把「随 N 增长」这条作为硬判据；绝对预算写成常量并允许**只能缩小**，避免某天加了一段正常逻辑就变成不可自愈的假红灯。
