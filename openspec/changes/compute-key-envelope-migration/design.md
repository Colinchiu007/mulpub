# Design: 官方 Key 迁移进 AES-256-GCM 信封体系

> 动机见 `proposal.md`（Why / 差异审计）。本文只写**怎么实现**与**为什么这样选**。
> 事实取证基线：`origin/main@5aed8337d`（除特别注明外，行号均为该基线）。

## Context

| 事实 | 取值 | 证据 |

| 契约 | 取值 | 证据 |

| 明文处理 | DK 用完 `fill(0)`；解出明文后在同一作用域内清空 | `:98,185-188,215-224` |

**当前状态（KMS 侧）——本设计的修正来源**

初稿把"生产 KMS 未定"当成开放问题，**实测不成立**：仓内已有生产形态实现，且选择口径已收敛为唯一一处。

| 事实 | 取值 | 证据 |
|---|---|---|
| KMS 选择的**唯一口径** | `createKmsFromEnv(env)`：配了 `MP_CLOUD_KMS_KEYRING` ⇒ 密钥环（生产，支持轮转）；否则 ⇒ `MP_CLOUD_KMS_LOCAL_KEY`（**仅开发/测试**）；两者都没配 ⇒ `KMS_CONFIG_INVALID` | `cloud-accounts/index.js:29-48` |
| 「配了但空白」vs「没配」 | **刻意区分**：前者是配置事故，必须当场 `KMS_CONFIG_INVALID`，不得静默降级成开发单密钥 | `index.js:35-37` |
| 生产实现 | `createKeyringKms` —— 文件密钥环：主密钥从「一个值」变成「一组带 id 的值 + active 指针」，**所用密钥 id 写进信封自身** ⇒ 轮转后旧信封仍可解；轮转 = 追加一把 + 移指针，**从不删旧密钥** | `keyring-kms.js:1-17,42-46` |
| 云 KMS 的定位 | **刻意留的接缝**，不是"以后再说"：抽象层只有 `{wrap, unwrap}`，真接云 KMS 换掉本模块即可，`envelope-crypto.js` 一行不改（有接口同形断言钉住） | `keyring-kms.js:13-17` |
| AAD 与密钥环 id 的关系 | **不得混为一谈**：AAD 绑业务 `keyId`（提供归属隔离）；密钥环 id **只决定用哪把主密钥**，不构成第二层归属隔离 | `keyring-kms.js:19-21` |

**这条修正的含义**：官方 Key 不需要"再选一次 KMS"，而应**复用同一处选择口径**（`createKmsFromEnv`）与同一套轮转语义——这也让 D1④「复用 KMS 形状」从"可行"升级为"应然"。

**约束**

- **K4**：`migrations/postgresql/` 已被 002-005 占用（`002_logto_identity` / `003_logto_webhook_events` / `004_member_commerce` / `005_cloud_accounts`），新迁移从 **006** 起，且编号受 checksum 台账锁定，撞号会让商务仓储整体硬失败。
- **K7**：全仓**无任务宿主**（无 cron/APScheduler/node-cron）⇒ 存量迁移不得依赖调度器。
- 现有信封的 `assertTriple` 把 `platform` 限制在 **`SUPPORTED_PLATFORMS`（发布平台白名单）**内（`:70-82`），而官方 Key 的 `provider` 是**模型供应商**（minimax / kling / zhipu / …）。

## Goals / Non-Goals

**Goals**

1. Node 侧（`api-publish-engine`）能在**不依赖 Python 进程**的前提下解开官方 Key，用于服务端代调。
2. 复用已有加密设施（KMS 抽象 + AES-256-GCM 原语 + fail-closed 纪律），**不引入新依赖**。
3. 存量 Fernet 密文可**安全、幂等、可续跑**地迁移；零存量流量窗口内完成。
4. 迁移全过程**可回滚**，且回滚点明确；只有最后一步（删列）不可逆且需显式授权。
5. 安全性质**不弱于现状**：行级绑定、明文不落地、错误不降级。

**Non-Goals**

- 不做官方算力供给链路本身（套餐池 / 调度 / 扣费 / 供给资格）——属另一 change（`DESIGN-COMPUTE-BILLING-MODEL-2026-10-11.md` §10 四个决策点未定）。
- 不选型具体云 KMS 供应商；本 change 只定义抽象形状与配置项（选型属部署决策）。
- 不改 `official_keys` 的对外 API 契约（仍只返回掩码）。
- 不改桌面端（客户端始终拿不到官方 Key）。
- **不为"顺手"把模型供应商加进 `SUPPORTED_PLATFORMS`**（见 D1）。

## Decisions

### D1. 复用边界：共用 KMS 抽象与算法常量，**不共用** `createEnvelopeCrypto`

| 选项 | 判断 |
|---|---|
| ① 直接调用 `createEnvelopeCrypto`（合成三元组） | ❌ **不可行**：`assertTriple` 的 `platform` 必须命中 `SUPPORTED_PLATFORMS`（发布平台白名单），模型供应商不在其中，直接抛 `ACCOUNT_PLATFORM_UNSUPPORTED` |
| ② 把模型供应商加进 `SUPPORTED_PLATFORMS` | ❌ **拒绝**：该白名单是"发布平台"概念，被云端凭证链路与桌面端使用。把"模型供应商"塞进去会让两个概念在同一真源里互相污染，且扩大了 `credentials` 的合法平台面 |
| ③ 官方 Key 另写一套加密（不复用） | ❌ **拒绝**：违背 Q2 决策初衷，且两套 KMS 封装必然漂移 |
| ④ **新增 `official-key-envelope.js`：复用 KMS 形状 + 从 `validate-account` 同源引用算法常量（`IV_BYTES`/`AUTH_TAG_BYTES`/`ENVELOPE_ALG`），自带归属元组与校验** | ✅ **选此** |
| ⑤ 复用 `createKmsFromEnv` 的**唯一选择口径**（不另立第三套判断） | ✅ **同时采纳**：官方 Key 与云端凭证走同一处 KMS 选择与轮转语义（见 Context「KMS 侧」） |

**理由**：官方 Key 需要的是"同一套密码学参数 + 不同的归属语义"，而不是"同一套归属语义"。把归属语义参数化会污染云端凭证的强校验（那条链路的 AAD 三元组是它防跨账号串解的**唯一硬约束**，`envelope-crypto.js:7-9` 明确写了）；反之另起一套参数则会漂移。

**配套防漂移锁（已按实测收窄，避免提出一条"当天就红"的锁）**：`IV_BYTES(12)` / `AUTH_TAG_BYTES(16)` / `DATA_KEY_BYTES(32)` 三组字面量**仓内已有重复声明**——`keyring-kms.js:38-40` 就自己声明了一遍。因此本 change 的锁**只覆盖"两个信封模块"**（`envelope-crypto.js` 与新增的 `official-key-envelope.js`）：断言二者从同一模块 import 这三个常量、不得各自声明字面量。**`keyring-kms.js` 的既有重复声明不在本次收口范围**（它属另一条链路，顺手收口会把本 change 的爆炸半径拉大），仅登记为遗留。

### D2. 格式族标识：**算法常量共用，格式族由 `v` 独立区分**（修正 i4）

**评审 i4 指出的自相矛盾成立**：D1 写"共用算法常量（含 alg）"，D2 又写"独立 alg 标识"。二者不能同时为真。**改正后的口径分两类，不得混用**：

| 类别 | 取值 | 是否共用 | 理由 |
|---|---|---|---|
| **算法原语常量** | `IV_BYTES=12` / `AUTH_TAG_BYTES=16` / `DATA_KEY_BYTES=32` | ✅ **共用**（从同一模块 import） | 它们是 AES-256-GCM 的参数，两种用途**确实是同一个算法**，各自声明字面量只会漂移 |
| **算法名 `alg`** | `'AES-256-GCM'` | ✅ **共用（相同值）** | `alg` 描述的是**算法**，而两族用的是同一算法 ⇒ 取值本就应当相同；此处无矛盾可言 |
| **格式族标识 `v`** | 云端凭证 `ENVELOPE_VERSION` vs 官方 Key `'official-key/1'` | ❌ **必须不同** | `v` 描述的是**格式族**（决定 AAD 材料与解包路径）。同 `v` 而 AAD 构造不同 ⇒ 无法判别格式，只能靠"试解失败"识别 |

**决定**：`v` 独立、`alg` 与算法常量共用；解码时**先校验 `v` 再解**，`v` 不匹配一律拒绝，不做"猜格式"。

**替代方案**：复用 `ENVELOPE_VERSION` + 靠 provider 字段区分 —— 拒绝：格式版本号必须能独立识别格式，靠外部字段区分等于把版本语义拆散。

### D3. 归属元组与两层 AAD 的职责划分

| 层 | 取值 | 职责 |
|---|---|---|
| **KMS 包裹上下文 `keyId`** | `official:<provider>` | 只回答"这把 DK 属于哪个供应商"，**不提供行级绑定** |
| **外层 AES-GCM AAD** | `` `official|${provider}|${keyRowId}` `` | **行级绑定**：把密文钉死在这一行 |

**必须写清楚的一点**：DK 与 KMS 上下文本身**不区分同一 provider 下的不同行**——若只靠 `keyId`，A 行的 `encryptedDataKey` 换到 B 行仍可能解开。行级绑定**完全由外层 AAD 承担**（`keyRowId` 进 AAD ⇒ 换行必 GCM 认证失败）。这与云端凭证信封同一设计（`envelope-crypto.js:7-9`），但**材料不同、必须各自显式声明**，不能靠"看起来一样"推断。

**替代方案**：`keyId` 也带上行 id（`official:<provider>:<keyId>`）—— 拒绝，会让 KMS 侧的 wrap 上下文数量随行数增长（每次新增 Key 都产生新的 KMS 上下文），收益与外层 AAD 重复。

### D4. 存储形态：**新表** `official_key_envelopes`，而非在 `official_keys` 上扩列

| 选项 | 判断 |
|---|---|
| ① `official_keys` 扩列（6 个信封字段：v/alg/iv/ct/tag/edk） | ❌ `official_keys` 已有 15 列，再加 6 列变宽表；且 6 个字段的 `NOT NULL` 与唯一性在一个宽表里无法独立约束 |
| ② **新表 `official_key_envelopes`**（`key_id` 唯一 FK → `official_keys.id`，字段 `v/alg/iv/ciphertext/tag/encrypted_data_key/created_at`，`key_id` UNIQUE） | ✅ **选此** |

**关键约束（实测）**：`official_keys.api_key` 是 **`NOT NULL`**（`models.py:122`）。因此**不能**在过渡期"只写新表、不写旧列"——那会让插入失败。二选一：

- **(a) 过渡期双写**：写 Key 时同时产出 Fernet 密文（进 `api_key`）与信封（进新表）；信封为主，Fernet 为兼容副本，供回滚。
- **(b) 先做 006 迁移把 `api_key` 改为可空**，再只写信封。

**决定 (a) 双写**。理由：① (b) 需要改列的可空性，一旦 `api_key` 可空，"Key 缺失"与"未迁移"两种状态在该列上**无法区分**，巡检与排障都失去判据；② (a) 让"删旧列"成为唯一不可逆步骤，回滚面清晰；③ 双写窗口短（零存量流量），双份密文可接受。

**代价如实记录**：双写期间存在**两格式漂移**风险（某路径只写了一份）⇒ 由 D6 的巡检兜底。

### D5. 迁移执行者：admin 触发的幂等 CLI（**不用调度器**）

K7 已证全仓无任务宿主，且本次是**零存量流量**的一次性迁移，引入一个调度器只为跑一次迁移属于过度设计。

**做法**：

```
python -m ops_center.tools.migrate_official_keys [--batch N] [--dry-run] [--only <key_id>]
```

- **幂等**：以「该 `key_id` 已有信封**且可解开**」为跳过判据，重复运行安全；
- **逐行原子**：单行 = 一个事务（解密 Fernet → 封印为信封 → 写新表 → **回读校验可解开且明文一致** → commit）；
- **可续跑（按评审 round 3 的 i2 修正）**：续跑查询 SHALL 为「**无信封 OR 信封解不开**」，与幂等判据**对齐**。初稿只写 `envelope IS NULL`，而幂等判据是"已有且可解开" ⇒ 存在**判据缝隙**：某行若因误挂另一密钥环而留下"有信封但解不开"的残留，续跑会**跳过它**，D6 变红后却没有修复路径。故同时增加 `--repair`：把"有信封但解不开"的行**重新封印**（在旧值仍可由 Fernet 解出时）；
- **启动前 KMS 自检**：跑之前先做一次 `wrap` + `unwrap` 随机 DK 的往返——**挂错密钥环要在启动时暴露**，而不是跑到第 N 行才失败；
- **迁移 CLI 默认拒绝 `local` provider（评审 round 3 的 i3，安全）**：自检只证明"当前 KMS 往返可用"，**不能证明所用 KMS 是预期的那一类**。生产若只配了 `MP_CLOUD_KMS_LOCAL_KEY`，会把全部官方 Key 用**本机单密钥**封印，而错误在删列后固化且不可见。因此迁移 CLI SHALL **默认拒绝**以 `provider === 'local'` 封印官方 Key，仅在显式传 `--allow-local`（供 CI/开发）时放行；
- **迁移报告须登记密钥环身份（评审 round 3 的 i7）**：报告 SHALL 记录所用密钥环的**密钥 id 列表**，并与部署文档登记的**预期清单**比对后才允许放行——否则"挂了一个空环/新环"时自检通过、巡检全绿，错误只在未来轮转时才暴露；
- **fail-closed**：KMS 自检不过 ⇒ **整批拒绝启动**（不得"跳过加密直接写明文"）；Fernet 解密失败 ⇒ 该行不计入成功、**不写半成品**；
- **写路径（非迁移）的 KMS 故障语义（评审 round 3 的 i4）**：`key_service` 在双写期与仅信封期遇到 KMS 不可用时 SHALL **fail-closed**——拒绝写入并返回明确错误（含"KMS 不可用"而非笼统 500），SHALL NOT 只写 Fernet 副本或"先存明文后补加密"（后者正是 PRD §8.3 禁止的降级形态）；
- **孤儿信封（评审 round 3 的 i4）**：`official_key_envelopes.key_id` 的外键 SHALL 为 `ON DELETE CASCADE`，并把「**不存在孤儿信封**」纳入 D6 巡检（初稿 D6-1 只查"每行有且仅有一条信封"，不查"信封有对应行"）。

**失败语义与残留行处置（修正评审 i3）**

评审 i3 成立：初稿"单行失败不中断整批"+"KMS 不可用整批拒绝启动"两条并置，会留下"部分行已 commit、部分未写"的状态，而初稿没写清这种残留是否可恢复。**补齐如下**：

- **默认 fail-fast**：遇到**首个**失败即**停机**并报告；`--continue-on-error` 为**显式可选**，仅用于"已知个别坏行"的场景。理由：盲目继续会把**系统性故障**（挂错密钥环、schema 不符）伪装成"若干行数据问题"，既浪费整批时间又掩盖配置事故；
- **残留行是否可恢复 —— 是，且无害**：① 每行信封**自包含**（同一密钥环可解），不依赖"整批完成"这个状态；② **旧列 `api_key`（Fernet）在步骤 8 之前始终保留**，任何时刻都存在一条完整可用的读取路径（双读），因此迁移进行到一半**不会出现"两边都读不到"**；③ 回滚 = 删除新表记录，**旧列未动、不需要数据恢复**；
- **唯一真正不可恢复的情形是"密钥环文件丢失"**——它与云端凭证同族，**与迁移是否分批无关**（分批不放大也不缩小该风险）；缓解 = 密钥环"从不删旧密钥"的既有纪律（`keyring-kms.js:9-11`）+ 迁移前备份环文件（R1）；
- **停机后如何续跑**：修复原因（换回正确密钥环 / 处理坏行）后原样重跑，幂等跳过已完成行。

### D6. 一致性巡检与判据

迁移的"成功"不能只看行数。巡检脚本 `--verify` 判据（每条都必须能独立变红）：

1. **覆盖**：`official_keys` 中每行都有且仅有一条信封记录（`COUNT` 对账）；
2. **可解**：信封能在 Node 侧解开（用与生产同一模块，非另写一份解密代码）；
3. **一致**：解出的明文与 `api_key`（Fernet）解出的明文**逐字节相等**——这条是双写漂移的唯一机械判据；
4. **绑定**：把任一行的 `encrypted_data_key` / `ciphertext` 换到另一行，必须解不开（变异反证，见测试策略）；
5. **无孤儿（评审 round 3 的 i4 补）**：`official_key_envelopes` 中不存在没有对应 `official_keys` 行的记录（删 Key 行后的残留）。初稿的判据 1 只查了"每行有信封"这一个方向，反向没查。

### D7. 解密主体与最小权限

| 主体 | 迁移前 | 迁移后 |
|---|---|---|
| Python（ops-center） | 唯一能解（Fernet） | 能解信封（需 KMS 客户端）——**过渡期同时保留 Fernet 读** |
| Node（api-publish-engine） | **不能解** | 能解信封（本 change 的交付目标） |

**权限与明文处置收口（按评审 round 2 的 i3 改写——初稿"明文不出模块"被本设计自身需求推翻）**

初稿写"明文**不出**模块"，但 D11 已证明管理面存在 `get_key(reveal=True)` 这类**必须把明文交给调用方**的路径。两者不能同时成立，**按事实改正**：

| 情形 | 明文处置 |
|---|---|
| **常规消费**（服务端代调模型） | 明文**不出**解封模块：模块对外只给"用它去做一次调用"的短时句柄或直接完成调用，调用方拿不到可长期持有的明文 |
| **显式授权例外**：`get_key(reveal=True)` | 明文**可以**返回给管理面，但这是**例外而非默认**，且必须同时满足：① 仅 `require_admin`；② 读取行为**写入配置审计日志**（`config_audit_log` 同族），不记明文本身，只记"谁在何时查看了哪条 Key"；③ 明文**绝不**进日志/错误信息/返回值以外的通道；④ 该路径的返回体不得被任何缓存层留存 |
| **掩码比对**（`update_key` 判"值是否未变"） | 明文只在**函数内短时作用域**存在，比较后立即 `fill(0)`，不返回调用方 |
| 通用 | 明文 Buffer 用后 `fill(0)`（沿用 `envelope-crypto.js:98,185-188` 的纪律）；主密钥与明文不得出现在返回值、错误信息与 `describe()` 中 |

⇒ 口径从"不出模块"改为**"默认不出模块；唯一例外是管理面 reveal，且有独立审计与限权约束"**——这样契约与事实一致，且例外本身是被约束的。

**句柄接口形态必须写死（评审 round 3 的 i6）**：初稿只说"短时句柄/直接完成调用"，**未定义接口形态与存活期**，而两处真实调用点（Node 服务端代调、Python `model_preset_service.py:1122` 把 Key 发往上游）如何落进该约束并不明确。补齐：

- 解封模块对外 SHALL 只提供**回调式**入口 `withKey(keyRowId, async (plaintext) => { ... })`：明文只在回调**作用域内**有效，模块在回调返回后立即 `fill(0)`；
- 明文 SHALL NOT 被序列化、SHALL NOT 被赋值到回调外可及的长存活变量、SHALL NOT 进入任何缓存；
- 两个调用点 SHALL 通过该入口完成（HTTP 请求头组装在回调内完成并立即失效），**禁止**先取出明文再在别处使用。
- **主密钥不入库、不进日志、不进记忆**；日志沿用 S6 已加固的脱敏（键级优先）；
- **KMS 选择复用唯一口径**（修正初稿）：官方 Key 路径 SHALL 调用 `createKmsFromEnv`（`cloud-accounts/index.js:41-48`），**不得**另写第三套"用哪个 KMS"的判断。该口径已具备两条必要性质：① 两者都没配 ⇒ `KMS_CONFIG_INVALID`（fail-closed，不是静默降级）；②「配了但空白」与「没配」被刻意区分（`index.js:35-37`），配置事故不会伪装成开发模式。`provider`（`keyring` / `local`）作为**运维观测形状**返回，绝不含主密钥。
- **是否对官方 Key 面追加更严断言 = 开放问题**：现约定允许 `provider === 'local'` 存在（供开发/测试），但官方 Key 面未来承载**真实付费流量**。是否要求"该面在生产必须 `provider === 'keyring'`"需在 spec 阶段定（见 Open Questions 2）——初稿曾把"启动期断言"直接写成决定，**过于武断**，已降级为开放问题。

### D8. 过渡期读取顺序（双读）与唯一真源

- **写**：双写（D4a）；
- **读**：**信封优先，Fernet 兜底**（仅过渡期）。**兜底必须出声**（warn 级日志 + 计数），否则"还在读旧格式"这件事会静默持续到删列当天才暴露；
- **真源**：过渡期出现不一致时**以信封为准**，并把该行计入巡检报告的"漂移"栏（不静默覆盖）。

### D9. 收尾删列：独立提交 + 显式授权 + 不可逆声明

删除 `api_key` 列与其读写路径属 **BREAKING（内部）**，且是**唯一不可逆步骤**。

- **独立 PR**，不与前序步骤混提；
- 前置条件：巡检四项全绿 **且** 双读兜底计数连续 0（说明没有老数据依赖旧格式）；
- 前置条件：回滚方案已从"回滚代码"变为"从备份恢复"——**该变更必须写进部署文档并由运营方显式授权**（本 change 不自动执行）。

### D10. AAD 材料**在本 change 内定型**，扩展走 `v` 升级（修正评审 i1）

评审 i1 成立：把「AAD 是否承载套餐/池」推给后续 change，而它**改变密文格式**、且 D6-4 的变异反证与续跑判据都依赖最终 AAD ⇒ 属"硬前置被推迟"。

**决定（本 change 内定型，不留悬空）**

- v1 的 AAD 材料**锁定为** `official|<provider>|<keyRowId>`；`provider` 与行 id 都进 AAD ⇒ 跨 provider / 跨行替换必失败；
- **未来若要承载套餐/池维度，必须新开格式族 `v='official-key/2'`，不得就地修改 v1 的 AAD 材料**。理由：AAD 是密文的自证材料，改它等于让已入库密文全部解不开；用 `v` 升级可让 v1 密文继续按 v1 解包，属**增量**而非破坏；
- ⟹ 「套餐维度是否进来」**不再是本 change 的阻塞前置**：它决定的是"要不要再加一个 v2"，**不影响步骤 1-8 的任何一步**。评审给的二选一（本 change 定型 / 设为阻塞步骤 1 的前置）中，本设计选**前者**；
- 唯一保留的**优化**提示（非前置，且**有生效窗口**——评审 round 3 的 i8）：若 `provider_plans`（另一 change）在**步骤 1 的决策之前**就定型为"同一 provider 多套餐"，则优先直接用 v2 起步，省一次格式升级。**步骤 1 决策之后一律 v1**：中途切换 AAD 材料会让步骤 3（双写）、步骤 5（迁移）、步骤 6（巡检）与 D6-4 的变异反证**同时失效**（它们都以 v1 的 AAD 材料为断言对象），因此**禁止**在步骤 1 之后变更格式族。

### D11. Python 侧职责**在本 change 内定案：必须实现同一信封读取**（修正评审 i2）

评审 i2 成立：OQ「Python 能否读信封」直接决定步骤 8 能否执行，却排在序列末端 ⇒ 收尾路径建立在未定前提上。

**取证后定案**：Python 侧**存在 3 处需要官方 Key 明文的读路径**，因此**不能**把读职责完全收敛到 Node：

| Python 读路径 | 需要明文的原因 | 证据 |
|---|---|---|
| `get_key(reveal=True)` | 管理面「二次确认查看明文」 | `ops-center/backend/services/key_service.py:159` |
| `update_key` 的「掩码未变更」比对 | 需当前明文才能判"值是否没变" | `services/key_service.py:332-333` |
| `model_preset_service` 连通性测试回退取键 | 要把 Key 发给上游做探测 | `services/model_preset_service.py:1122` |

**决定**：**Python 侧实现同一信封读取**——`cryptography` 已提供 AES-256-GCM；密钥环 unwrap 按 `keyring-kms.js` 的持久形态实现同构解析（含密钥 id 前缀，见 `keyring-kms.js:42-46`）。

⇒ **步骤 8 的前提在本 change 内闭合**，不再有悬空前提出现在迁移序列末端。

**为什么不选"Node 代 Python 解密"**：会把"读官方 Key"变成一次跨进程调用，为 3 条**管理面**读路径引入新的在线依赖与失败面——与交接文档否决 Q2 选项 3 同因。

**跨语言等价性必须被机械断言（评审 round 2 的 i4 成立）**：让 Python 重实现同一条密码学（AES-256-GCM + 密钥环 unwrap + id 前缀解析）**本身就是漂移源**，而 D1 的防漂移锁只覆盖两个 JS 信封模块、**覆盖不到 Python 副本**。因此追加：

- **新增跨语言对拍测试**：构造固定 `DK` / `iv` / 明文，**Node 封印 → Python 解封** 与 **Python 封印 → Node 解封** 两个方向，断言逐字节一致；密钥环包裹格式（id 前缀 + iv + tag + 密文）双向解析一致；
- 该对拍 SHALL 进 CI（不是"本地跑过"），并作为 D6 巡检判据 2 的补充（判据 2 只覆盖"Node 能解"，对拍覆盖"两侧同解同一份密文"）；
- 反向断言：把 Python 侧的 AAD 材料改一位 ⇒ 对拍必须变红（证明它不是同义反复）。

**对拍必须覆盖 KMS 选择语义，而不只是算法（评审 round 3 的 i1——本轮最重的一条）**：`createKmsFromEnv` 是 **JS**，Python 迁移 CLI **调不到它** ⇒ 选择语义（keyring 优先 /「配了但空白」vs「没配」/ 两者都缺则 INVALID）**必然在 Python 侧被复刻**，而 D1 的防漂移锁与初稿对拍**都不覆盖这段选择逻辑**。复刻错的后果是**生产静默用 `local` 单密钥封印全部官方 Key**，且删列后不可见。修正：

- 选择规则 SHALL 以**声明式真源**入库（一张「环境状态 → 期望 provider」的判定表，含空白/缺失/双缺三类边界）；
- 两侧实现（JS `createKmsFromEnv`、Python 复刻）SHALL **各自对该表**断言，而不是各写各的测试；
- D1 的防漂移锁扫描域相应扩为「两个 JS 信封模块 **+ Python 选择实现**」。

**密钥环字节解析必须做成纯函数以摆脱环境依赖（评审 round 3 的 i5）**：D12 的 CI 只配 `MP_CLOUD_KMS_LOCAL_KEY`（**无密钥 id 前缀**），因此"密钥环包裹格式双向解析"的对拍在 CI **无 fixture 可跑**——需求与 CI 环境矛盾。修正：把密钥环包裹的**字节解析/组装**抽成**纯函数**（输入输出皆为字节，不依赖任何 KMS 环境变量），对拍测试**注入字节样本**；这样 CI 无需密钥环即可覆盖该格式。

### D12. 非生产环境的 KMS 注入路径（修正评审 i7）

评审 i7 成立：步骤 6 的"生产禁用本地 KMS"断言排在迁移 CLI 之后，但迁移 CLI 在开发/测试下**反而需要**能跑。

| 环境 | KMS 取值 | 判据 |
|---|---|---|
| 单测 | `createLocalKms({ key })` **显式注入** | 测试自带 32 字节 hex；不读环境变量 |
| CI | `MP_CLOUD_KMS_LOCAL_KEY`（32 字节 hex） | 迁移 CLI 的测试路径必须在**无 keyring** 时可跑，否则迁移逻辑在 CI 里无法被测 |
| 预发 / 生产 | `MP_CLOUD_KMS_KEYRING` 环文件 | `provider === 'keyring'` |

- 因此「生产必须 `keyring`」这类断言**只对生产生效**，且必须先定义**如何判定"生产"**（见 Open Questions 2）；否则会误伤 CI 与预发；
- 若最终决定**不追加**该断言（维持既有"`provider` 可观测、不做环境断言"的约定），本表退化为**运行手册条目**。**两种取值的后果差异必须在 spec 里写清**，不得含糊留白。

## Risks / Trade-offs

| # | 风险 | 缓解 |
|---|---|---|
| R1 | **主密钥丢失 ⇒ 全部官方 Key 不可恢复**（与云端凭证同族） | **缓解比初稿更强**：复用密钥环后，轮转 = 追加一把 + 移指针、**从不删旧密钥**（`keyring-kms.js:9-11`），"换密钥即报废数据"这一最危险形态被既有实现消除；仍需部署文档登记环文件托管 + 迁移前备份 `official_keys`。**补充（评审 round 2 的 i6）**：环文件**本身就是全部官方 Key 的主密钥**，因此其**读取侧访问控制**必须约束——权限最小化（仅属主可读）、仅迁移 CLI 与 KMS 进程可读、不得进备份以外的分发通道，并登记进部署文档的**访问控制清单**（初稿只防"丢失"，未防"被越权读走"） |
| R10 | **把密钥环 id 误当第二层归属隔离**（`official-key-envelope` 若依赖"换密钥即解不开"来防跨行替换） | 显式写死：**行级绑定完全由外层 AAD 承担**，密钥环 id 只决定用哪把主密钥（`keyring-kms.js:19-21` 已就此事写下反向约束）；D6-4 的"换密文必失败"变异反证必须只由 AAD 触发 |
| R11 | **官方 Key 面在生产误用 `local` 单密钥**（该面承载真实付费流量） | ① `createKmsFromEnv` 已在"两者都没配"时 fail-closed；② 暴露 `provider` 供运维观测；③ 是否要求该面生产必须 `keyring` 列为开放问题 2；④ 迁移前备份 + 巡检可发现"信封解不开" |
| R12 | **常量重复声明收口范围失控** | D1 已把防漂移锁收窄到"两个信封模块"，`keyring-kms.js:38-40` 的既有重复仅登记遗留，不在本 change 收口 |
| R2 | **Node 侧新增解密能力扩大密钥暴露面**（原先只有 Python 能解） | D7：单一模块、明文不出模块、用后清零、不缓存；日志脱敏 |
| R3 | **双写漂移**（某路径只写一份） | D6-3 逐字节一致性巡检；单写路径的写入口收敛到 `key_service` 一处，由结构锁断言"不得有第二处直写 `api_key`" |
| R4 | **过渡期双读的兜底路径长期存活** | D8：兜底必须出声 + 计数；删列的前置条件是计数连续为 0 |
| R5 | **迁移中断留下部分信封** | D5 逐行原子 + 幂等 + 可续跑；巡检覆盖项（D6-1）机械发现缺口 |
| R6 | **`SUPPORTED_PLATFORMS` 被"顺手"扩写** | D1③ 明确拒绝；加结构锁：`SUPPORTED_PLATFORMS` 变更必须同步改桌面端发布能力清单（既有约束），使"+模型供应商"这种改动无法静默通过 |

| R8 | **迁移期间旧进程/新进程共存** | 部署顺序写死在 Migration Plan；过渡期保持双格式可读，使任一方向回滚都不需要数据恢复 |
| R9 | **零存量流量这一前提在实施期失效**（届时已接入供给链路） | 若实施前供给链路已上线，**本 change 必须先重跑差异审计**并重新评估"是否需要停机窗口"；此前提已写入 proposal 差异审计栏 |
