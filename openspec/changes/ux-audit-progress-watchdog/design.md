# Design: 发布进度「无更新」看门狗

## D1 锚点取「全局最近事件」，不取「每个任务各自陈旧」

面板要回答的问题是「还要不要等下去」，是**会话集合层面的单一事实**。若逐任务判陈旧再取
`some`，两个并发任务里一个刚上传、一个早就卡死时，界面上会出现「有的任务在动、面板却说没动静」
的自相矛盾；反之取全局最大值（最近一次任何事件）就不会与任务行的读数打架。

代价与如实声明：**单任务级停滞被全局口径吃掉**（A 卡 10 分钟、B 每 10 秒一动 ⇒ 不徽标）。
本 PR 接受这个代价，理由是解禁关闭的判据要保守（宁可少给一个可点的 ×，也不要谎报「没动静」），
而任务级的「这一步好久没变」属另一件事（现有行内百分比/阶段词已经在展示），不应混进同一条判据。

## D2 陈旧态点 × 是「收起」而不是「丢弃会话」

`handleClose()` 原本只做 `clearFinished()` + 「没有会话了就隐藏面板」。运行中的会话在
`clearFinished()` 后必然还在 ⇒ 若只是把 `disabled` 翻掉，× 会变成一个**看得见、点不动的死按钮**
（本仓反复出现的假修复形状）。

两条出路里选了副作用小的那条：

- 丢弃会话（`dismissSession`）→ 面板消失，但主进程如果**稍后**发来 `success/failed`，
  `handleProgressEvent` 会把它收纳成孤儿会话，而 `panelVisible` 已是 false ⇒ 用户看不到那次
  真实结果。等于为了「能关掉」而**牺牲证据**。
- 收进胶囊（`minimizePanel`）→ 面板同样消失（用户诉求满足），胶囊仍在、一次点击可回展开，
  迟到事件照常落进同一会话。

因此 × 在陈旧态的语义是「收起」。tooltip 文案必须说清这件事（`staleCloseHint` 原文含
「点击可收起面板（任务可能仍在后台进行）」），否则按钮图标（×）与动作（收起）不符。

## D3 计时器归组件所有，判据归纯函数

沿用 `usePublishProgressAutoCollapse` 已确立的分工：**store 不持计时器**（保持纯状态、可在
无组件环境下逐条测），**组件/组合式负责申请与清理**。判据本体再往外提一层到
`utils/publish-progress-staleness.js`，这样它可以在不 mount 任何东西的情况下把阈值、锚点、
射程、脏数据、时间跳变全部测完（本 PR 27 条纯函数用例就是靠这一点做到确定性的）。

轮询周期 15s 与阈值 3 分钟**是两个不同的量**，不能混用：周期只决定「多久重算一次已经多久没动静」，
阈值决定「算出来算不算陈旧」。文案粒度是分钟 ⇒ 15s 采样的最坏落后是 15 秒，肉眼不可见；
更密只会多烧定时器。

`hasRunning` 为 false 时停表（并在停表时刷一次读数），不给一个没有任何发布的应用留常驻定时器。

## D4 阈值不做环境变量覆盖

`process.env` 在渲染层不可用：Vite 生产构建把它替换为空对象桩（实测 `src` 下只有
`process.env.NODE_ENV` 这种被静态替换的写法能成立），所以 `MP_PUBLISH_STALE_MS` 这类旋钮
用户根本设不动。加它只会得到一条**看起来可配、实际恒默认**的装饰性防线。
判据本体用一条结构锁钉住这个决定（代码行里不得出现 `process.env`），并把「将来要可调就走设置页
真持久化」写进 PRD。

## D5 本 PR 只覆盖渲染层，不假装探测主进程

「没有事件」不等于「任务死了」。真正能定论的证据在主进程（任务队列状态、执行器是否在跑），
本 PR 不去读它 —— 措辞因此刻意是观测事实（「已 N 分钟无更新」）而不是判断（「发布已中断」）。
主进程侧的停滞检测/自愈属独立变更，与本条判据分界在 PRD §7 写明。

## D6 反证覆盖哪些面

14 条变异按「要证的危害」分组，而不是按「改了哪一行」：
判据本体（阈值改大 / 射程漏掉 running 过滤 / 终态集合漏 cancelled / 锚点缺席当新鲜 / 取最旧锚点 /
边界符号 / 分钟钳位 / 非法阈值不回落）、组合式（不 `immediate` 起表 / 卸载不停表）、
面板（可用性判据忽略陈旧 / 陈旧点击不收起 / 徽标 `role` 退化 / 胶囊提示顺序回退）。
每条必须**红且红在与该变异语义自洽的用例上**；NO-RED 一律按待解释异常处理，不得静默跳过。

## D7 QM-6 第一轮评审的四条采纳（fingerprint 8704be7834fb91ab）

评审返回 9 条问题、5 条进入裁决；逐条对当前 HEAD 重放后 **4 条成立并已修**（i1/i2/i4/i7），
1 条（i3，反证驱动的还原护栏）当场改造。以下记录"为什么这样修"，不是复述现象。

### i1 running 会话推不出任务锚点时仍被永久锁死

判据原来的射程是"running 会话里的非终态任务"，两条逃逸路径没覆盖：
`tasks` 为空（**可达** —— `registerSession` 允许只带 `batchId` 登记，`_ensureTask` 此时不被调用），
以及"全部任务已终态而会话还没被 `_recomputeSessionStatus` 移成 done"（异常态）。
两者都让 `lastEventAt` 恒 null ⇒ `stale=false`，而 `hasRunning=true` ⇒ × 永久禁用，
**与本 PR 宣称要消灭的症状同形**。

修法取"逐会话退回 `session.createdAt`"。关键约束：这个兜底**不参与全局 max**——
我第一版把它写成全局参与，于是刚登记的会话（`createdAt` 很新）会把同会话里早已停住的任务洗成新鲜，
徽标在正常场景反而不出现；该误形由变异 M17 常驻守住（实测红 11 条）。
数据形状异常（`tasks: null`）与空任务同类处理：异常数据不该变成"关闭入口永久锁死"。

### i2 终态相位被抄成两份

`TERMINAL_PHASES` 原本在判据里又写了一遍，注释自称"同语义"但没有任何机制保证 ——
这正是本 PR 自己在阈值上避免的错误（阈值有结构锁，终态集合当时没有）。
让判据 import store 会形成**循环依赖**（store 需要判据），所以把这张小语义表提到中立模块
`src/utils/publish-phases.js`，两侧都 import 它：store 的派生式
（`Array.from(PHASE_ENUM).filter(p => PUBLISH_TERMINAL_PHASES.has(p))`）保持不变，
"哪些相位算结束"这一件事只剩一处。
钉法两条：结构锁（判据与 store 的代码行都不得再出现第二份终态清单）+
**判别式**行为锁（同一份数据下，终态相位退回登记时刻、非终态相位用任务锚点 —— 两种结果相反才叫判据）。

### i4 类型假设没有取证

R4 的回落依赖 `session.createdAt` 是数字，而 diff 里既没有用例也没有引用生产者。
批评成立：如果它不是数字，"登记后从未收到事件"这一格会退化成"无结论"，
× 在解禁逻辑里永久禁用，**且界面不徽标、日志不吭声**。
补法不是加运行时校验（写者 `_createSession` 用的就是 `Date.now()`），
而是从**真 store** 走一遍：建会话 → 断 `Number.isFinite(createdAt)` → 把 `lastEventAt` 置 null
并把 `createdAt` 推到 200 秒前 → 断判据给陈旧。顺带成为"读者真的在链路上"的端到端证据。

### i7 胶囊的分钟数是否会自己走

徽标与胶囊共用同一份读数，但"共用"不等于"会更新"：若根组件在最小化时被卸载，
采样随卸载停止，胶囊的「已 N 分钟」会冻在收起那一刻，而我在 PRD 里写过"最坏落后 15 秒"。
补一条假时钟用例：最小化态挂载 ⇒ 断言现场只有 1 张采样表，推进 7 分钟后胶囊文本从
「已 3 分钟」走到「已 10 分钟」。它同时被 M9（不起表）与 M10（不停表）两条变异守住。

### i3 反证驱动的还原护栏"说的比做的多"

驱动里注入→跑测试→还原三步在 `try` 之外，`try/catch` 只包住了纯内存的 `mutate()`。
真实风险：`spawnSync` 自身抛错、Windows 文件占用、磁盘写满 —— 任一发生都会把源码留在**变异态**，
而 md5 核对永不执行。改为写入放进 `try`、还原放进 `finally`，还原失败即刻 `exit 4`；
探针自身抛错单列 `PROBE_BLIND`（不得与"MISSED=锁没抓住"混档，两者下一步相反）。
这条与本轮另外两次"探针说谎"（M4 首版把三元链改坏、锚点随重构失效）同族：
**驱动的可靠性不是自证的，要靠分档和逐条锚点校验。**
