# 设计：采集配额治理（hot-topics-throttle-url）

## 1. 为什么键要从「id」换成「配额键」

v2 的节流与熔断键都是 `config.id` / `source.id`。这个设计隐含了一个**不成立的假设**：
「一个端点对应一个来源身份」。实际配置里有两处破例：

| URL | 身份 | 理论频率（改前） |
|---|---|---|
| `https://weibo.com/ajax/statuses/hot_band` | `weibo`（主）、`weibo-emotion`、`weibo-health` | **3 次 / 10min** |
| `https://www.ithome.com/rss/` | `ithome-tech`、`ithome-ai` | **2 次 / 15min** |

而 `weibo-emotion`/`weibo-health` 的补拉阈值只有 4 条（多标签口径下计数很容易低于阈值），
`ithome-ai` 是本轮为 AI 分类新增的 —— 也就是说这条绕过路径**在正常使用里就会走到**。

### 1.1 键的设计取舍

| 候选 | 结论 |
|---|---|
| 保留 id | 就是缺陷本身 |
| 直接用 URL 原串 | 查询串差异（百度 `?tab=realtime` vs `?tab=finance`）会被当成两个端点，实际是同一台服务器的同类压力 |
| **host + path（归一化）** | ✅ 采纳：同端点同配额；query 差异合并；path 不同（`/rss/` vs `/api/x`）仍独立 |
| host only | 过粗：同一 CDN host 下不同 API 会被误合并 |

`throttleKey(url)` 实现：`new URL(url)` → `host + pathname`（小写、去尾斜杠、去 query）。
解析失败退化为整串小写（仍可作键，不会互相误伤）。

### 1.2 显式 `throttleKey` 的作用

- **逃生门**：若未来某个配置的 URL 归一化结果不符合预期（例如同一 host 下两个独立端点），
  可以用 `throttleKey` 精确指定配额归属，不必改归一化规则。
- **跨模块共享的预留接口**：快捷采集的 feed 类 `ithome` 源与热门选题补拉源打同一 RSS ——
  若未来要共享，双方声明同一个 `throttleKey` 即可，无需把两个模块耦在一起。
- 本轮已用它把 `ithome-tech`/`ithome-ai` 显式声明为同一配额（`'ithome-rss'`）。

### 1.3 单一真源纪律

`quotaKeyOf` 是**唯一**的键推导函数。service 层不得出现第二份「从 config 推键」的逻辑 ——
这与 `CATEGORY_KEYS` 五处契约是同一族问题：判据漂移比没有判据更危险。
回归锁 `不存在「同 URL 但 throttleKey 不同」的组合` 会扫描全部配置验证这一点。

## 2. P1 的口径细节

| 问题 | 决定 | 理由 |
|---|---|---|
| 间隔取多长 | 60s | 拦得住「连点」「轮询」；用户可感知的等待短 |
| 间隔内返回什么 | `{ ...cache, fromCache: true, throttled: true }` | 数据可见（不空白），且带标记让 UI/日志可区分 |
| `boostCategories` 是否豁免 | **豁免** | 那是用户指名的补拉意图；被 60s 拦掉等于功能失效（与评审 MINOR-3 取向一致） |
| `_lastManualRefreshAt` 何时更新 | **真实放行时**才更新 | 若在「被节流」时也更新，用户会陷入永远刷不动的死锁 |
| 非 force 路径是否受影响 | 否 | 自动刷新仍由缓存 TTL（10min）约束，语义不变 |

## 3. P3 的 fail-closed 方向

恢复快照时对非法载荷的处理是「清空状态」，不是「抛错」也不是「忽略坏条目保留其它」：

- **清空 = 退化成无记忆**，最坏情况是「重启后第一轮全量外呼」（v2 的既有行为），可接受；
- 若改成「忽略坏条目」，一条坏数据就可能让其它端点的节流被静默丢弃，反而更危险；
- 若抛错，构造器失败会让整个服务不可用，代价不成比例。

快照结构带 `version: 1`，为将来结构演进留位。

## 4. 与既有合同的关系

| 既有合同 | 是否受影响 | 说明 |
|---|---|---|
| 空列表视为失败 | 不变 | 仍按端点判，熔断记账的**键**变了 |
| fallback 顺序降级 | 不变 | 降级链仍挂在同一渠道身份下；且主端点与 fallback 的 URL 不同，配额天然独立 |
| 跳过不算失败（`ok: true`） | 不变 | `channelStats` 语义未动，UI「渠道不可用」标记不受影响 |
| 显式 boostCategories 不被吞 | 加强 | 现在同时豁免 P1 最小间隔 |
| 406 专项告警 | 不变 | 告警文案仍按渠道身份打印（人看的还是「哪个渠道坏了」） |

## 5. 未落地项（如实登记）

1. **快捷采集 feed 源与热门选题补拉的同端点共享**：`ithome` feed 源（快捷采集）与
   `ithome-tech/ai`（热门选题）打同一 RSS，两套限流仍各自独立。本轮用 `throttleKey`
   预留了接口，但未把快捷采集的 fetch 接到 `quotaKeyOf` 上（需要动快捷采集的依赖注入，
   改动面超出本轮目标）。真实增量有限：两边各有 30min/15min 节流，合计最坏 2 次/15min。
