# 提案：发布频率的四个「声明了没人接」面收编或删除

## 变更标识

`publish-frequency-unwired-surfaces`（2026-10-16）

## 为什么现在做

v4 收尾时把频率控制的"未接线清单"如实登记进 PRD §8（四条 + 一处不对称）。登记不是终点：
一份登记着的死接口比没有这个接口更危险 —— 它读起来像"能力已存在，只差接线"，
于是下一个会话可能直接**依赖**它，或照它的形状再抄一份。本变更逐条定夺：**能删的删、该接的接、
留下的必须说清它是给谁用的**。

四条面里有两条其实不只是"没接线"，而是**承诺了一件不存在的事**：

1. `clearRollbackDisabled(platform)` 的 docblock 写「用户手动清除…（设置页『我确认该平台接线正常』）」，
   而 `_disableRollbackForPlatform` 打出的告警更直接：「重启**或用户在设置页确认后**解除」。
   实测全仓无 IPC handler、无 UI 入口、无任何调用点（唯一"消费者"是它自己的回归测试）。
   ⇒ 这不是死代码，是一句**假承诺**；而且它给的权力（重新允许一个"接线未证实"的平台回滚窗口）
   本身就不是我们想要的能力。
2. `PLATFORM_BUCKET_DAILY_KEY_PREFIX = 'platform-daily'`：v2 设想过"平台级日配额"，
   日计数的写入点在 `if (accountKey)` 分支里 ⇒ 这个前缀**从未被任何代码路径产出过**，
   也没有对应的 env 名、档位数值或设置页入口。留着它 = 留下一个"看起来存在的通道"。

另外两条是"实现正确但没有生产调用点"的同一形态（本仓已把它记作「装饰性链路」家族）：

3. `store.prunePublishDailyCount(todayKey, ownerSubject)`：保留窗口（`RETAIN_DAYS = 7`）实现完整、
   有单测，但**没有任何调用方** ⇒ `publish_daily_count` 只增不减。
   先例就在同一个文件族里：`bootstrap/phase1-context.js` 里 signalCollector 的那行注释写着
   「启动时执行一次 30 天清理（C2 修复：**cleanup 需要有生产调用点**）」。
4. `getProbeCounts()`：D1 的 `inflightUnknown`、`rollbackDisabledPlatforms`、`missingWiring`
   三个探针的唯一出口，消费者只有测试。

## 还有一处同族的"同一个量三处各有各的界"

日配额的合法域：env **无上界**、设置页覆盖 **无上界**、而设置页输入框 **`:max="999"`**（分钟那两处
同理硬编码 `:max="10080"`）。后果不是难看，是**两套真值**：用户从 UI 填不进 5000，却可以用 env 填进去；
env 填了个荒谬值也没人告诉他界在哪。间隔维度早就有 `MAX_INTERVAL_MS` 单点钳位的先例，日配额没有。

## 打算怎么做（一句话版）

删 1、2；把 3 接进启动期维护（**按 owner 逐个删**，不跨 owner 一把删）；
4 **本片不造 UI**，如实登记为"观测面，当前消费者是测试"，另开工单；
新增 `MAX_DAILY_QUOTA` 单点持有日配额上界，env 钳位出声、覆盖拒绝越界、渲染层经 `getPolicy` 下发后绑定。

## 分层与风险

运行时代码变更（`packages/shared-utils` + `apps/desktop/electron` + 渲染层）⇒ 隔离 worktree、
TDD 先红、QM-1 打包必跑（触 `electron/`）、QM-6 双模型评审。
行为风险集中在两处：**删 `clearRollbackDisabled`** 让"解除停用"只剩重启一条路
（方向恒为"多等一个窗口"，不是少等）；**启动期裁剪** 如果日键口径与写入方不同源，
表现是"该删的没删"或"昨天的行今天被删"，故日键必须取守卫的 `today()`，不在启动侧另算。

## 明确不做

- 不给探针计数做设置页展示（那是 v2 tasks 3.4 未完成的半片，属功能开发，另片）。
- 不实现"平台级日配额"（没有任何数值来源，实现它才是造需求）。
- 不动 `full-auto-pipeline` 的 5s 直发旁路（PRD §8 已单独登记，属执行模型变更）。
- 不改守卫的三桶判定语义、抖动、D1 终身锁、回滚硬顶公式。
