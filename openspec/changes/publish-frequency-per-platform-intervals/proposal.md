# Proposal：发布频率账号间隔改为「逐平台独立」（视频号从严，其余取宽松保守值）

change: `publish-frequency-per-platform-intervals`
日期：2026-10-16
复杂度定档：**L+ / 中高风险**（跨 `packages/shared-utils` + `apps/desktop/electron` + 渲染层 + locales + 文档；
命中「状态机 + 持久化 + 数据校验」三条 QM-6 触发域）⇒ 完整流程：OpenSpec change + TDD + QM-1 + QM-6 + PR。

## 1. 为什么要做（问题，不是"想加功能"）

现行"同账号发布最小间隔"（`accountMinMs`）**按档位三选一**，档位由
`packages/shared-utils/src/publish-frequency-policy.js` 的 `PLATFORM_TIER`（:96-114）映射到
`TIER_PRESETS`（:86-93），15 个平台里没有任何一个有自己的间隔字面量：

| 档位 | accountMinMs | platformMinMs | accountDailyMax | 平台 |
|---|---|---|---|---|
| `long` | 5′ | 1′ | 200 | wechat_mp / zhihu / baijiahao / toutiao |
| `clip` | 3′ | 1′ | 350 | douyin / kuaishou / **tencent_video** / xiaohongshu / bilibili / youtube / tiktok / instagram / facebook |
| `short` | 1′ | 1′ | 500 | weibo / twitter |

后果：**限流严格程度不同的平台被同一把闸管着**。视频号与微博拿到"同为短视频/短内容"的宽松间隔，
而两者对"短时间连发"的容忍度差异极大——用户的现场感受是"视频号发两条间隔很短就被限流"，
但在现有结构下想单独把视频号收紧，只能改档位（会连带动 8 个平台）或去改代码常量。

## 2. 调研做了什么、得到什么（把"取证"与"暂定"分开写）

对外公开口径检索结论（2026-10-16 当场取证）：

1. **抖音**：检索到的运营口径明确写着"官方没有『发 3 条就限流』的硬规定，限流的核心是内容质量差、
   违规、同质化，不是数量本身"；数量侧给的是"新号前 7 天 1–3 条、老号单日 10 条以内、蓝V 20 条/天"。
   ⇒ **间隔无任何官方量化数值**，只有"给发布时间加随机区间"这类定性建议。
   来源：NoobClaw《抖音一天发几条?频率与内容重复》（2026-08-18）。
2. **微信视频号**：检索到的多篇运营口径给的是**按粉丝量分级的日发上限**——
   "千粉以下每天只能发 1 条；万粉以下每天发 2 条；万粉以上每天最多 5 条；新手期(0-30 天) 3-5 条、
   稳定期(30 天+) 1-2 条"，并提示"超出限制直接限流"。
   ⇒ **同样没有官方间隔值**，但"数量上限远低于其他平台且超限即限流"这一条是明确的定性差异，
   足以支撑"视频号单独收紧"的产品决策。
   来源：极致了《视频号一天发几条才不踩雷》（2026-03-11）等。
3. **百家号 / 公众号 / 小红书 / B 站 / 知乎 / 头条 / 微博 / 海外平台（YouTube/TikTok/Instagram/Facebook）**：
   本轮检索未取到可信的量化间隔（海外平台的公开文档只讲配额 API 调用速率，不讲"两条内容之间的间隔"）。

**因此本片的取值口径是**：只有视频号按产品决策从严（60′），其余 14 个平台
**保持现行档位默认值不变**（零行为变化），但把它们落成"逐平台可读、可单独调"的表结构——
以后任何平台要收紧，改一行数据而不是改档位分类。每个默认值的性质在表里如实标注
`取证` 或 `暂定`（见 design.md §2），不把"没取到数"写成"平台允许"。

## 3. 改什么（范围）

1. **策略层（单一真源）**：新增 `PLATFORM_ACCOUNT_MIN_INTERVAL_MS`（15 项逐平台毫秒表），
   `PLATFORM_FREQUENCY_POLICY[platform].accountMinMs` 由它提供；`TIER_PRESETS` 继续持有
   `platformMinMs` 与 `accountDailyMax`（档位仍是这两维的真源，不拆）。
   视频号 = 60′；其余 = 各自档位现值。
2. **覆盖层**：设置页覆盖新增按平台维度 `accountMinMsByPlatform: { <platform>: ms }`，
   合法域 `[0, MAX_INTERVAL_MS]` 整数；沿用"全有或全无"语义。
   **优先级必须是**：平台专属覆盖 > 全局覆盖 `accountMinMs` > env 全局 > 逐平台表默认
   （否则"给视频号设 60 分钟"会被一个全局值抹掉，且这种抹掉不留痕迹）。
3. **env 层**：新增单条 JSON env `MP_PUBLISH_ACCOUNT_MIN_INTERVAL_MS_JSON`
   （例：`{"tencent_video":3600000,"douyin":600000}`）。解析失败/含未知平台/值非法 ⇒
   **整条 env 作废 + 出声**，不部分生效（与既有"半生效态不可解释"同一条纪律）。
   不新增 15 个独立 env：那会把"一个数被当几道闸"的老问题换成"15 个没人记得存在的开关"。
4. **IPC 下发**：`publishFreq:getPolicy` 已经在逐平台返回 `_intervals(p)`（:27-29），
   本片补 `accountMinMsByPlatformDefaults`（表默认，供 UI 显示"未覆盖时是多少"）——
   渲染层继续**不持有任何数字**（既有约束，AGENTS/ARCH §7 的"文案纪律"）。
5. **设置页**：新增「按平台覆盖同账号间隔（分钟）」区，15 个 `el-input-number`（留空=不覆盖），
   复用现有 `:min="0" :max="bounds.intervalMinutes"` 绑定；展示区把"按档位分组"的文案改成
   "逐平台生效值"列表。**刻意不引入新组件类型**（`el-table` 等），避免动
   `src/plugins/element-plus.js` 的按需登记与样式闭包（AGENTS 的 P4/P5/P6 像素回归源）。
6. **locales**：zh/en 成对新增键；新增用户可见文案一律进 locales（Gate 7）。
7. **文档**：新增 `01-docs/PRD-PUBLISH-FREQUENCY-V5-2026-10-16.md`（数值表 + 依据 + 校验 + 交互 +
   显示项 + 提示文字 + 回退路径）；同步改写 `01-docs/ARCH-PUBLISH-FREQUENCY-AND-QUEUE-2026-10-16.md`
   §2 数值表、§3 合法域/env 全表、§7 用户可见面、§9 活例外；CHANGELOG 收口。

## 4. 明确不做什么（防范围膨胀）

- **不改日配额**：视频号 `accountDailyMax` 现在仍是 350 条/天，而公开运营口径是"日发 1–5 条"。
  这个不对称**如实登记为未闭合**（PRD v5 §9 + ARCH §9 活例外），不在本片偷偷改数值——
  它改的是"能不能发"而不是"多久能发"，属另一刀，且需要用户拍板取值。
- **不动平台档（`platformMinMs`）**：跨账号的 1′ 统一档保留，v4 的 §3 理由不变。
- **不碰两条伪防线**（`publish-spacer` 18′、`publish-schedule-contract` 5′）：
  本片只把守卫侧的真源改成逐平台；两条伪防线仍在 ARCH §9 登记，等各自的片子收。
- **不做"新号/老号分级"**：调研里的粉丝量分级需要账号画像数据，本仓没有可靠的粉丝量来源；
  没有数据就不假装做能力（登记为后续候选）。
- **不给视频号写死代码分支**：所有差异化只进数据表，`if (platform === 'tencent_video')` 这种写法一律禁止。

## 5. 验收标准（可判据）

1. 15 个平台各自的 `accountMinMs` 能被逐平台断言钉住；视频号 60′ 且是唯一偏离档位默认的平台。
2. 给 douyin 设 5 分钟的平台专属覆盖时，视频号仍走自己的 60′；给全局覆盖设 1 分钟时，
   平台专属覆盖仍然赢（优先级不被翻转）。
3. 非法 JSON env ⇒ 整条作废并出声，**生效值全部回到表默认**（不得一半生效）。
4. 设置页新增/修改平台覆盖后保存，重新打开回显一致；留空的平台提交后不落库（`null` 语义）。
5. 渲染层源码里不出现任何新的间隔数字字面量（结构锁）。
6. QM-1 打包 + 启动三层判据通过；`packages/shared-utils` 全量与桌面消费者并集全绿；
   变异反证覆盖"优先级翻转""表被档位派生覆盖""env 部分生效"三种退化各至少一条。
