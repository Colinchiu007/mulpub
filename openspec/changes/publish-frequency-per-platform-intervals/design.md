# Design：逐平台账号间隔

## 决策 1 —— 用「逐平台表」而不是「加档位」或「给视频号写 if」

三个候选：

| 方案 | 判定 | 理由 |
|---|---|---|
| A. 新增第四档 `strict`，把视频号挪进去 | ❌ 否 | 档位是"分类器"，为一个平台开一档会让 `TIER_ENV`（日配额按三档 env）、设置页"按档位分组文案"、`档间单调` 锁全部要跟着改语义；且下次任何平台要调，又得开第五档 |
| B. `if (platform === 'tencent_video') return 60 * MIN` | ❌ 否 | 把策略塞进控制流：合法域、env、覆盖、UI 显示各读各的，正是本片要消灭的"一个量抄成多份"。AGENTS 的"单一真源"直接禁止 |
| C. **逐平台默认表 + 档位仍管其余两维**（采纳） | ✅ | `accountMinMs` 从"档位派生"改为"逐平台字面量"；`platformMinMs`/`accountDailyMax` 继续按档（它们确实没有逐平台差异需求）。改动面最小，且"以后任何平台要收紧 = 改一行数据" |

## 决策 2 —— 优先级链（本片最容易做错的地方）

```
1. 设置页「平台专属覆盖」 accountMinMsByPlatform[platform]     ← 最细粒度，必须赢
2. 设置页「全局覆盖」     accountMinMs                          ← 保留既有语义（一键压平）
3. env 平台专属          MP_PUBLISH_ACCOUNT_MIN_INTERVAL_MS_JSON[platform]
4. env 全局              MP_PUBLISH_MIN_INTERVAL_MS
5. 逐平台表默认          PLATFORM_ACCOUNT_MIN_INTERVAL_MS[platform]
```

两条硬约束：

- **细粒度必须赢粗粒度**。若 2 赢 1，用户"给视频号单独设 60 分钟"会被一个全局值静默抹掉——
  与 2026-10-14 那条"账号档被全局值压平"同族事故。
- **env 与设置页的关系保持不变**：现状是 env 只在**无覆盖**时生效（`pick(ov.x, env[k])`），本片沿用，
  不新发明第二套优先级。

## 决策 3 —— env 用一条 JSON，不用 15 个变量

`MP_PUBLISH_ACCOUNT_MIN_INTERVAL_MS_JSON='{"tencent_video":3600000}'`。
理由：15 个 `MP_PUBLISH_*_<PLATFORM>` 会变成"没人记得存在"的开关集；一条 JSON 的代价是**必须自己写校验**：

| 输入 | 行为 |
|---|---|
| 未设/空串 | 整条视为缺席，回落到下一级 |
| JSON 解析失败 | **整条作废** + `warn` 点名 env 名与失败原因，全部平台回落表默认 |
| 不是对象 / 是数组 | 同上 |
| key 不在 `SUPPORTED_PLATFORMS` | 忽略该键 + `warn` 点名（不得静默接受，也不得因此作废整条：拼错一个平台名不该让其他 14 个平台失去配置） |
| value 非有限数 / <0 / >`MAX_INTERVAL_MS` | **整条作废** + `warn`（与设置页覆盖同口径：不做"一半生效"） |

## 决策 4 —— 数值表与"取证/暂定"标注

| platform | accountMinMs 默认 | 相对档位 | 性质与依据 |
|---|---|---|---|
| `tencent_video`（视频号） | **60′** | 由 clip 3′ **收紧** | 暂定值。依据是公开运营口径的"日发上限按粉丝量分级（千粉 1 条／万粉 2 条／万粉以上 ≤5 条）、超出限制直接限流"；**官方从未公布间隔数值**，故 60′ 是产品决策而非平台规则，文档必须这样写 |
| `wechat_mp` | 5′ | 不变（long） | 未取证，保持现值 |
| `zhihu` / `baijiahao` / `toutiao` | 5′ | 不变（long） | 未取证，保持现值 |
| `douyin` | 3′ | 不变（clip） | 未取证。检索到的口径原文即"官方没有『发 3 条就限流』的硬规定，限流核心是质量/违规/同质化" |
| `kuaishou` / `xiaohongshu` / `bilibili` / `youtube` / `tiktok` / `instagram` / `facebook` | 3′ | 不变（clip） | 未取证，保持现值 |
| `weibo` / `twitter` | 1′ | 不变（short） | 未取证，保持现值 |

⇒ **行为变化面只有视频号一个平台**（3′→60′）。其余 14 个平台的生效值逐字节不变，
由"表默认 == 档位代表值"的可执行断言守住（防止"顺手调数值"混进本片）。

## 决策 5 —— 守卫侧不改判定算法，只改取值来源

`publish-interval-guard.js` 的 `check()`（:285-326）继续按
`max(账号档剩余, 平台档剩余)` 取更严者 + 抖动叠加；本片的改动全部发生在它注入的
`policy(platform)` 返回值里。**不动 guard 的原因**：它已被 D1/回滚/紧急放行三套锁钉住，
任何改动都要重跑那三套；把差异留在策略层，回归面最小。

## 决策 6 —— UI：15 个 `el-input-number`，不引入新组件类型

设置页新增「按平台覆盖同账号间隔（分钟）」折叠区，逐平台一行 `label + el-input-number`，
留空 = 不覆盖（`null`）。**不用 `el-table`**：按需引入下 `el-table` 的样式闭包
（`table`→`checkbox`/`popper`/…）会牵动 `src/plugins/element-plus.js` 登记与
`main.bundle-contract.test.js`/像素回归，为一组数字输入框付这个代价不值。
展示区把现在的"按档位分组文案"（`currentTierText`）改成"逐平台生效值 + 被覆盖标记"，
数字全部来自 `getPolicy` 下发，**渲染层不写任何数字字面量**（既有结构锁继续生效）。

## 数据校验表（本片新增部分）

| 入口 | 字段 | 合法域 | 非法时 |
|---|---|---|---|
| 设置页 | `accountMinMsByPlatform` | 对象，key ∈ 15 平台，值 `[0, MAX_INTERVAL_MS]` 整数毫秒（UI 侧填分钟、提交前 ×60000 取整） | **整个覆盖对象作废**（沿用"全有或全无"），IPC 返回 `VALIDATION_ERROR`，界面显示"已整体拒绝（未保存任何字段）"，不落库 |
| 设置页 | 未知平台 key | 忽略该键（前向兼容），但 `warn` 记计数 | 不作废整体（拼错平台名不该抹掉其他配置） |
| env | `MP_PUBLISH_ACCOUNT_MIN_INTERVAL_MS_JSON` | 见决策 3 | 整条作废 + 出声，回落表 |
| IPC | `getPolicy` 下发缺字段 | 渲染层取 `undefined` ⇒ 输入框不设上界 | 权威界仍由主进程在保存时拒绝 |

## 交互与提示文字（locale 成对）

| 场景 | 文案（zh） | 说明 |
|---|---|---|
| 区块标题 | 「按平台覆盖同账号发布间隔」 | 新增 |
| 区块说明 | 「留空表示该平台使用默认间隔；填写后优先于上方「账号最小间隔」全局值。」 | 关键：把优先级链讲成人话，否则用户会以为全局值更大 |
| 视频号一行提示 | 「视频号对连发更敏感，默认已收紧为 1 小时」 | 数值来自下发，不写进代码；文案里出现"1 小时"是**展示层文字**，需在测试里锁"数字来自 props 而非硬编码" |
| 保存失败 | 复用既有 `已整体拒绝（未保存任何字段）` | 不新增第二套失败文案 |

## 兼容与回退

- 老 `publishFrequencyPolicy` 存储值不含新键 ⇒ `resolvePolicyOverrides` 原样忽略，行为等价于今天（零迁移）。
- 回退路径：把表里视频号改回 `3 * MIN` 即恢复 v4 行为；`git revert` 本 PR 同样安全（无持久化格式变更）。
- 运营临时放宽：env 设 `MP_PUBLISH_ACCOUNT_MIN_INTERVAL_MS_JSON={"tencent_video":180000}` 即可，不必改代码。

## 风险（不藏着）

1. **视频号 60′ 会显著拉长批量发布**：350 条/天配额 ÷ 60′ 间隔 ⇒ 单账号一天理论上限 24 条，
   与运营口径的"日发 1–5 条"仍差一个数量级。**真正卡住它的是日配额而不是间隔**，
   已登记为未闭合项（PRD v5 §9），留给用户拍板取值。
2. **定时发布表单仍是 5′ 输入期校验**（`publish-schedule-contract.js:21`）：用户可对视频号排 5′ 间隔的
   两条定时任务，表单放行、发布时由守卫排队推迟。属"能提交但会等"，不是数据错误；本片不改它，
   在 PRD v5 §9 与 ARCH §9 活例外里点名。
3. **间隔收紧 = 风控面变小但吞吐变低**：若用户体感"变慢"，回退成本是一行数据；不引入新持久化格式。
