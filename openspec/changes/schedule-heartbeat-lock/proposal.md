# Proposal: 定时作业的「心跳」锁——根本没有 run 的那种失败（schedule-heartbeat-lock）

> 本 change 是 `schedule-failure-watch`（PR #4234，主干 `6f9467cef`）**明确记为遗留第 1 条**的那一刀：
> 上一刀把"有 run 且失败"接进了报警，但 `workflow_run` 只在**有 run 完成时**才触发，所以
> "某条定时作业一次都没跑"这一整类失败仍然无人出声。落点与预算由用户 2026-10-23 授权 agent 自定。

## Why

上一刀的现场是：`Cleanup Artifacts` 的定时 run 连红 9 次没人知道（run `38385152658`…`39570873661`）。
修完之后，"红"这一类有锁了（`Gate 2b13` 对账覆盖面），但**"不跑"这一类没有**，而它的成因更常见：

- cron 表达式写错（时区/星期位）⇒ GitHub 根本不会排它，**一次 run 都不会产生**；
- 作业被禁用或从 `main` 删掉文件名而 workflow 定义仍在 ⇒ 没有 run；
- runner 长期排队/配额耗尽 ⇒ run 停在 `queued`/`in_progress`，**永远不"完成"**，`workflow_run` 也就永远不触发；
- 仓库改私有/迁移 ⇒ 老 run 列表与 cron 声明同时错位。

这四类的共同形状是：**Actions 页面上一片空白，而所有"看失败"的机制都在等一个不会来的事件**。
本仓对这类"没跑的文件在摘要里与跑了且绿完全同形"的坑已经定性过（`collected != candidates` 那条巡检事故），
所以这次的判据从一开始就把"取不到数"与"取到且新鲜"分成不同档。

## 现状取证（2026-10-23 现跑，重取命令见 design §4）

4 条带 `on.schedule:` 的作业，实测节奏**很稳**——这是阈值能收紧的依据：

| 作业 | cron | 周期估算 | completed schedule 样本 | 最大相邻间隔 / 周期 | 实际落点相对 cron 的漂移 |
| --- | --- | --- | --- | --- | --- |
| `Cleanup Artifacts` | `23 3 * * *` | daily/86400s | 20 | 1.04× | +5.68h |
| `时钟位移引信巡检` | `0 18 * * 3` | weekly/604800s | 2 | 1.00× | +3.15h |
| `依赖漏洞审计门禁` | `0 3 * * 1` | weekly/604800s | 4 | 1.00× | +5.13h |
| `Sidecar Parity (cross-repo)` | `10 22 * * *` | daily/86400s | 4 | 1.00× | +2.45h（跨过午夜，裸差值 -21.38h 不是漂移） |

三条结论直接影响设计：**① 间隔从不超过周期的 1.04 倍** ⇒ "漏一次"就能被判异常，不必等两次；
**② 但 run 的起跑时刻相对 cron 可漂到 ~5.7 小时**（GitHub 调度排队） ⇒ 纯 `period` 做阈值必然假红；
**③ 每周作业只有 2–4 个样本** ⇒ 任何按"最近 N 次"取样的算法在样本不足时必须出声，不能默认放行。

## 打算做什么（Details）

1. **周期由 cron 自己推**，不新建第二份手抄清单（上一刀的教训）：`dom/dow/mon` 三个位决定 daily/weekly/monthly；
   推不出来的（非 `*` 的 mon、列表/步进表达式当 dom 等）一律 `SCANNER_FAULT`，**不许猜成 daily**。
2. 阈值 = **周期 + 可覆盖的宽限（默认 8h）**，不是"周期 ×2"。依据就是上表②：漂移实测 5.68h，8h 覆盖它且留 2.3h 余量；
   代价是"漏一次"当天就能响，而 ×2 会让日报纸漏一天要到第三天、周报漏一周要到第 15 天。
3. **三档失明各自可区分**：无 completed schedule run（从没跑过）/ 采集失败（API 非 2xx、JSON 解析不动）/
   样本数低于下界 —— 全部非零退出并点名作业，绝不退化成"没有数据 ⇒ 通过"。
4. 心跳作业**自己带 `on.schedule:`** ⇒ 它必须进 `ci-failure-handler.yml` 的名单，而这条要求由上一刀的
   `Gate 2b13` 机械逼出来：**两把锁互相咬住**，心跳锁烂掉（改名、删名单项、cron 推不出周期）会在任何 PR 上显形。
5. 判据本体是**纯函数 + 注入式采集**：`judge({now, workflows, runsOf})`，测试不碰网络
   （本仓 `network-egress-guard` 会拦真实出站），`now` 由调用方给 ⇒ "多久没跑"这类判据必须能在假时钟下测。

## 不在范围（写明以免被"顺手"扩进来）

- 不做 `queued`/`in_progress` 超时的独立判据（第 3 类成因只覆盖到"永远不完成 ⇒ 没有 completed run"，
  更细的"排队卡了 10 小时"要另一把读 `status` 的锁，且需要新的实测分布）。
- 不改 `Gate 2b13` 的不变量（只扩展它消费的 loader，输出 cron 位；那条锁的 13 条用例必须照旧全绿）。
- 不引入 cron 解析依赖（`changes` 作业无 Install deps 是既定约束，本判据也只用 node 内置）。
- 不把心跳结果写进台账/`CHANGELOG.md`（热写面禁改，见 `Gate 2b9`）。
