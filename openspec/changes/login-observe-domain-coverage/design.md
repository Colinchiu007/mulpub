# 设计：补正头条号登录期观测的覆盖面

## D1. 第一性原因

上一刀把头条号登录链路的资源域登记成了 **10 条**，来源是当时观测到的请求。
2026-10-22 换了个更靠前的取数口——**直接抓 `https://mp.toutiao.com/` 的登录页 HTML**，
从 `<script src>` 里列出页面**静态引用**的全部资源域——发现清单里缺了两条，
且缺的那两条恰好承载**最关键**的那个组件。

这不是「当时没看仔细」能解释的：上一刀的取数口是**运行时的请求流**，
而验证码组件是**点「发送验证码」之后才按需加载**的——它不在登录页首屏的资源清单里，
所以首屏观测抓不到它，只有静态引用清单能抓到。

两个取数口互补，缺一不可：

| 取数口 | 能看到 | 看不到 |
| --- | --- | --- |
| 运行时的请求流（上一刀） | 首屏加载的所有域 | 登录页 HTML 里静态引用、但**尚未被请求**的域 |
| 登录页 HTML 的静态引用（本刀） | 页面引用的一切域（含尚未请求的） | 纯运行时动态拼接、无静态引用的域 |

⇒ **本刀补的是「静态引用」这一口**，它正好覆盖上一刀的结构性盲区。

## D2. 逃逸分析：为什么两处漏都没被现有测试抓住

| 漏点 | 逃逸原因 |
| --- | --- |
| 域不在监测域清单 | 上一刀的域清单是**数据**（数组），没有「清单必须覆盖登录页静态引用域」这类**可表达的**判据；测试只能验「登记的域被匹配」，验不了「没登记的域」。这与「测试全在微信语义下」是同型问题：断言的对象是实现，不是需求 |
| 路径形态不匹配锚点 | 锚点常量是**字面量数组**，同样没有「必须覆盖真实链路上出现过的形态」这个判据；反例锁只锁了「查询串/域名里出现标记不算」，没锁「真实形态必须命中」 |

⇒ 本刀的测试必须**从真实链路取样**（把登录页实际引用的 URL 写进用例），
而不是再写一条「某个我编的 URL 应该命中」。

## D3. 判据设计

### D3.1 监测域补两条

| 域 | 承载什么 | 实证 |
| --- | --- | --- |
| `yhgfb-cn-static.com` | 验证码中心：真实生效的验证码入口 | 登录页 HTML 静态引用 `lf-rc1`/`lf-rc2` 两个冗余节点 |
| `bytetos.com` | 风控 glue | 登录页 HTML 静态引用 `lf-c-flwb.bytetos.com/…/sdk-glue.js` |

补后这两域的失败请求 / HTTP≥400 / 慢请求才会进日志。

### D3.2 验证码组件判定：组合锚点

```js
const CAPTCHA_SDK_DIR_MARKER = '/sec_sdk_build/'
const CAPTCHA_SDK_SEGMENT   = '/captcha/'
// 命中 = 老锚点任一命中  OR  (含 DIR_MARKER 且含 SEGMENT)
```

**为什么必须是两段一起判**（这三条是本刀的核心取舍，不能简化）：

| 判法 | 后果 |
| --- | --- |
| 只认 `/captcha/` | 任何路径带 captcha 字样的无关资源都命中 ⇒ 噪声淹没真信号（用户看到一堆「验证码组件加载完成」，却分不清哪个是真的） |
| 只认 `/sec_sdk_build/` | 该版本目录下的非验证码资源也命中 ⇒ 「灰显遮罩结束的时刻」这个读数**提前**且失真 |
| **两段同时** | 判据仍窄；`/sec_sdk_build/` 是字节验证码中心的版本目录，专属性足够 |

### D3.3 不变的部分（一字不动）

- 老锚点 `/secsdk-captcha/`、`/webmssdk/` 及其「只认路径、不认查询串/域名」约束。
- 未登记平台走默认（微信域）过滤面，既有契约锁逐字相等。
- 观测层永不读响应体；日志 URL 去 query/fragment。
- 槽位复用逻辑（缓存跨次留存、导航前清凭证、按轮次判凭证）本刀不碰。

## D4. 为什么不把 `sdk-glue.js` 算成验证码组件

`captcha-sdk-loaded` 这个事件的语义是「**用户看到的灰显遮罩结束**的时刻」。
风控 glue 加载完 ≠ 验证码就绪；把它算进去会让这个时刻**提前** ⇒ 读数失真。
它在监测域内 ⇒ 它的慢请求/失败**照常被记**，只是不占「验证码组件」这个事件名。
（这条是「显式不做什么」，不是遗漏。）

## D5. 验证口径

| 项 | 口径 |
| --- | --- |
| 红灯 | 先写用例并跑出失败：新增 3 条用例在实现前 **2 failed / 63 passed**（修正一条弱负例后） |
| 绿灯 | 本刀相关 9 个测试文件 **273 passed / 0 failed** |
| 变异反证 | M1~M6 逐条改坏实现，断言对应用例必须变红，跑后源文件 md5 与跑前逐一相等 |
| 外部评审 | CCG 双家族（critic=claude / proposer=opencode） |
| 行数门禁 | `node .github/scripts/check-max-lines.js` 不得引入新增超大文件 |

## D6. 现场读数（写进文档，作为「为什么这条必须观测」的证据）

| 观测点 | 读数 | 归属 |
| --- | --- | --- |
| 字节自家埋点脚本 | 504，首包 16.68s；**外部网络同样 504** | 字节侧，通用 |
| 登录页整体（应用日志两次） | 48.9s / 56.3s | — |
| 同一台机器、同一网络、**无关浏览器**独立 profile 冷加载 | 23.8s | 应用比浏览器慢一倍以上 ⇒ 差值是本仓造成的（上一刀已修） |
| 登录页本体 `mp.toutiao.com` | 首包 0.149s | 页面本体不慢 |
| 真实验证码入口（77,476 B） | 冷 2.65~2.96s / 命中边缘 0.13s | 高度间歇 ⇒ 「灰显几秒」的来源 |
| 同链路其它资源 | 190KB→1.35s、100KB→0.60s、520KB→2.16s | 耗时与体积不成比例 ⇒ 瓶颈在连接建立/转发路径，不在带宽 |

## D7. 边界（不假装闭合）

- 本刀**不修**字节侧那个 504，也不改用户本机的代理线路。
- 本刀**只保证**「该被看见的都被看见」；看到之后**能不能修**是另一件事。
- 登录页 HTML 的静态引用清单会随平台改版变化；本刀登记的是 **2026-10-22 现场实测**的形态，
  不是「永久正确」的清单。后续平台改版若换形态，仍需按本刀同法补测。
