# tasks.md 读数更正

## 1. 问题

`openspec/changes/wechat-native-payment/tasks.md` 的校准表写着：

> 结果 | 完成 **35** 项 / 未完成 **2** 项（`0.3`、`8.8`）

但实际 `grep` 出来是 **49 项已勾选 / 3 项未勾选**（`0.3`、`6.6`、`8.8`）。

两个错叠加：

| 错 | 来由 |
|---|---|
| 35 → 49 | #4247 校准后我又勾了 `9.8`（4 个子项）等条目，**表格没跟着更新** |
| 2 → 3 | `6.6` 是**故意不勾**的（主动改方案），当时按"待办"口径统计就漏算了它在文件里的存在 |

## 2. 为什么这条值得单独修

`tasks.md` 是**交付进度的单一真源**。读它的人（包括下一轮的我）会拿这个数字判断"还剩多少活"。

- 数字偏小 ⇒ 误以为接近完成
- 把 `6.6` 算成待办 ⇒ 误以为还有一件没做，实际它是有意为之并写明了理由

两种都直接导致错误决策。而且这类"记录漂移"**不会让任何测试变红** —— 只有人去 grep 才会发现。

## 3. 改法

| 改动 | 内容 |
|---|---|
| 结果行 | 35 / 2 → **49 / 3**，并写明复现方式：`grep '^- \[x\] NN.N'` 实测 |
| 待办行 | 明确「只剩 `0.3` / `8.8`」，并说明 `6.6` 仍 `[ ]` 但是**主动改方案**、**不是待办** |
| 相关 PR 行 | 补齐 #4249 / #4252 / #4256 / #4267 / #4269 / #4274 / #4286 |
| 新增更正说明 | 写清原数字是 #4247 当时的读数、此后漂移，并立一条规矩：**记录的读数必须能被 grep 复现** |

## 4. 一条通用教训

凡"我在某个时点数了一遍"写进文档的数字，只要被数的东西还会变，这个数字就**必然过期**。

两个可选做法：

| 做法 | 评价 |
|---|---|
| 每改一次勾选就同步改汇总 | 依赖人记得，实测会漂（本次就是） |
| **写清复现命令，让读者自己数** | 抗漂移；数字只作"当时读数"的注记 |

本次两者都做：给当前实测值 + 给 `grep` 命令。
