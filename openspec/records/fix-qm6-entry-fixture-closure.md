## learnings

### lesson: fixture-closure-drift-blames-every-unrelated-pr

**现场**：`scripts/deep-review-entry-rc.test.js` 的临时仓靠一份手工清单 `SCRIPT_CLOSURE`
从真仓抄脚本。#4093 给 `check-pr-exec-record.js` 加了 `require('./lib/exec-record-statuses')`
并新增了那个模块，却没把模块抄进清单 ⇒ 临时仓缺模块 ⇒ 6 条用例同形失败 ⇒
Gate 2b11 在 changes 作业里对**每一个** PR 转红。而本机直接跑这批测试是**全绿**的 ——
因为真仓里那个模块确实存在，只有夹具把它排除掉。

**根因**：缺陷不在被测代码里，在**夹具的复制清单**里。两点让它格外难查：
① 夹具与真仓不一致 ⇒ 本机复现不出来（能复现的失败一般当天就被发现）；
② 门禁对每个 PR 都跑 ⇒ 断链的红被记在**无辜 PR**的账上，第一反应自然是「这个 PR 弄坏的」。

**可复用的 N 条**：

1. 门禁红了先做**对照**：换成 `origin/main` 跑同一道门禁，同样红 ⇒ 是 main 级存量债，
   与本 PR 无关；这一步能省掉「改自己的代码 → 白改」和「硬扛 → 背锅」两种误判。
2. **本机绿 ≠ CI 绿**。这两者的差集只可能来自「环境差异」或「夹具与真仓的差异」，
   而后者专挑「清单型」夹具（手工维护的复制清单 / 硬编码的白名单 / 手工登记的模块表）。
3. 夹具里凡是**手工维护的清单**，都要配一条「清单与实际依赖同源」的机械守卫；
   守卫本身必须做**变异验证**（删一行清单 ⇒ 守卫必须红），否则它可能只是个恒真断言。
4. 守卫报错要能**指名道姓**（谁 require 了哪个模块），而不是只说「闭包不完整」——
   否则守卫只是把「看不懂的红」换成「看不懂的红」。
5. 这类断链**红在无关 PR 上**的性质本身就该被写进记录：它让主干长期处于「人人有罪」的状态，
   而每个人都只看到自己那一条红。
