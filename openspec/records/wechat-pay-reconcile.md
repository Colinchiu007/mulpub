# 支付对账

## 1. 为什么做这个

支付链路有四张表各记一半事实：

| 表 | 记什么 |
|---|---|
| `identity_orders` | 订单（pending → paid） |
| `identity_webhook_events` | 回调到达与处理（2026-10-23 起） |
| `identity_subscriptions` | 权益发放（`provider_reference = 'wechat:<orderId>'`） |
| 微信商户平台 | 钱实际到没到 |

任何一环错位，用户看到的现象都一样：**「我付了钱但没会员」**。

日志只能回答「这个请求返回了什么」，**回答不了「有多少单处在不一致状态」**。
灰度期每天要看的不是日志，是这个数。

## 2. 五项判据

| # | 判据 | 等级 | 含义 |
|---|---|---|---|
| 1 | `paid-without-entitlement` | **阻塞** | 已支付但没发权益 —— 用户已损失 |
| 2 | `entitlement-without-paid-order` | **阻塞** | 发了权益但订单非已支付（反向孤儿） |
| 3 | `event-processed-order-pending` | **阻塞** | 回调已处理但订单非 paid —— 事务边界被改坏的信号 |
| 4 | `paid-order-without-event` | 提示 | 历史单必然如此（事件表 2026-10-23 才上线）；新单出现才是问题 |
| 5 | `stuck-processing` | 提示 | 事件卡 `processing` >10 分钟，权益已发，仅留痕没闭环 |

**只有阻塞项让退出码变 1**。否则历史单会把对账永久钉红 —— 一个永远红的判据等于没有判据。

退出码：`0` 无阻塞 / `1` 有阻塞 / `2` 用法错误或连不上库。
`2` 不得读成「对账通过」：工具失明与「没有问题」是两件事。

## 3. ⛔ 只读硬约束

脚本**只允许 SELECT**，并有一条**结构性测试**锁住：五条判据都必须以 `SELECT` 开头，
且不含 `INSERT / UPDATE / DELETE / ALTER / DROP / TRUNCATE / CREATE`；另有一条运行时断言，
确认实际发出的每条语句都以 SELECT 开头。

理由：对账工具一旦能写库，就会有人用它「顺手修一下」，而**自动修复资金不一致是资金路径上最危险的动作** ——
改错了没人知道。修正一律人工核对 + 单独脚本 + 评审。

## 4. 设计上的三个克制

| 决定 | 理由 |
|---|---|
| 不自动修复 | 见上。差异只报告 + 给「第一动作」提示 |
| 提示项不阻塞 | 历史单没有事件行是**正常**的；把正常状态判红会让真问题被噪声淹没 |
| 每条差异都带 `hint` | 只报数字的对账表，值班的人拿到也不知道下一步做什么。测试里专门断言 `hint.length > 20` |

### 覆盖到的边界

- 每条判据只绑两个参数（`Date` + `LIMIT`）—— 断言参数是 `Date` 实例，防止把字符串拼进 SQL
- `sample` 最多 5 条但 `count` 是真实条数
- `--since-days 0` / `--limit abc` / 未知参数 → rc=2
- 没有 `BUSINESS_DATABASE_URL` → rc=2（不静默当成通过）
- `client.end()` 一定被调用（不泄漏连接）

## 5.5 外部评审（2 Critical + 3 High）——全部落地

| # | 意见 | 核验 | 处置 |
|---|---|---|---|
| 1 | LIMIT 截断把真实条数报小 | **部分成立**：它说会报"干净"是错的（截断时 `count>0` ⇒ `ok=false`）；但"200 条"确实骗人 | 加 `truncated` / `truncatedBlocking`，输出明确写「被 LIMIT=N 截断，真实条数更多」 |
| 2 | `substring(from 8)` 无长度守卫 | 成立 | `AND length(s.provider_reference) > 7` |
| 3 | INNER JOIN 丢掉孤儿事件 | 成立 | 改 `LEFT JOIN` + `(o.id IS NULL OR o.status <> 'paid')` |
| 4 | 默认窗口藏历史差异且输出看不出 | 成立 | 报告加 `inspectionWindow`，首行打印 |
| 5 | 连错库/空库 ⇒ 全 0 行 ⇒ 报"一致" | **成立且最危险** | 加 schema 预检 `to_regclass()`，缺表即 `PAYMENT_RECONCILE_SCHEMA_MISSING`（rc=2） |
| 6 | 只读锁不拦 `FOR UPDATE` / `INTO` | 成立 | 结构锁补两条 |
| 7 | 测试可能被掏空仍通过 | 部分成立 | 补「每条判据 SQL 都真的被执行」逐条比对 |
| 9 | `auth_subject` 语义未写明 | 成立 | SQL 注释写明是订单号 |

### 自查又抓到一条（评审没提）

加 schema 预检时我先写成 `schema.rows[0] || {}` —— **查询返回零行时会被当成"什么都不缺"**，
正是这个预检要防的失明形态。我自己的测试「CLI 层：缺表 ⇒ rc=2」当场变红才暴露出来。
改为：零行也算失败。

这条值得记：**防失明的检查本身也会失明**，而且它的失明与"一切正常"长得一模一样。
