### ① 根因溯源

不是 runner 突然变慢，是**套件的健康长尾长到了墙底下**。

| | 2026-09-28 定 2100s 时 | 2026-10-20 重测 |
|---|---|---|
| 健康耗时基线 | 794s（**单样本**） | 长尾 **2094s**（23 样本窗口） |
| 步骤预算 | 2100s | 2100s（没动过） |
| 余量 | 794 对 1200 旧墙 ≈ 33% | **2094 对 2100 ≈ 6 秒** |

重测口径：取最近 **23 次成功运行**（electron-ci on main、`branch=main event=push`、2026-10-19~10-20）
的单测步骤耗时 —— 最小 1282s / 中位 1692s / 均值 1639s / **长尾 2094s**。

**最慢的那次成功已经是 2094s，墙是 2100s。** 所以稍微一抖就翻过去，超时从「偶尔」变成「常态」。

### ② 逃逸分析（这个误判是怎么逃过所有层的）

| 层 | 为什么没拦住 |
|---|---|
| 我的第一版判断 | 我把**工作流 YAML 的源码回显**当成了执行输出。脚本原文里就写着 `echo "TIMEOUT_BUDGET_EXCEEDED…"`，被 Actions 打进日志，我 grep 到就以为它执行过，于是得出「最近 7 次全是超时、FAIL=0、一次真问题没抓到」的**错误结论**，并据此建议「删掉这一步」 |
| CI 自身 | 自证块自 #2525 起从未执行（本轮前一节 PR #4061 已修），所以失败时没有任何可归因读数，只能靠下 7MB 日志反推 |
| 结构性锁 | 锁里钉的 `measuredStepElapsedSeconds = 794` 是**陈旧实测**，而它只校验「预算 ≥ 实测 ×2」——2100 ≥ 1588 恒真，于是套件长 81% 这件事**锁一点反应都没有** |

**教训**：「锁是绿的」不等于「锁还有效」。当锁的比较对象是一个**写死的旧数字**时，它会在被测量对象变化后静默失效 —— 与本仓已记录的「判据域错位」同型。

### ③ 系统性漏洞定位

**实测基线没有复测机制。** 预算挂实测这个方向是对的，但「实测」被固化成一个常量，没有：
- 样本量要求（1 个样本就等于把偶然当分布）
- 复测入口 / 时间戳
- 「基线是否过期」的判据

所以系统性修法 = **把基线从常量改成带出处与样本量的分布读数**，并让它随窗口更新。

### ④ 修复 + 回归保护

| 改动 | 内容 |
|---|---|
| `.github/workflows/electron-ci.yml` | `BUDGET_SECONDS` 2100 → **4200**；job `timeout-minutes` 70 → **95**；注释账本换成新实测（23 样本、长尾 2094、并写明为何是退守） |
| `apps/desktop/tests/gui-ci-exit-contract.test.js` | `measuredStepElapsedSeconds` 794 → **2094**（长尾），补样本量与出处；两处记录值（70→95、2100→4200）同步 |
| `docs/electron-ci-step-budget-baseline.md` | 更正「档 2 落地」的误导标题；追加「重挂账本」小节（分布表 + 新旧对照 + 为何是退守） |

回归保护（两条锁，均已验证会咬）：
- **预算挂实测**：`budget ≥ 长尾 × 2` → 4200 ≥ 4188 ✓
- **不与 job 级倒挂**：`job.timeout > 其余步骤上限之和(20) + budget/60(70)` → 95 > 90 ✓

**变异反证（两次，均成立）**：
1. 预算退回 2100 → 「预算挂实测、超时可自证、且不与 job 级倒挂」等 **2 条锁红**
2. job timeout 退回 70、预算保持 4200 → 倒挂锁等 **2 条锁红**

### ⑤ 预防措施

- 锁里的实测常量现在写成**带出处与样本量的窗口读数**，并在注释里写明「预算要挡的是分布右端，均值会把长尾那一半判成超时」—— 下一次重测时数字会变，出处与口径不变。
- 基线文档新增「重挂账本」小节，把**分布表**留档，下次不必重新跑 23 次 API。
- 明确登记这是**退守**：根因（按 `--shard` 切开）被两件事挡住（matrix 后缀名与 ruleset required context 冲突；结构性锁按 job 名断言单测位置），不属于本 PR 范围。

### 遗留（不假装已闭合）

1. **根因未修**：分片仍是正确方向，但需要改 job 身份 + 两条结构性锁，属「谁来守门」邻域，需人工过目后单独做。
2. **套件还会继续长**：本轮把余量从 1.00× 拉回 2.01×，下一次套件再长 40% 就会重新贴脸。**必须定期重测**（本轮已把复测口径写进锁注释与基线文档）。
3. **抬墙的代价**：单次 main push 的 Electron CI 最长会占 70 分钟 runner 时间（现在撞墙也是耗满 35 分钟后判失败，等于白烧；抬墙后中位数仍约 28 分钟）。
4. **`docs-only` 判定**：本次改了 `.github/workflows/`，属混合 PR，未被 docs-only 通道短路。

## 附：本轮撞到的第四、第五处机械锁（都是好事）

抬一个 timeout 数字，被本仓 **5 处**机械判据拦到，逐处同步后才绿：

| # | 位置 | 拦住的形式 |
|---|---|---|
| 1 | `apps/desktop/tests/gui-ci-exit-contract.test.js` | `budget ≥ 实测 ×2` |
| 2 | 同上 | `job.timeout > 步级上限之和 + budget/60`（倒挂） |
| 3 | 同上（两处记录值） | `toBe(70)` / `toContain('BUDGET_SECONDS=2100')` |
| 4 | `scripts/check-coverage-budget.test.js` | 扫描器读对作业级天花板（70 → 95） |
| 5 | **`scripts/gate-timeout-registry.json`** | **`PROVENANCE_VALUE_DRIFT`：注册表值 ≠ workflow 实际值** |

第 5 处最值得记：本仓有个「全仓 CI 作业超时治理注册表」（24 格，数值与代码分离，配 PRD
`01-docs/PRD-GATE-TIMEOUT-GOVERNANCE-2026-10-20.md`）。**改 workflow 而不改注册表会当场红** ——
这正是「表与 runner 不同源时，判据变成自证」要防的形状。

本轮对该格的更新：

| 字段 | 旧 | 新 |
|---|---|---|
| `timeoutMinutes` | 70 | **95** |
| `state` | `seeded` | **`measured`**（样本 30 ≥ 20，攒够了就该升级） |
| `provenance.samples` | 15 | **30** |
| `provenance.maxMinutes` | 30.1 | **37.4** |
| `provenance.p90Minutes` | 3.4 | **36.6** |
| `provenance.collectedAt` | 2026-10-18 | **2026-10-20** |

（p90 从 3.4 跳到 36.6，是因为旧值明显只采到了「快」的那一批；新采的 30 个成功样本 job 级
分布：最小 23.4 / 均值 30.1 / p90 36.6 / max 37.4 分钟。）

### 一个必须单独记的治理面盲区（本轮不修，但要留证）

**注册表治理的是「作业级天花板」，而真正杀人的墙是步骤级预算**（`BUDGET_SECONDS`）。
本轮把步骤预算从 35m 抬到 70m，在注册表里只体现为「登记值 70 → 95」，盲区依旧。

更糟的一层：采样器 `scripts/coverage-budget-sample.js` 目前 **fail-closed 在「有 9 趟已跑完
却取不到时长」上**。查代码可见判定是 `started_at && completed_at`，而**被 `timeout` 杀掉的趟
读不出时长** —— 于是那 45 次撞墙（右截尾证据）在采集侧根本统计不到，
`censoredAtCeiling` 恒为 0。

也就是说：**治理面不仅管不到步骤级预算，连「有多少趟是被杀的」都看不见。**
这解释了为什么「45 次撞墙、占 61%」这件事在注册表上完全不可见。

修它属于独立任务（要动采集器与它自己的锁），本轮不碰，只在此留证。
