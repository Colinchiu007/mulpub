## 2. 为什么是这两处、且只改这两处

### 2.1 CHANGELOG 缺条目（我的漏项）

`#4344`（长篇化方案）入库后，`CHANGELOG.md` 里**没有**它的条目
（`grep "film-auto-longform\|长篇化" CHANGELOG.md` 零命中）。
原因是我把条目草稿写进了**执行记录**的「## CHANGELOG 条目」小节，
**没有同步落到台账文件本身** ⇒ 台账缺一条真实发生过的合并。

⇒ 本次从该小节取回条目，按台账既有格式（`# 类型(域): 标题（slug）` + 若干 bullet）补在**顶部**。

⚠️ **台账型文档的插入纪律**（照旧）：**从 base 逐字节重建 + 只加自己那一条**，
用**标题锚点**定位，不按行号 ⇒ 别人的条目一个都不动。

⚠️ `changelog-growth`（不许丢）与 `changelog-dup-ratchet`（不许多）**都不管「你有没有自己的条目」**
⇒ 这一类漏项只能靠 `git diff --stat` 的形状与人工复核发现，门禁不会替你抓。

### 2.2 PRD 头部版本号与正文不符

文档头写「**版本**：v1.0」，而正文实际已经是 **v1.2**
（v1.1 = 第一轮自查后修正 14 处；v1.2 = 独立复核后修正 19 处、含 R3 档 3「部分可控」）。
⇒ 头部那一行是**当前文档版本的唯一标注**，属过时 ⇒ 改为 `v1.2`。

### 2.3 为什么**不动**正文里的另外两处 `v1.1`

文档里还有两处提到 v1.1：

- M0.5 里程碑的产出列：「本文档 v1.1（补 R3 档 1/档 2/档 3 的最终选择）」；
- M0 阶段的产出物行：「`01-docs/PRD-FILM-AUTO-LONGFORM-2026-10-24.md` v1.1（含实测表）」。

这两处说的是**未来里程碑完成后文档会变成哪一版**（M0.5 要用 M0.1/M0.2 的实测结论
**冻结** R3 的档位形态），属**计划性陈述**，不是「本文档当前是第几版」的标注
⇒ 改它们会把「里程碑的产出」讲错 ⇒ **不动**。

⇒ 判据一句话：**只有标注「本文档当前版本」的那一行该改；描述「未来产出物是哪一版」的，不该改。**

### 2.4 后续订正（2026-10-24，#4379 落库之后）

本记录写于 **v1.2 当时**：上面的「头部版本号 v1.0 ⇒ v1.2」是**当时真实发生的动作**，**不修改**。

但本记录落库后，**`#4379`（长篇化 M0′ 落地）**又改了同一份 PRD 的
§3.1（本次落地的边界）与 §5.1（实现口径 / 数据校验表 / 交互逻辑 / 显示项 / 提示文字）
⇒ 头部版本号**随之升到 v1.3**。

⇒ **读法**：本记录里凡出现「v1.2」，指的是**本 PR 落库当时**的版本；
**当前版本以文件头为准（v1.3）**。
同理，§2.2 那句「正文实际已经是 v1.2」在**当时**成立，按当前状态应读作 v1.3。

⚠️ 为什么用「追加后续订正」而不是直接改那两行：
执行记录是**审计载体**，要如实保留**当时发生的动作**；
若把 v1.2 直接改成 v1.3，读者会误以为「本 PR 当时就把版本号定成了 v1.3」⇒ 反而失真。
