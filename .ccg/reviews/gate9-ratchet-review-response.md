## #1 (high) 降级前提只靠 `summary.total` —— **内核采纳，修法拒绝**

**采纳的内核**：判据不该架在一条跨文件派生约定上。已改为读 `coverage.details`（审计器逐条写出的直接物证）：

```js
const details = report.coverage && report.coverage.details;
return Array.isArray(details) && details.length > 0;
```

新增**两格 A/B 行为锁**（「降级前提读 details 这份直接物证」）：details 有项而派生计数谎报 0 ⇒ 仍降级；details 为空而派生计数谎报 218 ⇒ 仍阻塞。
反证 **M11**（把前提退回 `summary.total > 0`）实测指名变红那条用例。

**拒绝它给的修法，L1 反例**：它要求「还必须有 missing/partial 类条目才允许降级」，即 `countBy('missing') > 0`。
而本片要放行的那份**真实产物**（#3617，run 38646664947 / job 116135306680）现场是
`missing=0 / partial=130 / covered=88 / decision=FAIL / coverageRate=0.36`——`missing` 恰恰是 0。
按该修法，本片一条也放不了，#3617 继续被拦，PR 的目的被反掉。

**顺带纠正它的一处事实定性**：`coverage.summary` 不是裁判自报的那一份。它是
`requirements-runner.js:117` 的 `this.summarize(details)`，由我们按逐条结果算；
裁判自报的是 `coverage._verdict.summary`（同一份产物里是 `{covered:82, partial:145, missing:0}`，
与它自己的 items 直方图 88/130 都对不上）。所以"total 是裁判写的数"这一半前提不成立。
但结论不变——**读直接物证比读派生计数更稳**，这条内核是真的，已落地。

## #2 (medium) NEED_HUMAN 分支不看 `requiredFeatureIds` —— **拒绝（本片范围外），登记遗留**

L2 约束三条：

1. 「NEED_HUMAN 一律按报告型处理」是**本片之前就写死的既有口径**（`agent-review-gate.js` 的 NEED_HUMAN 分支注释：
   需求覆盖审计的 NEED_HUMAN 对任何未覆盖全部 PRD 的 PR 都必然出现，与本次改动质量无关）。本片没有动它，
   也没有在 PR 描述里声称动了。
2. 按它的建议改成阻塞，等于**把「裁判这一轮没定论」当成正向的失败证据**——与本仓反复落地的
   「没拿到证据不是反证」（登录态三态、`AUDIT_NO_VERDICT` 只命名不阻塞的那条）直接冲突。
3. 更关键：它会把**非确定性重新引回 required check**，而且只引给"声明了 feat_ 的 PR"这一子集，
   正是本片要消灭的形态（同一棵树两次跑可以 NEED_HUMAN / FAIL 来回）。真要收紧这一格，
   前提与 #907 一样是「裁判输出稳定」被实测证明，那是独立的判据决策，按规矩得停下来交人，不在判据 PR 里顺手做。

已作为**遗留第 6 条**写进记录与 PR 正文，点名到分支与行为。

## #3 (low) 注解分项与总数无一致性约束 —— **采纳**

加了第四个桶 `other`，并在用例里同时断言「分项之和 == judged」：

```
judge picked 10: covered 2 / partial 3 / missing 1 / other 4
```

反证 **M12**（`other: 0`，即把未知 type 静默丢掉）实测让该用例指名变红。
它另一半建议「直接去掉 inScope」未采纳：`auditedCount` 缺省时打 `N/A` 是**如实表达生产方没给这个字段**，
比整句去掉少一个信息维度更利于排障；这里不做静默省略。

## #4 (medium) 作用域只认两个前端前缀 —— **拒绝其修法，采纳其可见性要求**

L2：`apps/desktop/` + `ops-center/` 这张作用域表不是本片写的，是 **2026-10-12 `gate9-scope-fix`** 为修
「#3413 只动 ops-center 却被判 0.31 分拦合并、#3409 连挂 4 次」而建立的，判据本体与事故出处都写在
`scripts/gate9-classify.js` 的文件头注释里。本片只删了「标题/label ⇒ 不跑」这一条豁免，
**既没有扩大也没有收窄这张表**。

按它建议「未知但疑似前端的路径 fail-closed 走 full」，会把 `packages/*/src` 之类的改动送去审
**桌面端全量存量**——那正是那次修复要消灭的作用域错配，会让每个引擎侧 PR 都撞上一条与自己无关的红。

**采纳的部分**：它指出的读者风险是真的——「取消标题豁免」很容易被读成「全仓都被审了」。
已按要求在记录、`.quality-gates.md` 与 PR 正文写明：覆盖面仍由这两个前缀决定，
实测 200 条里 `touch_frontend_src=45`，其余 140 条即使没有标题豁免也仍是 report-only（理由换成「没有覆盖标的」）。
作用域表要不要扩，作为**遗留第 7 条**登记。

## #5 (low) doc-only 判定按路径前缀、不校验内容 —— **拒绝**

L1（针对其修法有效性）：它描述的洞是「把源码塞进 `docs/` 式前缀下就免审」。
按它给的修法（加扩展名/内容指纹）之后，那份改动**仍然免审**——因为分类器接着会走到
「未触及任何前端源码目录 ⇒ report-only」那一格。也就是说这个修法不闭合它自己举的例子，
只是把洞从「文档前缀」挪到「作用域表」。真正的洞是 #4 那张表，已按 #4 处置并登记。
在不闭合洞的前提下往判据里加一层"内容指纹"，属于增加不可测的启发式，本片不加。
