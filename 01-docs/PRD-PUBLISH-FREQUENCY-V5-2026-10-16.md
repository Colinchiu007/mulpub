## 1. 问题与目标

**用户诉求原话（2026-10-16）**：不同自媒体平台对内容限流的严格程度不同，例如视频号要求更严格；
体感是"一定时间内发布超过一定数量后，如果内容间隔时间又很短，就会对内容的流量限流"。
若网上查不到具体量化数值，就暂定一个宽松值，**只有视频号严格一些**。

v4 之前，"同账号最小发布间隔"这一维**由档位派生**：15 个平台被压进 `long / clip / short` 三档，
同档平台只能同时变严或同时变松。于是"只收紧视频号"在工程上只有两条路，两条都不能接受：

| 做法 | 为什么不行 |
|---|---|
| 为视频号新增第四档 `strict` | 档位是**分类器**：`TIER_ENV`（日配额按三档 env）、设置页"按档位分组"文案、"档间单调"锁全部要改语义；下次任何平台要调又得开第五档 |
| `if (platform === 'tencent_video') return 60 * MIN` | 把策略塞进控制流：合法域、env、覆盖、UI 显示各读各的，正是策略模块立项要消灭的"同一个量抄成多份" |

**目标**：把差异化留在**数据面**——一张逐平台默认表。以后任何平台收紧或放宽 = 改这一行数据，
不动分类器、不动控制流、不动守卫算法。

**非目标**（明确不做，见 §9）：不改 `platformMinMs` 与 `accountDailyMax` 的按档语义；不改守卫判定算法；
不改定时发布表单的输入期校验；不引入新的持久化格式。

## 2. 外部限制取证（如实标注"取证"与"暂定"）

检索结论只有一条硬事实：**公开渠道没有任何平台公布过"两次发布必须间隔 N 分钟"的量化规则。**

| 平台 | 检索到的口径 | 性质 | 本篇取值 |
|---|---|---|---|
| 视频号（tencent_video） | 运营口径：日发上限按粉丝量分级——**千粉 1 条 / 万粉 2 条 / 万粉以上 ≤5 条**，"超出限制直接限流"；间隔数值**无官方口径** | 部分取证（上限有、间隔无） | **60 分钟**（暂定，产品决策） |
| 抖音 | 原文即"官方没有『发 3 条就限流』的**硬规定**；新号前 7 天建议 1–3 条、老号 ≤10 条、蓝 V 20 条"，限流核心归因是内容质量／违规／同质化 | 运营建议，非平台规则 | 3 分钟（不变） |
| 百家号 | 检索到的来源已失效（原页 302 到错误页），**未取得**任何量化口径 | 未取证 | 5 分钟（不变） |
| 其余 12 个平台（微信公号／知乎／头条／快手／小红书／B 站／YouTube／TikTok／Instagram／Facebook／微博／X） | 未取到平台官方量化间隔 | 未取证 | 沿用各自档位现行值（5′／3′／1′） |

**因此本篇不自称"符合任何平台官方规定"**（设置页副标题也是这句话，属产品契约不是免责声明）：

- 视频号 60′ 的**依据链条**是"上限有公开口径 + 间隔无公开口径 ⇒ 取一个能让'日发 1–5 条'天然成立的间隔"，
  60 分钟 ⇒ 单账号一天最多 24 条，远高于运营口径的 1–5 条，属于**宽松侧的暂定值**，不是"平台要求 60 分钟"。
- 其余 14 个平台**行为逐字节不变**。这一点由回归锁显式钉住（§6 锁 L1：偏离集合恰好等于 `[tencent_video]`），
  防止后续会话"顺手把抖音也调一下"混进结构变更。

> 把"暂定"写进代码注释与文档，而不是写成"平台规则"，是本篇最重要的一条纪律：
> 一旦写成规则，下一个会话就不敢改它，而它本来就该随运营数据被改。

## 3. 功能逻辑

### 3.1 数值真源与维度归属

| 维度 | v5 真源 | 是否逐平台 | 说明 |
|---|---|---|---|
| `accountMinMs` 同账号最小间隔 | **`PLATFORM_ACCOUNT_MIN_INTERVAL_MS`** | **是** | 本篇新增；15 个键全覆盖 |
| `platformMinMs` 同平台跨账号最小间隔 | `TIER_PRESETS[tier].platformMinMs` | 否（三档统一 1′） | v4 口径不变 |
| `accountDailyMax` 当日提交上限 | `TIER_PRESETS[tier].accountDailyMax` | 否（按档 200/350/500） | v4 口径不变 |

`PLATFORM_FREQUENCY_POLICY`（派生表）在 v5 里把账号档替换为逐平台值，其余两维仍来自档位——
这样"读策略表的人"和"走 `resolveIntervals` 的人"拿到的是同一个账号档，不存在第二份真相。

### 3.2 回落基线

`BASELINE_INTERVALS.accountMinMs` 自 v5 起 **引用逐平台表**（`= PLATFORM_ACCOUNT_MIN_INTERVAL_MS.tencent_video`），
不再另写一个数字。定义仍是"人为想清楚过的最严值"：未登记平台（含 `undefined`／非字符串）拿这一档并置 `fallback: true`。
基线与表写成两个数字，迟早有一天漂移——所以只能引用。

### 3.3 优先级链（五级，细粒度必须赢粗粒度）

```
1. 设置页平台专属   overrides.accountMinMsByPlatform[platform]
2. 设置页全局       overrides.accountMinMs
3. env 平台专属     MP_PUBLISH_ACCOUNT_MIN_INTERVAL_MS_JSON[platform]
4. env 全局         MP_PUBLISH_MIN_INTERVAL_MS
5. 逐平台表默认     PLATFORM_ACCOUNT_MIN_INTERVAL_MS[platform]（未登记平台 ⇒ BASELINE_INTERVALS）
```

- 1 赢 2 是本篇新增的判据：若 2 赢 1，"给视频号单独设 60 分钟"会被一个全局值**静默抹掉**。
- 2 赢 3/4 沿用既有关系（env 只在无覆盖时生效），不新发明第二套优先级。
- 3 赢 4 是同一条 env 内部的"专属赢全局"。
- `0` 在每一级都是**合法值**（显式关闭该档），所以判"是否已设置"一律用 `pick(...)` / `hasOwnProperty`，禁止 `||` 兜底。

### 3.4 流程（一次提交怎么被判定）

```
TaskQueue 出队（通道 = (platform, accountId)）
  → guard.check(platform, accountId)
      → policy(platform) = resolveIntervals(platform, { env, overrides: store 里的覆盖对象 })
          → accountMinMs = resolveAccountMinIntervalMs(platform, {…})   ← v5 新走这一层
      → 账号桶剩余等待 vs 平台桶剩余等待，取更严者
      → ×(1 + jitterRatio)，钳在 TIMER_SAFE_MS 内
      → 日配额判定（按档，未变）
  → 需等待 ⇒ publish:blocked（bucket=account/platform/daily）+ 释放通道；不阻塞其他通道
  → 放行 ⇒ recordPublish(platform, accountId) 打点
```

守卫算法**一行未改**：本篇的全部改动发生在它注入的 `policy(platform)` 返回值里。
原因是守卫已被 D1（竞态输掉不得回滚窗口）、回滚资格矩阵、紧急放行三套锁钉住，
动它要把三套全重跑；把差异留在策略层，回归面最小。

### 3.5 实现落点（拆文件是被门禁点名的正解，不是分层设计）

本 PR 把策略模块推到 678 行，被逐文件行数门禁判 `NEW_OVER_LIMIT`（该文件此前从未挂账 ⇒ 门禁对"新越线"不给豁免通道，
唯一出路是拆分，不是往 `scripts/debt-baseline.json` 里加一条）。拆出去的两块恰好各自内聚：

| 文件 | 装什么 | 谁消费它 |
|---|---|---|
| `publish-frequency-policy.js` | 档位表、回落基线、`resolveIntervals` 等解析入口 | 守卫、IPC、标定脚本（**公开面 33 个导出名一个没动**） |
| `publish-frequency-account-interval.js` | 逐平台表 `PLATFORM_ACCOUNT_MIN_INTERVAL_MS`、env JSON 解析、五级优先级链 `resolveAccountMinIntervalMs`、设置页覆盖校验器 | 策略模块**同名再导出** |
| `publish-frequency-overrides.js` | 设置页覆盖的"全有或全无"校验 `resolvePolicyOverrides` | 策略模块**同名再导出** |

两条硬约束：依赖一律经工厂参数注入，**新模块不 require 策略模块**（否则成环）；策略模块只再导出、不复制实现
（否则就是本片立题要消灭的"同一个量抄成多份"）。拆分后原来的「两个解析函数不得互相调用」行为锁**保留**
——虽然结构上已不可能互调，留着防的是"下一次又把实现搬回去"。反证也跟着搬家：M4 改写成**接线反证**
（摘掉策略模块对解析器的取用 ⇒ 套件当场崩），并新增 M9 打"跨模块校验结果没被写回覆盖对象"这一格断链。

## 4. 数据校验（三个入口，两套严格度）

| 入口 | 字段 | 合法域 | 非法时行为 |
|---|---|---|---|
| 设置页 → IPC `publishFreq:setPolicy` | `accountMinMsByPlatform` | 对象；键 ∈ 15 平台；值 `[0, MAX_INTERVAL_MS]` 的**整数毫秒**（UI 填分钟，提交前 `× 60000` 取整） | **整个覆盖对象作废**（返回 `null`），IPC 回 `VALIDATION_ERROR`，界面显示「已整体拒绝（未保存任何字段）」，**不落库** |
| 同上 | 未知平台键 | — | **只忽略该键**并 `warn` 点名；不作废整体（拼错一个平台名不该抹掉用户其余配置） |
| 同上 | 全部键都未知 | — | 视为无效 ⇒ 整体作废（不得留下空 map 被下游读成"覆盖了但值为空"） |
| 同上 | 值为 `null` / `undefined` 的项 | — | 跳过（等价于该平台不覆盖）；整个字段为 `null` ⇒ 清空该维度 |
| env | `MP_PUBLISH_ACCOUNT_MIN_INTERVAL_MS_JSON` | JSON 对象 `{"<platform>": ms}` | **值非法（非有限数 / `<0`）⇒ 整条作废** + 出声，全部平台回落表默认；**未知平台键 ⇒ 忽略该键** + 点名 |
| env | 同上 | 超上界 | **钳位**到 `MAX_INTERVAL_MS` 并出声（与既有间隔语义一致：钳位不作废） |
| env | 同上 | 坏 JSON / 非对象 / 数组 / 空串 / 未设置 | 整条视为缺席或作废 + 出声；**绝不抛错**（配置写错不能让发布链起不来） |
| IPC | `publishFreq:getPolicy` | 下发 `accountMinDefaults`（逐平台默认表）+ 每平台生效值 | 载荷缺字段 ⇒ 渲染层显示 `—`，**不得自造数字** |

env 为什么用**一条 JSON**而不是 15 个变量：15 个 `MP_PUBLISH_*_<PLATFORM>` 会变成"没人记得自己存在"的开关集。
代价是必须自己写校验，于是有了上面"值非法整条作废 / 未知键只忽略"这两档刻意不同的严格度——
前者防"一半生效不可解释"，后者防"一个拼写错误抹掉全部配置"。

### 5.2 三条交互纪律（每条都有对应的回归锁）

1. **未覆盖的平台必须留空**，不得用它的默认值预填。
   预填的后果：用户"什么都不改直接保存"会把每个平台钉成一份"默认值覆盖"，此后策略表再改**永不生效**。
   这是评审 i3（全局覆盖那次）的逐平台版本。
2. **一个都没填 ⇒ 省略 `accountMinMsByPlatform` 键**，而不是提交空 map。
   "清空覆盖"的既有语义是提交 `null`（`pubfreq-reset` 走的就是这条）。
3. **渲染层不持有任何频率数字**。默认值、生效值、上界全部来自 `getPolicy`；
   载荷缺 `accountMinDefaults` 时显示 `—`。结构锁扫 `.vue` 的**代码行**，
   出现平台名或 `60 * 60000` 这类第二份真源即红（注释不过滤会把自己写的说明判成违规，故过滤注释行，
   并同时断言过滤后的扫描域非空且真含代码——否则"把代码全滤掉"会让禁令恒真）。

## 7. 兼容、回退与运营口径

- **零迁移**：老 `publishFrequencyPolicy` 存储值不含新键 ⇒ `resolvePolicyOverrides` 原样忽略，行为等价于今天。
- **回退**：把表里 `tencent_video` 改回 `3 * MIN` 即恢复 v4 行为；`git revert` 本 PR 同样安全（无持久化格式变更）。
- **运营临时放宽**（不改代码）：
  `MP_PUBLISH_ACCOUNT_MIN_INTERVAL_MS_JSON={"tencent_video":180000}`（30 分钟），
  或设置页在该平台行填 30。env 与设置页的关系不变：设置页覆盖赢 env。
- **日志判障**：`[PublishFrequency] 环境变量 MP_PUBLISH_ACCOUNT_MIN_INTERVAL_MS_JSON … 整条作废 …`
  ⇒ 有一个值非法，**其余好键也一起失效**（这是刻意的，不是 bug）；
  `… 含未知平台 "xxx"，已忽略该键` ⇒ 拼错平台名，其余照常。

## 8. 验收标准

1. 视频号在未覆盖时的生效间隔为 60 分钟，其余 14 个平台与 v4 逐字节相同（L1、L3 实测）。
2. 设置页可为任意单平台设覆盖，且该平台不受全局值影响（L2、L10）。

## 9. 未闭合（不假装已闭合）

1. **视频号 60′ 与日配额 350 不对称**：60′ ⇒ 单账号一天理论 24 条，而该档配额是 350。
   真正卡住视频号连发的是**间隔**而不是配额；运营口径的"日发 1–5 条"两者都还没覆盖。
   本篇按用户口径只做"视频号严格一些"，配额是否要为视频号单独收紧**留给用户拍板**。
2. **定时发布表单仍是 5 分钟输入期校验**（`publish-schedule-contract.js`）：用户可对视频号排两条相隔 5 分钟的
   定时任务，表单放行、发布时由守卫排队推迟——"能提交但会等"，不是数据错误。
   改成逐平台校验要先决定"冲突时拒填还是自动顺延"，属产品口径，不在本片。
3. **60′ 这个数本身是拍的**：没有任何平台公布过间隔阈值。它应被运营数据（发布成功率／限流投诉）
   推翻或确认，代码注释与本 § 都把它标成"暂定"，就是为了让下一次改它不需要论证"为什么可以改"。
4. **吞吐影响未实测**：间隔收紧会让批量发布变慢。若用户体感"变慢"，回退成本是一行数据（§7）。
