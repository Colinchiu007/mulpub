## 1. 一句话：我需要的是什么

**每家供应商「你实际付了多少钱 ÷ 这些钱覆盖了多少额度」——也就是你的真实单价。**

有了这个数，才能算出「送 1000 积分」实际能换多少次生成、成本占售价比多少（研究报告 §3.3 / §3.4 的摊销四段全靠它）。没有它，只能用官网挂牌价，会把你的成本算高（买套餐通常比挂牌价便宜），导致赠送量给太少或定价过高。

## 2. 需要的数据（按计费方式分两类）

### 2.1 订阅套餐型（两种子形态：**有总额度** / **窗口配额**）

> 2026-10-11 运营方确认：MiniMax 这类套餐**不承诺具体额度，只用 5 小时窗口与周窗口限制**，因此必须区分下面两个子形态。

**子形态 2.1a：有总额度**（例：可灵 ¥3000 套餐包 2000 秒）

| 字段 | 说明 | 例 |
|---|---|---|
| 供应商 / 产品线 | 哪家、哪条产品 | 可灵 · 720P 视频 |
| **套餐类型** | **coding plan / API 套餐 / 会员制**——决定能否商用（见 §8.3） | coding plan |
| 实付金额 | **实际支付**（不是标价）；注明含税/未税 | ¥3000（含税） |
| **套餐总额度** | 这份套餐**包含**多少用量——**不是已用量**（见 §2.4-1） | 2000 |
| **已用量** | 当前**已消耗**多少（与上一行是两个独立字段，勿混） | 340 |
| 计量单位 | 秒 / tokens / 张 / 次 / 字符 | 秒 |
| **计量口径** | 额度按什么口径扣：是否含缓存读/写、缓存读是否打折——**同额度不同口径单价可差约 40 倍**（见 §8.2） | 输入+输出+缓存读（全额） |
| 有效期起止 | 什么时候到什么时候 | 2026-10-01 ~ 2026-12-31 |
| **速率限制** | 并发 / RPM / TPM / 每 N 小时次数——**额度用不完时，它才是瓶颈** | 每 5 小时 N 次 |
| **用途与条款** | 是否允许商用 / 供第三方 / 转售（自用、coding 套餐通常禁止） | 仅个人使用 |
| 折扣来源 | 为什么便宜（年付/预付/销售议价/活动） | 预付年包 |
| 是否续费 | 到期自动续费还是手动 | 手动 |
| 阶梯/超额价 | 超出套餐部分怎么算 | ¥3/秒 |

**子形态 2.1b：窗口配额（无总额度承诺）**（例：MiniMax coding plan，**只有 5 小时与周窗口限制**）

| 字段 | 说明 | 例 |
|---|---|---|
| 供应商 / 产品线 | 哪家、哪条产品 | MiniMax · coding plan |
| 套餐类型 | 见上；窗口配额型几乎都是 coding plan / 会员制 ⇒ 通常**不可商用** | coding plan |
| 实付金额 | 实际支付（注明含税/未税） | ¥49（含税） |
| **窗口结构** | 窗口长度 + 每窗口限额 | 5 小时窗口 + 周窗口 |
| **每窗口限额** | 具体数值。**不知道就写 `UNKNOWN`，不要编造**（见 §2.4 与设计文档 §7） | `UNKNOWN`（待查） |
| 限额单位 | 次数 / 等值用量 / tokens | 次数（推测） |
| 已过窗口数 | 从套餐生效起过了多少个窗口 | 约 50 个 5h 窗口 |
| **实测用量** | 同口径的实际消耗 | 8,789,898,170（四项合计，见 §8.1） |
| 计量单位 | tokens / 秒 / 张 / 次 | tokens |
| **计量口径** | 额度按什么口径扣 | `UNKNOWN` |
| 有效期起止 | 什么时候到什么时候 | ~2026-11-04 |
| 速率限制 | 见「窗口结构」 | 每 5 小时 N 次（N 待查） |
| **估算等效单价** | `已付金额 ÷ 实测用量`——**依赖使用强度的估算值**，必须带置信度 | ¥49 ÷ 8.79B（**置信度低**） |

> **子形态 2.1b 的单价是估算，不是事实。** 无总额度 ⇒ 单价随你的**使用强度**变化：用到窗口上限 10% 与 90%，单价差 9 倍。⇒ 这类**只能作成本参考，不得作定价基准**（详见 `01-docs/DESIGN-COMPUTE-BILLING-MODEL-2026-10-11.md` §5–§6）。
>
> **利率限制的填写纪律**：不知道就写 `UNKNOWN`。若确需一个占位数做规划，**必须加 `source=ASSUMED` 标记**并在报表中与实测值**分开渲染**——绝不允许占位数伪装成实测值（设计文档 §7）。
| 是否续费 | 到期自动续费还是手动 | 手动 |
| 阶梯/超额价 | 超出套餐部分怎么算 | ¥3/秒 |

### 2.2 按量付费型（中转站 / 聚合 API）

| 字段 | 说明 | 例 |
|---|---|---|
| 供应商 / 中转站名称 | 站点名 | （我来按你给的实际名称填） |
| 账户余额 | 当前余额 | ¥500 / $70 |
| **单价表** | **按模型**列价：输入 / 输出（每百万 tokens），或按次/按秒 | gpt-4o：$2.5/$10 per 1M |
| **倍率** | 中转站常见口径「官方价 × N」；有就写，没有写「无」 | ×1.2 |
| 结算币种 | CNY / USD | USD |
| 汇率口径 | 若以 USD 结算，按什么汇率折算 | 按充值当日汇率 7.1 |
| 近 30 天实付 | 实际扣了多少钱 | $42 |
| 近 30 天用量 | 对应消耗（tokens/次/张） | 8.2M tokens |
| 最低充值 / 余额告警 | 余额低于多少会停 | 充值 ≥$10 |

> **为什么按量型要单独要「近 30 天实付 + 用量」**：中转站的标称单价与实际扣费**经常不一致**（倍率、缓存命中折扣、渠道差异）。用「实付 ÷ 实际用量」反算出来的等效单价，才是能拿去算成本的数；标称单价只作参考。

### 2.3 通用（两类都要）

- **账单周期**：自然月 / 充值制（无周期）；
- **是否含税**；
- **有没有阶梯价**（用量越大单价越低）；
- **速率限制**：并发上限 / RPM / TPM / 每 N 小时次数。**要专门问一句「额度用不完的时候，速率是多少」**——大额度 + 紧速率的套餐，瓶颈在速率（见 §8.3）；
- **用途与条款**：能否商用、能否供第三方、能否转售（自用 / coding 套餐通常禁止，见 §8.3）；
- **试用 / 赠送额度**：是否与付费额度合并计数（会拉低等效单价）。

### 2.4 采集后的交叉校验（新增；来自首条样本的实测教训）

| # | 校验 | 判据 | 失败动作 |
|---|---|---|---|
| 1 | **额度 ≠ 已用量** | 填报的「总额度」若与导出文件的用量合计**吻合**即判可疑 | 要求复核（首条样本就踩了这条，见 §8.1） |
| 2 | 口径自洽 | 「总额度 − 已用量 = 剩余」必须在**同一计量口径**下成立 | 口径不明则退回补问（见 §8.2） |
| 3 | 单价量级合理 | 反算单价的**数量级**应在该品类的常识区间内（LLM 约 ¥0.5–50/1M tokens；视频约 ¥0.1–10/秒；图片约 ¥0.01–1/张） | 偏离一个数量级以上必须给出解释，否则**不得用于定价** |
| 4 | 期效覆盖 | 有效期覆盖预期运营期 | 不覆盖 ⇒ 只能作参考单价，**不得进供给池**（见 §8.3） |

> 第 3 条的区间是**防错护栏的粗略量级**，不是市场调研结论；随采集样本增多再校准。它的作用只有一个：把「已用量当额度」这类错误挡在定价之外。

## 3. 这些数据落到哪（设计影响，供实现方）

数据最终进入运营中心的**套餐台账**（PRD §4.2 F1）。因上游混合计费，台账必须容纳两种形状：

| | 订阅套餐型 | 按量付费型 |
|---|---|---|
| 核心字段 | 总额度 + 有效期 + 已用量 | 余额 + 单价表 + 倍率 |
| **等效单价算法** | 实付金额 ÷ 套餐总额度 | 周期实付 ÷ 周期实际用量 |
| 耗尽判据 | 已用量 ≥ 总额度 或 过期 | 余额 ≤ 0 或 单价表不可得 |
| 摊销四段（研究报告 §3.4） | 按剩余额度比例 | 按余额比例 |
| **供给资格** | 需过三判据（条款/速率/期效，见 §8.3 与 PRD §4.2 F1） | 同上（余额为 0 或单价表缺失即失格） |

**建议**：`provider_plans` 一张表 + `billing_type` 判别字段（公共字段：供应商/实付/币种/状态；分型字段可空），或拆「套餐台账」与「按量价目表」两张表。**这个选择必须在写迁移前定**（否则返工），见 PRD §4.4-6。

## 4. 交付方式（**安全纪律优先**）

按推荐顺序：

1. **首选：导出文件**。供应商后台的「账单 / 费用中心 / 用量明细」导出 CSV、Excel，或直接截图，放到一个本地目录，把**路径**告诉我即可。
2. **可选：只读接口凭证**，由我写脚本拉取。**但请遵守三条**：
   - **不要贴在聊天里**。放到仓库外的本地文件（例：`D:\Data\projects\mulpub\.local\upstream-billing.env`，或任意仓库外目录），只告诉我路径；
   - 必须是**只读 / 账单查询**权限的凭证，不要给能消费、能改配置的主账号密钥；
   - 我会保证它**不写入 git、不写入日志、不写入记忆文档**（本项目刚在 S6 收紧了日志脱敏，但纪律仍是「源头不落盘」优先）。
3. **兜底：口头/文本给关键数字**（哪家、多少钱、多少额度），我先按粗口径填，后续再补细。

**原始导出文件默认不进仓库**：账单明细含用量结构与单价，属运营敏感信息。我读完后只把**归一化后的单价与结论**写进文档；原始 CSV/Excel 留在仓库外（与研究报告放在仓库外同一处理）。

**我不会做的事**：不把任何上游凭证或账单明细提交进仓库；不在 PR/文档/记忆里写你的具体密钥；不把单价数据下发到桌面客户端（价格属运营敏感信息，研究报告 §4.1 明确「不要塞进 `ModelPreset`」）。

## 5. 常见坑（提前对齐，避免来回）

| # | 坑 | 为什么重要 |
|---|---|---|
| 1 | **含税 / 未税混用** | 混着算会让成本偏差百分之几到十几 |
| 2 | **币种与汇率** | 中转站多以 USD 结算；用哪个汇率折算直接决定成本 |
| 3 | **套餐有效期跨月与结转** | 「月清零」的积分口径 vs 套餐本身的有效期不是一回事，要分清 |
| 4 | **赠送/试用额度** | 有些套餐附赠额度（不算钱但算用量），要单独标出，否则等效单价被拉低 |
| 5 | **已过期/已停用套餐** | 不能进供给池，但要留档（算历史成本时用得到） |
| 6 | **中转站倍率 vs 实际扣费不一致** | 见 §2.2，必须用实付反算 |
| 7 | **阶梯价** | 用量变化会让单价变化，测算时要知道处在哪一档 |
| 8 | **速率限制** | 套餐额度再大，若 RPM/并发很低，高峰时等于「买得到用不上」——这会影响供给池的调度策略（研究报告 §7.4） |
| 9 | **「额度」与「已用量」混淆** | 会把单价算低一到几个数量级，据此送积分必亏。首条样本即踩（§8.1），校验见 §2.4-1 |
| 10 | **计量口径不同（缓存读是否计入 / 是否打折）** | 同一个数字在两种口径下的单价可差约 40 倍（§8.2）。属**必采字段**，且逐供应商不同 |
| 11 | **把个人 / 自用套餐当作平台供给源** | 条款违约 + 速率受限 + 有效期短，三重不可行（§8.3）。这类只能计入成本测算的**参考单价**，不得进供给池 |

## 6. 我拿到数据后会做什么（验收与回报）

1. 产出一份**归一化清单**（Excel/表格）：供应商 × 计费方式 × 实付 × 额度 × **等效单价** × 有效期/余额，给你核对；
2. 据此把 PRD §4 的**套餐单价与摊销测算**补实（研究报告 §3.4 四段：保底期 / 接近耗尽 / 濒危 / 耗尽）；
3. 反过来校验「赠送量」（现行口径：标准版 1600 积分、专业版 2200 积分，1 积分 = ¥0.01 上游成本）是否站得住——**如果真实单价明显高于挂牌价假设，赠送量需要下调**，否则会亏；
4. 把「单价口径」以**可复核的形式**记入 PRD 与运营中心设计，不写死进代码（研究报告 §3.2 的「写死单价是定时炸弹」）。

**争议处理**：凡我算出的等效单价与你后台账单不一致，**以你的账单为准**，我会把差异记进文档而不是覆盖你的数。

## 8. 首条参考样本与实测发现（2026-10-11）

**样本**：供应商 **MiniMax**；类型为**订阅套餐（coding plan）**——导出文件「来源」列 95 行全为 `MiniMax Code`；实付 **¥49**；声称有效期至 **2026-11-04**。附用量导出 `token_plan_usage`（2026/10/01 21:00 ~ 2026/10/11 12:00，95 行数据）。

> ⚠️ **运营方明确声明**：这份套餐是**其个人自用**，**尚未**作为平台内置模型录入运营中心；提供它只为校准字段与校验规则。因此下列发现**不等于**已具备平台供给资格（见 §8.3）。

### 8.1 抓到的第一个数据错误：把「已用量」当成「总额度」

导出文件四项合计 = **8,789,898,170（8.7899B）**，与运营方填报的「覆盖额度 8.79B」**精确吻合（差 0.0012%）**。这不可能是巧合 ⇒ 该数字是**已用量**（控制台「计划用量」），**不是**套餐覆盖的总额度。

| 项 | 值 |
|---|---|
| 输入 Token | 209,731,258 |
| 输出 Token | 13,577,188 |
| 缓存读取 | 8,566,589,724 |
| 缓存写入 | 0 |
| **四项合计** | **8,789,898,170** |

**后果**：若照此算，等效单价 = ¥49 ÷ 8.79B = **¥0.0056/1M tokens**——比常识区间低一到几个数量级（§2.4-3），据此定价会严重低估成本、超送积分。

**已固化为校验规则**：见 §2.4-1（额度与用量合计吻合即判可疑、要求复核）。

### 8.2 第二个发现：计量口径可造成约 40 倍单价差异

同一个 8.79B，在不同口径下含义完全不同：

| 口径 | 用量 | 若按「¥49 覆盖该口径」反算单价 |
|---|---|---|
| 四项总计（输入+输出+缓存读+缓存写，缓存读**全额**计入） | 8,789,898,170 | ¥0.0056 / 1M |
| 仅 输入 + 输出 | 223,308,446 | ¥0.22 / 1M |
| 输入 + 输出 + 缓存读按 10% 折算 | 约 1.08B | ¥0.045 / 1M |

**首行 vs 次行 = 39.4 倍**。而实测结构显示：**缓存读取占 97.5%**，输入 : 缓存读 ≈ **1 : 40.8**（样本中 M3.1-Flash-Preview 的 cache 命中率常态在 95–99%）。

⇒ 「额度按什么口径扣」**必须逐供应商采集**，否则单价不可比、不可用。这是 §2.1「计量口径」字段存在的原因。

### 8.3 第三个发现：这类套餐**不能直接作为平台供给源**

三条硬约束叠加：

1. **用途条款**：coding plan 面向**个人开发使用**，通常禁止转售或供第三方使用。拿它承载平台用户流量属违约，有封号风险；
2. **速率限制**：coding plan 是「大额度 + 强速率限制」形态（典型为每 N 小时 M 次）。**额度不是瓶颈，速率才是**——用户高峰一挤就撞墙，且这是**买再多额度也解决不了**的那类瓶颈；
3. **有效期极短**：本样本 2026-11-04 到期（距采集日仅 24 天）⇒ 供给池必须有「**到期自动摘除 + 提前告警**」，否则线上静默失败。

⇒ 由此引入 **供给资格（eligibility）判据**（已写入 PRD §4.2 F1）：只有同时满足「条款允许商用/供给」「有可观测且够用的速率上限」「有效期覆盖运营期」的套餐才能进供给池；不满足的**只能计入成本测算的参考单价**，不得进池。

### 8.4 样本局限（**不据此下结论**）

- 仅 **10.6 天**、**单一供应商**、**单一模型**（M3.1-Flash-Preview 占输入 99.9%）；
- 来源全部为 `MiniMax Code`（coding agent 形态）⇒ **不代表**开放平台 API 套餐的用量结构；
- 输出占比极小（13.6M / 8.79B），是 coding agent 的典型形态（大量上下文读取）⇒ **与视频/图片/TTS 类业务的用量结构不可比**。

⇒ 需更多供应商与更长周期，才能反推稳定单价与采购折扣系数。**当前不得用本样本推导赠送量或定价**，它只用于校准字段、校验规则与资格判据。
