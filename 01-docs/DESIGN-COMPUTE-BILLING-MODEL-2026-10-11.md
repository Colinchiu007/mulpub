# DESIGN NOTE：算力计费模型分层设计（DN-COMPUTE-BILLING-001）

> **创建**：2026-10-11 ｜ **状态**：**提案（三项原则已获运营方确认）**
> **触发问题**：运营方问「上游计费方式多种（订阅套餐 / 按量付费，且 MiniMax 这类只有 5 小时与周窗口、不承诺总额度），**是否需要做一套适应多种情况的复杂计费模型，支持多个计算方式？**」
> **关联**：`PRD-OFFICIAL-COMPUTE-STOPGAP-2026-10-09.md` §4 ｜ `HANDOFF-UPSTREAM-BILLING-INTAKE-2026-10-11.md` §2 / §8

---

## 0. 结论（TL;DR）

**不要做「多套计费模型」。要做三层分离，其中只有中间一层的形状多样，用户侧永远只有一套。**

> **「多种计算方式」是上游采购的事实，不是产品要暴露的概念。** 它必须被关在采购登记与换算层里，不得泄漏到用户可见面。

---

## 1. 问题与需求

### 1.1 上游实况（为什么"情况多"）

| 维度 | 实况 | 是否已定 |
|---|---|---|
| 供应商数量 | ≥2（清单未定，运营方后续补充） | ❌ 未定 |
| **计费形状** | **3 类**：A 有总额度套餐 / B 按量付费 / C 窗口配额订阅（无总额度） | ✅ 已确立 |
| 计量家族 | ≥3：token / 秒 / 张·次·字符 | ✅ 已确立 |
| **计量口径** | **逐供应商不同**（缓存读是否计入/打折） | ⚠️ 首条样本即未知 |
| 速率约束 | 逐供应商不同（窗口制 / RPM / 并发） | ⚠️ 多处未知 |
| 用途条款 | 部分套餐禁止商用（如 coding plan） | ✅ 已确立 |

### 1.2 若照"多套模型"直觉做，会发生什么

若为每种计费方式在**用户侧**做一套算法与一套界面语义，会立刻产生：每个计量家族一套余额、一套预警阈值、一套换算文案（3 套 UI 语义）；用户无法比较「生成一段视频」与「写一篇文章」哪个更贵（单位不同）；加第 4 个家族要改用户侧全部展示。

**这正是积分体系存在的理由**——积分就是把不同计量统一成可比较单位的那一层。绕过它等于白做积分体系。

---

## 2. 方案选择（三选一）

| | 方案 A：多套计费模型并列 | **方案 B：三层分离（推荐）** | 方案 C：只支持按量付费 |
|---|---|---|---|
| 做法 | 每种形状一套算法 + 一套用户侧语义 | 采购形状多样（数据）→ 单层换算 → 用户侧单一积分模型 | 放弃套餐，只做按量 |
| 优点 | 每种形状都贴合 | 形状数量**有界**；加供应商 = **加数据行**；用户侧**零改动**；计量差异被积分吸收 | 最简单 |
| 缺点 | UI 语义 ×N；加形状要改用户侧；用户无法跨品类比较 | 需在采集侧建立「形状判别」纪律；C 类无法精确单价（**但那本来就是事实**） | 与上游实况不符（已有/将有套餐）；**浪费已购额度** |
| Completeness 评分 | 4/10 | **9/10** | 6/10 |

**选 B。**

## 3. 三层设计

| 层 | 载体 | 形状 | 加一个新供应商的代价 | 本设计是否新建 |
|---|---|---|---|---|
| **L1 采购登记** | `provider_plans` | **3 类形状**（见 §4），字段按形状可空 | **加一行数据**，不加算法 | ✅ 新建 |
| **L2 单价换算** | `model_price_cards` | **1 张费率表 + 3 个计量家族** | **加几行费率** | ✅ 新建（研究报告已规划） |
| **L3 用户扣费** | `identity_entitlement_usage`（现有） | **唯一模型**：预扣 → 结算（→ 退款），扣的永远是积分 | **零改动** | ❌ 形状不变 |

**L3 的不可破约束**：用户在界面上看到的永远只有「本次消耗 N 积分 / 剩余 M 积分」；**永远不出现**「这个模型按秒计费 / 那个按 token 计费」。计量家族差异只影响 L2 的**费率数值**。

## 4. 三类采购形状与判别规则

| | A 订阅套餐（有总额度） | B 按量付费 | **C 窗口配额订阅** |
|---|---|---|---|
| 例 | 可灵 ¥3000 包 2000 秒 | 中转站充值 ¥500 | **MiniMax coding plan**（5 小时 + 周窗口） |
| 约束性质 | **累计**用量封顶 + 到期 | **余额**耗尽 | **时间窗**内封顶、窗口滚动重置 |
| 有「总额度」吗 | 有 | 无（有余额） | **无——运营方也无法预知总量** |
| 单价可否精确算 | 可（实付 ÷ 总额度） | 可（实付 ÷ 实际用量） | **不可，只能估算（见 §5）** |
| 摊销四段（研究报告 §3.4）适用 | ✅ 必要（有累计额度才有"接近耗尽"） | ❌ 只需用尽告警 | ❌ 无摊销可言（窗口滚动） |

### 4.1 判别规则（防止形状爆炸）

**新增一类形状的唯一理由是「约束的性质不同」，不是「供应商不同」。**

```
新供应商的约束能否归入已有三类？
  ├── 能在【累计】维度封顶            → A
  ├── 能在【余额】维度封顶            → B
  ├── 只能在【时间窗】维度封顶且窗口滚动重置 → C
  └── 都归不进 → 才新增第 4 类，且必须写出它与前三类的【本质差异】
```

**本规则保证形状数量与供应商数量无关**（当前有界为 3 类）。这是"不复杂"的机制保证，不是口头承诺。

## 5. C 类（窗口配额）的估算方法——以及为什么它不能作定价基准

无总额度 ⇒ **单价不是套餐的属性，而是使用强度的函数**。同一个 ¥49 套餐，用到窗口上限 10% 还是 90%，等效单价差 9 倍。

估算流程（**全部是估算，必须带置信度**）：

1. 记录窗口结构：窗口长度（5h / 周）、每窗口限额（**当前 UNKNOWN**）、已过窗口数；
2. 用实测量反推可达用量：`实际可达用量 ≈ 实测已用量 ÷ 已过窗口数`（前提：期间接近窗口上限；若没用到则**低估**）；
3. 等效单价 = `已付金额 ÷ 实测用量`（**该使用强度下**的估算）；
4. 置信度标注：**低**（既不知道限额，也不知道是否触到限）；
5. **低置信度 ⇒ 只能作"成本参考"，不得进入定价基准**。

---

## 6. 定价基准的来源优先级

1. **B 类（按量付费）** —— 有单价表、实付可反算、无窗口黑箱 ⇒ **首选基准**
2. **A 类（有总额度的套餐）** —— 实付 ÷ 总额度，口径清楚 ⇒ 次选
3. **C 类（窗口配额）** —— 只能估算且依赖使用强度 ⇒ **仅作参考，不入基准**

> 推论：上游**以按量付费为主**对定价是**好消息**——基准最硬的就是它。

---

## 7. 纪律：未知值 fail-closed，**不编造**

上游目前有三处 UNKNOWN：C 类每窗口限额、MiniMax 计量口径、后续供应商清单。

| 纪律 | 做法 |
|---|---|
| 不填占位数字 | 编造的数字会一路流进单价测算与供给池容量规划，**假数据比没有数据更糟**（本仓先例：S4 成本项宁留 NULL 也不本地估算） |
| 速率未知 | 资格判据②不通过 ⇒ `reference_only` ⇒ **不进供给池**（fail-closed） |
| 计量口径未知 | 该套餐**不参与单价比较与定价**（口径缺失即不可比） |
| 好处 | 未知不会伪装成已知；真实值到位后**只改数据、不改设计** |

**妥协方案（若确需占位数做规划）**：可以填，但必须结构上**无法被误认为实测值**——加 `source=ASSUMED` 标记，报表单独渲染，**绝不与实测值混排**。

## 8. 影响范围

| 对象 | 影响 |
|---|---|
| `provider_plans`（新表） | 需 `billing_shape` 判别字段 + 三类形状字段（按形状可空）+ `usage_unit` + `measurement_basis`（计量口径）+ `rate_limit` + `usage_terms` + `reference_only` 状态 |

| 运营中心前端 | 套餐页需两种形状表单 + 供给资格判据结果展示（PRD §4.2 F1） |

## 9. 风险点与缓解

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **C 类估算被误当定价基准** | 定价偏低 → 亏损 | 基准优先级（§6）+ 报表强制标注 `source`/`confidence`；C 类默认 `reference_only` |
| 2 | **形状误判**（把 C 塞进 A，于是拿"总额度"当分母） | 单价算错一到几个数量级 | 判别规则（§4.1）+ 采集校验（额度 ≠ 已用量） |
| 3 | 未来出现第 4 类形状 | 设计返工 | 判别规则要求写出本质差异；形状数量有界 |
| 4 | 计量口径未知导致定价错 | 差约 40 倍（首条样本实测） | 口径缺失即不得定价（fail-closed） |
| 5 | `provider_plans` 变宽表（三类字段堆一张表） | 可维护性下降 | 见 §10 决策点 1；**写迁移前必须定** |
| 6 | 用户侧被"泄漏"上游计量方式 | 复杂度爆炸、用户困惑 | L3 约束（§3）+ 契约测试（§11） |

## 10. 待决策点（留给第二阶段 `/opsx:propose`）

1. `provider_plans` **单表 + `billing_shape` 判别** vs **拆「套餐台账」+「按量价目表」两张表**；
2. `billing_shape` 与 `reference_only` 落库形式（枚举值命名与迁移默认值）；
3. `model_price_cards` 的积分换算口径（现行：1 积分 = ¥0.01 上游成本）是否维持；
4. `source=ASSUMED` 的表达方式（字段 / 枚举 / 单独列）。

## 11. 测试策略（设计层如何验证）

| 层级 | 用例 |
|---|---|
| 单元 | 形状判别（3 类 + 边界输入）；A/B 等效单价算法；C 类估算**必须**带置信度标注；口径缺失时**拒绝**参与定价；`reference_only` 不进供给池 |
| 数据校验 | 填报「总额度」与用量合计吻合 ⇒ 判可疑；「额度 − 已用量 = 剩余」在同口径下成立 |
| 契约 | 用户侧可见面**只出现积分**（文案/快照扫描，禁止出现"按秒/按 token"计费语义） |
| 变异反证 | ① 把 C 类当 A 类算 ⇒ 必须红；② 去掉计量口径校验 ⇒ 必须红；③ 让 `reference_only` 可进池 ⇒ 必须红 |
