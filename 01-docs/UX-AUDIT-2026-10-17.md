## 3. 改版机会点（按优先级）

### 🥇 O1 给不可逆操作装安全网
- 关联：audit-1, 2, 3, 12, 13, 27, 28
- 为什么第一：这是唯一一类「用户做错一次就永久损失内容或对外发出无法撤回的东西」的缺陷。**单篇**发布（`Publish.vue:544`）当前点一下即外发、无摘要确认（批量路径已有确认，见 audit-1 更正）；发布到 15 个中文平台是**外部可见、不可撤回**的动作。
- 影响面：`Publish.vue`、`usePublishFlow.js`、`usePublishDrafts.js`、`Accounts.vue`、`CacheCleanupSection.vue`、`ProfileMenu.vue`、`AccountSecurity.vue`
- 成本：低-中（删草稿补确认约 5 行；发布前摘要确认约 1 个组件）

### 🥇 O2 把已经建好的功能接上电（接线批次）
- 关联：audit-4, 6, 7, 10, 11, 20, 24（**audit-9 已移出本包**，见下条与阶段 1.1）
- 理由：包内修复动作多是「加一行挂载 / 加一个入口」，收益是整条功能从 0% 可达变 100% 可达，是全表 ROI 最高的一包。
- **⚠️ 评审否证后修正（c2/w17）**：上一版称本包「几乎不产生新的视觉回归面」并把 audit-9 主题接线列在首位——**该宣称不成立并已撤回**。接线暗色主题会让实测 **72 处** `[data-theme=...]` 选择器（`styles/*.css`，当场 grep 重取；77 是第一轮已撤回的旧值）与 **20 张**暗色基线（实测 `base-screenshots/` 共 43 张，其中 `*-dark.png` 20 张）**首次变成真实用户可达态**，即凭空引入一大块回归面；其成本也从 S 上修为 **M**（需设置页 UI + 跟随系统检测 + 持久化 + 暗色基线重建与人工审核）。故 **audit-9 移出本包，独立成「1.1 主题接线」单独批次**，验收含暗色基线重建。

### 维度 5：error-prevention 错误预防

**[audit-1] [major] 单篇发布无确认闸门（原判 blocker 已被外部评审否证并降级）**
- 证据（**两轮评审后收敛**）：`usePublishFlow.js:289-350` 缺的是**发布摘要确认**，入口 `views/Publish.vue:544`。⚠️ 不得写成「整条路径无 confirm」——`:448-455` 有敏感词命中的 `notifyConfirm` + `if (!confirmed) return`，那是**条件性**闸门，不是无闸门。准确表述：单篇路径**仅有敏感词强确认，缺发布前的摘要确认（平台×账号×篇数）**。
- ⛔ **原证据里的「`:123` 批量」是错的，已删除**：`composables/runBatchPublish.js:124-140` 实有 `const confirmed = await notifyConfirm(...)` + `if (!confirmed) return`，且确认文案已含条数、平台任务数与截断汇总；`useCollectionBatchPublish.js:189-193` 同形。本报告的 audit-28 早已写到那个确认弹窗存在，**与 audit-1 前后矛盾**，属自查漏项。
- 因此本条只成立到「**单篇**发布缺摘要确认」，批量路径已有闸门。降级 blocker→major。
- 症状：误点一次即把内容推向外部平台，无法撤回；用户以为「点了会让我确认」。
- 建议：发布前摘要确认（平台 × 账号 × 篇数 + 截断预警）。⚠️ **前置：0.4 的 `confirmDanger` 结构门禁先落地**——该原语目前自称契约而仅 4 个消费点（audit-12），未硬化前直接复用等于传播一个不可信机制。成本 M。

**[audit-2] [blocker] 同一个删除 API 在两个页面守卫不对称**
- 证据：`views/Publish.vue:586` → `composables/usePublishDrafts.js:184-190` 直接 `await draftDelete(draftId)`，无确认；`composables/useCollectionDrafts.js:159-166` 对**同一个** `draftDelete` 先 `notifyConfirm`。
- 症状：在发布页误点「删除」，刚写好的正文永久丢失，且无回收站/无撤销（全仓 `undo|撤销|回收站` 仅命中 story2video 自己的撤销栈）。
- 建议：`Publish.vue:586` 补确认，文案含被删标题与条数。成本 XS（约 5 行）。

**[audit-3] [major] 零「未保存离开」拦截（对 Publish 页的症状描述已被否证并降级）**
- 证据：`onBeforeRouteLeave` 命中 **0**、`beforeunload` 命中 **0**（域自检：同批 `onMounted` 命中 156）。`App.vue:270-272` 只拦「关闭未保存凭证的账号标签」，不拦路由切换。
- ⛔ **原症状「文章写一半点侧边栏即丢草稿」对 Publish 不成立，已撤回**：`App.vue:73` 是 `<keep-alive :include="[Publish]">`（`:68` 注释明写「让发布页在【路由切换】时也保留」）。路由切换保活的回归锁在 **`publish-draft-keepalive.test.js`**；⚠️ 本行曾误引 `publish-tab-state-keepalive.test.js`，那个文件锁的是 `v-show` **标签切换**（`App.vue:64-75` 注释），第三轮评审命中此张冠李戴。`onBeforeRouteLeave`/`beforeunload` 在**排除 `*.test.*` 后**计数为 0（含测试则 `beforeEach(` 有 296 处，域必须写明）。
- 成立范围收敛为：`CreateView` / `RewriteView` 等未被 keep-alive include 的编辑页，以及标签关闭与应用退出路径。
- 建议：先枚举「哪些编辑态页面不在 keep-alive include 内」再挂脏标记 + `onBeforeRouteLeave`；**不得**把 Publish 与它们并列。降级 blocker→major。成本 M。

**[audit-12] [major] 确认机制碎成 4 套，且自称的契约与现实不符**
- 证据：`utils/confirm-danger.js:6-7` 注释写「所有删除类/不可逆操作必须经由此函数」，实际只有 **4** 个消费点；其余走 `notifyConfirm`（`useNotify.js:107`，48 处）、`ConfirmDialog`（`CreateView.vue` 12 处）、两步内联（`PublishProgressFooter.vue:51`）。
- 建议：先加结构门禁（扫 `delete/remove/clear` 写入口未走 `confirmDanger` 即红），再逐个补。成本 S。

**[audit-13] [major] 6 类破坏性操作无确认**
- 证据：清理缓存 `components/CacheCleanupSection.vue:76-86`；退出登录 `components/ProfileMenu.vue:256-264`、`views/member-center/AccountSecurity.vue:71-78`；撤销其他所有会话 `AccountSecurity.vue:80-87`；删草稿（见 audit-2）；发布（见 audit-1）。

1. **同一失败模式三轮各犯一次**：把「我的扫描域没扫到」当成「不存在」。第一轮 `markDone|isFirstRun` 漏 `runSetup`；第二轮 `electron/preload + src` 漏 `electron/window.js`；第三轮 `beforeEach` 未区分含/不含测试。**三次都不是判断错，是探针域选错。** ⇒ 任何「0 命中 / 只有 N 个 / 全仓没有」的断言，**必须与结论同行写出扫描域**，否则不成立。

## 第三轮更正（2026-10-19）：audit-60 的 harm 陈述被实测否证，4.6 的正确范围随之收窄

**触发**：准备按阶段 4.6「toast 容器补 `role="status"`/`aria-live`」动工前，先核实了已安装的组件库实现（AGENTS「宿主 API 字段归属必须先核实」同一条纪律：读库的真实产物，不读规范印象）。

### 实测读数（element-plus 2.14.2，本机 `node_modules`）

| 取数 | 命令 / 位置 | 读数 |
|---|---|---|
| 消息根节点的语义角色 | `node_modules/element-plus/es/components/message/src/message.vue_vue_type_script_setup_true_lang.mjs` 里 `role` 出现 **1** 次，值为 `"alert"`，挂在 `.el-message` 根 div 的属性表上（与 `style`/`onMouseenter`/`onMouseleave` 同级） | **每条 toast 都带 `role="alert"`，且不分类型** |
| 消息组件是否暴露任何 aria 选项 | `src/` 下 5 个实现文件（instance / message / message.vue_setup / message2 / method）里 `aria-` 出现次数 **全为 0** | 库不提供 `aria-live` / `aria-atomic` 一类可配置项 |
| 调用方能否拿到 DOM 句柄 | `message.d.ts` 的 `interface MessageHandler { close: () => void }` | 返回值只有 `close()`，**没有 `.el`**；想改根节点属性只能挂载后再查 DOM（脆） |
| 原 finding 的"仅 12 处 aria-live / 11 文件" | 与上面三条不矛盾 | 成立，但它是**计数事实**，不是"用户听不到"的证据 |

### 结论：原 finding 的 harm 陈述不成立，成立的是另一半

- **不成立**：「250 次 `ElMessage.*` 作为主要反馈通道，**读屏用户听不到成功/失败**」。`role="alert"` 是隐式 `aria-live="assertive"` 的 landmark，每条消息都会被播报。按这句话去"补 role"，补出来的会是**第二个播报源**（重复朗读同一段文案），比现状更差。
- **成立**：因为不分类型统一 alert，**礼貌级无法区分** —— 成功/信息类本该走 polite（不打断用户当前朗读），这里也走 assertive；批量发布连发多条 toast 时会**连续打断**。这是真实的残留可用性问题，但它的解法不是加 role，而是**限频/合并**与**按类型分流**。

### 因此阶段 4.6 改成这样（不照字面执行）

1. **不在应用侧新增 live region**，也不给 `.el-message` 加 `aria-hidden`（框里有可聚焦的关闭按钮，隐藏容器会把焦点可达性一起弄坏）。
2. **限频/分组优先**：`showToast` 单点化那一批（PR #3996）已经在唯一出口做时长档位与 grouping 策略 —— 连发打断属于同一处可收敛的面，应在**那一个出口**上收，而不是在 250 个调用点上收。
3. **若确要按类型分礼貌级**，先做真机取证（NVDA + Windows 内置 Narrator，必要时 VoiceOver），拿到"同一文案被读几次/是否打断"的现场，再决定是覆盖根节点 role 还是接受现状。**不得**凭规范推断直接改 DOM —— 本仓对"装饰性改动"的记录比这条修复本身更贵。
4. 上面第 3 条落地前，`role="alert"` 的现状**按已接受处理**（不是"待修的沉默缺陷"）。

### 方法论（与 `learnings.md` 同族，这里就地记一条）

这是一条**被否证的审计 harm 陈述**：计数证据（`aria-live` 出现 12 次）是真的，但从它推到"用户听不到"跳过了"播报的载体是不是只有 aria-live 这一种"。审计里任何 `X 计数很低 ⇒ 用户得不到 Y` 的句子，动工前都必须先回答**"还有哪条通道在承载 Y"** —— 本例的答案是组件库已经用 `role=alert` 承载了播报，只是没有分级。
