# 调查：本机单次进程创建成本约 1 秒（未闭合，机器级前提）

调查日期：2026-10-15 ～ 2026-10-16。触发场景见 `openspec/changes/fix-precommit-reviews-spawn-storm/`。
**结论边界先说清楚：本文不闭合该问题，只把它从「猜测」变成「有读数、有复跑方法、有自证口径」的登记项。**

## 1. 现象

多个并发会话的 `git commit` 全部停在原地，且**每个 `git commit` 进程自身 CPU≈0**；同时整机 CPU 高企。看起来像「git 在抢锁」，实测否证（见 §4）。

## 2. 关键读数（本机一次采样，均为时点数）

| 判据 | 读数 | 复跑口径 |
| --- | --- | --- |
| 原生 `cmd.exe /c exit` × 10 均值 | 拥堵现场 **1,175 ms** / 风暴排空后 **53 ms**（同机、同一套防护与索引器在场） | PowerShell 内 `Stopwatch` 包 10 次调用取均值 |
| 原生 `git --version` × 10 均值 | 699 ms | 同上 |
| **空临时仓库** `git rev-parse HEAD` × 5 均值 | 705 ms | `git init` 一个空库再测 ⇒ 与仓库体积/index 大小无关 |
| 本仓 `git rev-parse HEAD` × 5 均值 | 774 ms | 同上，差值不显著 |
| `git ls-files -- <一条记录>` × 10 均值 | 970–2,284 ms | 见下「测量污染」小节 |
| `git diff --quiet -- <一条记录>` × 10 均值 | 1,329–1,697 ms | 同上 |
| git.exe 创建速率 | **18.2 个/秒**（12 秒内 218 个不同 PID） | 400 ms 采样，按 PID 去重 |
| 整机 CPU | **6.32 / 12 逻辑核在忙（53%）** | `Get-Process` 两次快照差分算 CPU 增量 |
| 内存 | 74.2% 已用 / 8.4 GB 空闲（清理后真值） | 见「测量污染」 |

**判读（2026-10-16 复测后更正，见 §8）**：拥堵现场一次「什么都不做」的进程创建要 1 秒级；风暴排空后同法复测为 53 ms。
因此**不能**把「~1 秒」当机器常数用 —— 它是并发 spawn 压力下的放大读数。真正成立的因果是：
O(N) 的 spawn 形态 × 并发会话数 ⇒ 互相把对方的进程创建拖慢 ⇒ 拥堵自持。本例单条链付 1,218 次创建，
13 条链同时付 ⇒ 机上瞬时并发创建约 18.2 次/秒。拆掉 N 这一侧，才是拆掉放大器本身。

## 3. 归因边界：哪些是实测、哪些只是线索

**实测成立**：进程创建成本与 git 无关、与仓库无关、与 MSYS 无关（拥堵现场原生 `cmd.exe` 同样 1,175 ms）。因此「不是 git 慢」「不是仓库大」「不是 bash fork 模拟慢」。
**但归因边界要收窄**：这组否证只说明「慢不在 git/仓库/MSYS」，**不**说明「慢在实时拦截层」—— 排空后同一套防护与索引器在场、成本却回落到 53 ms，说明在场组件只是候选放大器，未做单变量实验前不得当致因引用。

**在场但未做因果实验**（只作线索，不得当结论引用）：

| 在场组件 | 现场读数 | 未做的实验 |
| --- | --- | --- |
| 注册实时防护：腾讯电脑管家系统防护（`QQPCRTP` 运行中，`QQPCTray` 历史累计 CPU 16.9 CPU·小时） | `Get-CimInstance -Namespace root/SecurityCenter2 -ClassName AntiVirusProduct` 报两条：管家 + Windows Defender（state 393472） | 未做「临时停用实时防护后复测 10 次」的 A/B |
| `Everything` 常驻索引（历史累计 **36.4 CPU·小时**，当次采样 0.98 核） | 同上差分表 | 未做「排除 `D:\Data\projects\*` 后复测」的 A/B |
| 极空间 `ZSpaceSync` / `syncstate` / `ZSpaceMountMonitor` 监听 D:（累计 5.5 CPU·小时；`syncstate` 当次 0.5 核） | 同上 | 未做「暂停同步盘后复测」的 A/B |
| `ipf_helper`（当次 0.56 核，累计 15 CPU·小时） | 同上 | 归属未查明，未做对照 |

**为什么这些只能算线索**：进程创建被拖慢的典型原因是内核回调过滤（实时防护、索引器、同步盘的 minifilter 都会在每次 CreateProcess / 文件打开时插入工作），但本仓没有对任何一个组件做过「关掉它 → 复测 → 数值变化」的单变量实验。**没有对照实验就没有归因**，下文排除项因此是「值得一试的排查顺序」，不是「做了就会好的处方」。

## 4. 已否证的三条误判（避免下一次重复诊断）

| 误判 | 否证证据 |
| --- | --- |
| 共享仓库级 git 锁竞争 | 全机 0 把锁：38 个 worktree 无 `index.lock`；`refs/` 递归 `.lock`=0；`.git/worktrees/*/*.lock`=0；无 `gc.log`/`gc.pid`；松散对象 295（远低于 auto-gc 阈值）；无 `git gc`/`repack` 进程 |
| 钩子在等 CCG 外部模型，`SKIP_CCG_GATE=1` 可解 | 采样窗口内无任何 `node.exe` 在跑 `ccg-gate.js`/`quality-rhythm-wrapper.js`；且 `SKIP_CCG_GATE` 只在 `ccg-gate.js` 内生效（L242/L334），被放大的 for 循环在钩子 shell 里无条件执行 |
| 钩子自递归 | 「嵌套的同名 `bash pre-commit` 子进程」是 `$(...)` 命令替换的 fork 继承父 argv；采样 59 次中 52 次命中该形态且深度恒为 2，无递增 |

## 5. 建议的排查顺序（不改仓库代码，均需你手动操作并逐项复测）

每一项都按同一口径自证：**改前测 10 次 `cmd.exe /c exit` 均值 → 改 → 再测 10 次均值**，两个数都记进本文档，只有均值显著下降才算该项有效。单跑一次不构成证据。

1. 实时防护排除项：把 `D:\Data\projects\`（含 `mp-worktrees\`）与 `C:\Program Files\Git\` 加入管家的**文件实时监控 + 进程启动**排除；这是最典型的 CreateProcess 回调来源。
2. 索引器排除：`Everything` 的索引范围排除 `D:\Data\projects\mp-worktrees\`——38 份 `node_modules` 与 609 个持续自增的审计 JSON 会让它长期重扫（现场累计 36.4 CPU·小时）。
3. 同步盘排除：确认极空间 `ZSpaceSync` 没有在同步 `D:\Data\projects\`；若在同步，提交过程中产生的 `tmp_obj_*`/`index.lock` 建删会被逐次拦。
4. 归因不明项：`ipf_helper` 的来源需先确认（`Get-CimInstance Win32_Process` 取 CommandLine 与父进程）再决定是否处理，不要凭名字下结论。
5. 结构性缓解（与上面四项独立）：并发会话数本身是乘数。当同时有 13 条提交链时，每条链都在制造其余链要扫描的记录。串行化「提交动作」比优化单次提交更有效。

## 6. 测量污染：本调查自己踩过并纠正的坑（供下一个读者复用）

- **探针自己会改变被测量。** 首版诊断脚本对 38 个 worktree 做递归 `Get-ChildItem -Recurse -Force`，单进程涨到 **7,957 MB**，于是报出「内存 98.5% 已用 / 剩 480 MB」和「powershell 占 1.09 核居 CPU 榜首」——**那个内存告急是探针造成的，不是环境**。杀掉自己的探针后真值是 74.2% / 8.4 GB 空闲。表中 `ls-files`/`diff --quiet` 的读数也受此污染，故给出区间而非单值。
- **判结构要先确认扫描器没把目标当二进制**：本仓历史文档含 NUL，`grep`/`rg` 默认静默跳过；凡「扫到 0」当判据一律 `-a`。
- **`git -C /d/...` 在设了 `MSYS_NO_PATHCONV` 后找不到目录**（原生 git.exe 把 POSIX 路径按 Windows 解读），必须写盘符路径 `D:/...`；同一条变量还会把 `git show origin/main:<path>` 改成 `origin\main;<path>`。
- **假 0 的经典成因是探针写法与被测命令语义不匹配**：本调查中 `git ls-tree -r --name-only origin/main -- '.ccg/reviews/*.json'` 返回 0，而实际有 609 个——正解是先全量列名再 `grep '\.json$'` 收口。
- **终止进程时筛选模式会匹配到自己**：写 `Where-Object { $_.CommandLine -match 'hookproto' }` 的杀手脚本，其自身命令行就含该串，结果把自己杀了。判据须用运行期拼装的模式或按 PID 白名单，并核完整进程树。

## 7. 复测更正（2026-10-16，风暴排空后重取）

本文初稿把「单次进程创建 ~1 秒」当成本机前提来写。这个读数**错了口径**，不是读错了数：

| 状态 | `cmd.exe /c exit` | `git --version`（原生） | 本仓 `git rev-parse HEAD` | 现场并发 |
| --- | --- | --- | --- | --- |
| 拥堵现场（13 条提交链在跑） | **1,175 ms** | 699 ms | 774 ms | git.exe 18.2 个/秒 |
| 风暴排空后（`gitexe=4 / hookbash=2`） | **53 ms** | 84 ms | 136 ms | 近乎无 |

两组都是同机、同一套防护与索引器在场，只差「有多少进程在被同时创建」这一维 ⇒ 差 **22 倍**。
结论修订为三条：
1. **「~1 秒/进程」是并发放大后的读数**，不是机器常数；引用它必须连着「当时有 13 条提交链在跑」一起写。
2. 因此 §3 表里的在场组件（实时防护 / Everything / 同步盘 / `ipf_helper`）从「疑似元凶」降级为**候选放大器**：
   它们排空后依旧在场，而成本回落了 —— 这一条本身就是对「AV 是元凶」的反证，除非有人做单变量停用实验。
3. **回归锁因此只数 git 调用条数，不数墙钟**。条数与负载无关；用墙钟当判据会随拥堵度自己弹，
   同一条实现今天绿明天红，最后只能靠放宽阈值消化 —— 那是本仓点名的「相对基线代替绝对判据」的反面教材。

## 8. 与仓库侧修复的关系

`openspec/changes/fix-precommit-reviews-spawn-storm/` 只解除「提交耗时随审计记录数线性增长」这一耦合（约 1,218 次进程创建 → 常数次）。**本文 §2 的 ~1 秒/进程 不在其修复范围内，仍为未闭合前提。** 若本 PR 落地后再次出现「多会话共同变慢」，先复跑 §2 的 `cmd.exe /c exit` 均值：若它仍 ≈1 秒，问题在机器；若它正常而提交仍慢，才需要回到仓库找新的 O(N) 形态。
