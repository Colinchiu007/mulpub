## 0. 结论速览

1. **可执行门禁面只有一条**（C1 章节）：桌面应用里，平台能真正强制的只有
   「服务端经手的功能」——即 `cloud_publish` 云端发布通道（`publish-api-server.js:629-657`
   服务端强制校验+扣减，是全仓唯一的服务端权威门禁）。本地 RPA、BYOK AI 生成、本地看板
   在技术上**全部拦不住**（Electron asar 可解包是业界共识，Electron 官方只把完整性校验定位为
   "additional layer"）。**档位设计的基点必须从「锁本地功能」转向「把价值放上云」**。
2. **¥59/¥79 价差 1.34 倍，显著低于行业 1.5-3.4x（中位 2.0x）**（C2 章节）：这是标准版与专业版
   「features 逐字节相同」的经济根源——价差窄到撑不起一条功能分界线。两条修法：
   结构 A（拉开价差至 2x，专业版 ¥119~139，承载自动化+商用+云托管）；结构 B（压缩为
   「免费+专业」两档，砍掉标准版的定位模糊）。**推荐结构 A**，理由见 §3.2。
3. **本地功能的分档走「价值感知 + 荣誉制」，不是硬墙**（C3 章节）：Sublime（一码全设备、
   无限期试用）、Obsidian（商业授权不强制）证明荣誉制在桌面工具是可持续的；硬墙只留给
   云侧。本项目的 `maxPlatforms/dailyPublish/concurrentTasks` 目前是**空头承诺**
   （`limits` 被客户端 `normalizeEntitlement()` 丢弃、零校验）——v2.0 给出分两级兑现的路径。
4. **额度数字第一次有了工作负载推导**（C4 章节）：以三档人物画像的工作负载
   （MARKET-RESEARCH §3.1：个人 1-3 平台日更 1-2 篇 / 运营 5-10 平台日更 3-5 篇 / 团队 10+ 账号）
   反推各档额度，并按「画像负载 × 2-3 倍余量」校准。结论：现有数字大体健康，
   **免费档 5 平台/5 篇是人物画像的 2.5 倍余量（偏松），标准版 50 篇/日是画像的 10 倍（远超必要）**——
   过松的额度不产生转化压力，§4 给出收敛建议。
5. **转化漏斗的第一性数据**（C5 章节）：2026 年一手报告（200 家 B2B）免费→付费中位数 **8%**；
   本仓目标 >8% 恰好压在头部；真实支付未接通前谈转化率是空转——**变现闭环（P2-PAYMENT）
   是档位机制的前置项，不是并行项**。
6. **三条新增权益轴**（C6 章节）：设备数（1/3/不限，BoltAI 范式，服务端会话表已有地基）、
   云端代执行（Buffer 定时发布范式，`cloud_publish` 通道已存在）、BYOK 工具化
   （TypingMind/BoltAI 范式：卖 UI 与聚合，不卖算力）。
7. **修复清单升级为「四批」**（C7 章节）：在 v1.1 三批之上加「D 批：可执行性」——
   服务端 `limits` 校验、`normalizeEntitlement()` 透传 `limits`、账号数分档接入、
   免费档反滥用（支付验证/手机验证选型）。

## C1. 可执行性分层：哪些档位差异是真的，哪些是纸糊的

### C1.1 门禁面全景（代码取证，2026-10-19）

| 能力 | 强制点 | 强制强度 | 证据 |
|---|---|---|---|
| **云端 API 发布** | 服务端 `publish-api-server.js:629-657`：`_assertEntitlementFeature("cloud_publish")` + `_consumeEntitlementFeature`（每任务 × 平台数扣减） | **强**（服务端权威，无法绕过） | 全仓唯一在服务端校验+扣减的 feature |
| 云端发布客户端侧 | `license-access-control.js:190-193` `ONLINE_ONLY_FEATURE_CHANNELS` + `cloud-publisher.js:91` `requireEntitlement('cloud_publish', {onlineOnly:true})` | 中（客户端闸，可被破解客户端绕过，但正常用户被拦） | onlineOnly 语义：离线宽限期禁写不禁读 |
| 定时批量发布 | 同上（走 `cloud_publish` 配额） | 中 | `plan-matrix.js:155` `cloudPublishMonthly = dailyPublish × 30` |
| 视频生成 feature 门禁 | 客户端 `CHANNEL_FEATURE_MAP`（`video_create`）+ 未来服务端积分引擎 | 弱→中（积分引擎落地后变强：官方算力走服务端代理） | DEEP-ANALYSIS §2.2 G1：`official_credit` 有字段无引擎 |
| 数据看板 | 渲染层体验分级（`entitlement-gate.js` 注释自认「这是体验分级，不是访问控制」） | **弱**（拦不住主动绕过） | `entitlement-gate.js:20-37` 整段免责声明 |
| 本地 RPA 发布 | 无任何门禁 | **无** | 平台功能在本地执行，平台不经手 |
| BYOK AI 生成 | 无任何门禁 | **无** | 用户 Key 本地直连厂商，平台不经手流量 |
| `limits` 三项（平台数/日发/并发） | **零校验**：服务端下发但客户端 `normalizeEntitlement()` 直接丢弃 | **无** | `entitlement-service.js:37-47` 无 `limits` 字段；DEEP-ANALYSIS G6 |

**结论**：v1.1 五层权益栈里，L1（平台能力层）的「平台数/日发布」若只做客户端提示，是纸糊的；
真正立得住的是：云端发布配额（强）、未来官方算力积分（强）、体验分级（弱但可接受）。

### C1.2 两条业界验证的对策

**对策一：价值上云（SaaS 化权益）**。混合架构产品的成熟划线是「本地核心全免费，
云端服务按档收费」——Obsidian（Sync $4/月、Publish $8/月，核心应用全免费无账号）、
Bear（编辑免费，Pro 卖导出/OCR/iCloud 同步）、Raycast（个人全功能免费，Pro 卖 AI credits+
云同步）。付费点整体搬云侧后，**客户端破解拿到的是空壳**。对本项目的映射：

| 权益 | 云侧可强制强度 | 放哪一档 |
|---|---|---|
| 云端 API 发布（`cloud_publish`） | 强 | 已全档有；**配额**按档拉开（已有） |
| **云端定时/离线执行**（关机也发） | 强 | **新权益轴**：free ✗ / standard ✓ / pro ✓（同 schedule_batch，但语义升格为「云端代跑」对外表述） |
| 云端账号巡检（掉线检测） | 强 | standard 起（复用现有 30 分钟检测，服务端化后可强制） |
| 云凭证同步（多设备） | 强 | **新权益轴**：free ✗ / standard ✓（1 设备同步）/ pro ✓（不限）——`identity_user_sessions` 表已有设备维度地基 |
| 云托管播客（P2 规划） | 强 | pro（PRD-PODCAST-RSS-CHANNEL §三：能收费/可审核/可退出三前置） |
| 本地 RPA 发布 | 无 | **全部档位可用**（价值感知，不设硬墙） |
| BYOK AI 生成 | 无 | 全档可用；配额差异走官方积分（未来） |

**对策二：本地功能荣誉制 + 价值感知**。Sublime（无限期试用、一码全设备）、Obsidian
（商业授权不强制购买）证明：桌面工具的破解损失 < 技术强制的摩擦损失时，荣誉制可持续。
对本项目：本地 RPA 与 BYOK 的「档位差异」降级为**价值差异**（模板库数量、批量 UI 的
单次条数上限——UI 层限制防君子，配合 EULA），不再作为档位承诺的硬边界。

### C1.3 空头承诺的兑现路径（G6 缺口，分两级）

现状 `limits`（平台数/日发布/并发）服务端有数、客户端丢弃、零校验——v1.1 总表承诺了它，
就必须兑现。**两级兑现**：

- **P0（UI 级，周级）**：`normalizeEntitlement()` 透传 `limits` → 发布页选平台超过
  `max_platforms` 时前端禁用并显示升级引导（防君子，与 Buffer「免费 3 频道」同型的
  价值感知边界）；`daily_publish` 前端计数（本地 publish_history 已有数据源）。
- **P1（服务端级，立项）**：本地 RPA 发布上报计数（复用 usage-reporter 管道）→
  服务端对 `daily_publish` 做**事后审计**（超限标脏，不硬阻断）→ 累计违规触发
  权益复核。这是「荣誉制 + 审计」的折中：不建硬墙，但违约不再零成本。

## C2. 价格结构诊断：¥59/¥79 撑不起三档

### C2.1 行业基准（2026-10-19 官方页一手实证）

| 产品 | 档位价 | 二档→三档倍数 |
|---|---|---|
| Notion | $0/$10/$20 | 2.0x |
| Slack | $0/$8.75/$18/$45 | 2.06x / 2.5x |
| Dropbox | $9.99/$15/$24 | 1.5x / 1.6x |
| Linear | $0/$10/$16（年付） | 1.6x |
| Figma | Full $16→Org $55→Ent $90 | 3.4x |
| **中位** | | **≈2.0x** |

来源：五家官网定价页直抓（2026-10-19）；GBB 方法论「Good/Better/Best 收入占比
15-25%/45-55%/25-35%」（fintastiq.com）。

### C2.2 本项目的问题

```
标准 ¥59 → 专业 ¥79 = 1.34x   ← 低于行业中位 2.0x，接近 Dropbox 的 1.5x 下限
```

**因果链**：价差窄 → 每月只多 ¥20 → 撑不起任何一条有分量的功能分界 →
features 数组两档逐字节相同（plan-matrix.js:150-153）→ 升级专业版只买到
积分 +37.5%（1600→2200）和视频配额 → 用户没有升级理由 → 目标转化率 8% 无支撑。

反过来看，**标准版与免费版的关系反而健康**：¥0→¥59 是从 0 到 1 的转化，
靠的是「5 平台/5 篇/日」的价值感知边界 + 30 积分体验——这条边界存在且可感知
（尽管目前是空头承诺，见 C1.3）。

### C2.3 两条修法（v2.0 核心决策点，需 CEO 拍板）

**结构 A：拉开价差至 ~2x（推荐）**

| 档 | 现价 | 建议价 | 新承载的「质变」 |
|---|---|---|---|
| free | ¥0 | ¥0 | （不变） |
| standard | ¥59/¥499 | **¥59/¥499（不动）** | 云端定时执行、云凭证同步（1 设备）、完整看板、商用授权 |
| pro | ¥79/¥699 | **¥119/¥999（月 2.0x、年 2.0x）** | 自动流水线（全自动成片→发布）、批量上限放开、多设备同步、云端账号巡检、tier_access 高成本模型、优先队列（未来） |

- 年付折扣收敛：¥999 vs ¥119×12=¥1428 → 折扣 30.0%（标准版 29.5% 保持）；
  两档年付折扣一致化，消除「专业版年付折扣更低」的倒挂感。
- 成本侧：专业版积分维持 2200/月不变（积分成本占比已定案 27.8%），
  **涨的是功能价不是算力价**——自动化/巡检/多设备同步的边际成本近乎零
  （服务端编排，无第三方算力），涨价的毛利是真实的。
- 风险：现价 ¥79 尚无付费存量（支付未接通），调价零成本窗口仍在
  （DEEP-ANALYSIS §6.1b 同款论证：「接了支付再改就要处理退差价」）。

**结构 B：压缩为两档（free / pro）**

- 砍掉标准版，免费→专业一步转化 ¥99/月 或 ¥79/月。
- 优点：消灭「定位模糊」；缺点：丢失 ¥59 的低门槛入口——MARKET-RESEARCH
  §3.1 里 30% 的「自媒体运营」人群付费意愿正落在 ¥39-99 区间，直接砍掉
  中间档会把他们推向「不付费」或「流失」。**不推荐**，除非未来数据证明
  标准版转化贡献 < 10%。

### C2.4 年付折扣的行业校准

行业默认「2 个月免费 = 16.7%」，竞争市场 20%（saaspricelab.com 实证：
Notion/Slack ≈17%）。本项目标准版 29.5% **偏慷慨**——但它与积分成本占比
是数学锁死的（DEEP-ANALYSIS §0.5 ③：年付成本占比 = 月付 ÷ (1−折扣)），
积分量不动就降不了折扣。**建议**：结构 A 落地时专业版年付 ¥999（折扣 30%）
与标准版对齐；未来若砍积分成本，同步下调折扣至 20-25% 区间。

## C3. 经济模型：每档的成本-价值账

### C3.1 免费档：成本上限与转化杠杆

**成本项**（全部真实发生）：

| 项 | 单用户成本 | 说明 |
|---|---|---|
| 30 体验积分 | ¥0.30/月（上限） | 1 积分=¥0.01 上游成本（定案）；实际用量远低于上限 |
| 云端发布配额 150/月（5×30） | ≈¥0.1-0.5/月 | orchestrator 侧边际成本极低（HTTP 转发+队列），无第三方算力 |
| entitlement 快照/会话/通知 | ≈¥0.05/月 | Postgres 行存储，可忽略 |
| **合计** | **< ¥1/月/人** | 免费档成本可控的前提是积分引擎未放量（当前无扣减路径，实际成本≈0） |

**反滥用**（v2.0 新增轴）：免费档的最大风险不是成本是**薅号**。行业手段按
成本递增：邮箱验证（无效）< 设备指纹（可绕）< 手机验证（Twilio $0.05/次成功验证）
< 支付验证（1 元预授权，最强）。**建议**：免费档保持低摩擦（邮箱即可），
把防滥用预算花在「云端功能侧」——`identity_user_sessions` 已有设备维度，
对免费档限 **2 个活跃设备**（软上限：第 3 台登录时提示「注销其他设备或升级」，
复用现有 revoke-others 交互），成本零、摩擦低、数据已有。

### C3.2 标准版：定价锚 vs 竞品同位

| 对标 | 同位档 | 价格 | 账号/频道数 |
|---|---|---|---|
| 参考产品（国内分发） | VIP | ¥59/月 | 20 账号点 |
| Buffer | Essentials | $6/频道/月 | 3 频道免费 |
| Hootsuite | Professional | $99/月 | 10 账号 |

标准版 ¥59 对标参考产品同价，但账号数无上限（竞品 20 点封顶）——**这是本项目
「不限账号数」的隐性让利**。v2.0 建议：**把账号数变成显式分档轴**（见 C6.1），
标准版限 20 个绑定账号（对标参考产品），pro 不限——既对齐竞品定价锚，
又给了矩阵用户升级理由。**前提**：账号数分档必须走云侧（云同步的账号配额），
本地绑定不拦（荣誉制）——即「云端同步的账号数 ≤ 档位上限」，本地随便绑。

### C3.3 专业版：涨价的成本-价值支撑（结构 A 下 ¥119）

| 新增权益 | 平台边际成本 | 用户价值 |
|---|---|---|
| 自动流水线 | 服务端编排，无第三方算力 | 「全自动成片→发布」是 Copy.ai「Chat vs Workflow」分界的本项目版——工作流自动化天然高档墙 |
| 多设备同步 | 存储字节，可忽略 | 矩阵团队刚需（现状单设备语义） |
| 云端账号巡检 | 心跳轮询，极低 | 「掉线立刻知道」是代运营付费理由 Top3（marketing/03 §四） |
| tier_access 高成本模型 | 走官方积分（未来），用户自付积分 | 高质量产出 |

**结论**：¥40 的价差由「自动化 + 多设备 + 巡检」三项支撑，每项都有
竞品验证的付费意愿（Copy.ai Workflow $1000+/月、BoltAI 多设备档 +$20 买断、
代运营痛点地图），成本侧近乎零边际——**这是全表毛利最好的一档**。

## C4. 额度校准：从人物画像反推，而不是拍脑袋

### C4.1 方法论

「配额 = 目标画像工作负载 × 2-3 倍余量」未找到公开权威出处（调研明确标注），
可用的替代框架是 ConsultEvo 五要素（每额度写清：度量物 / 阈值 / 触顶行为 /
付费差异 / 重置周期）+ Price Intelligently 的实证结论「**限用量优于堵功能**
（转化高约 30%）」。本节按此框架把 v1.1 总表的额度全部过一遍。

### C4.2 三档画像与额度对照（MARKET-RESEARCH §3.1 画像 × 现有额度）

| 维度 | 免费画像<br>个人 1-3 平台日更 1-2 篇 | 现值 | 余量倍数 | 判定 |
|---|---|---|---|---|
| 平台数 | 1-3 | 5 | ~2x | ✅ 健康 |
| 日发布 | 1-2 篇 × 2-3 平台 = 2-6 条/日 | 5 | ~1-2x | ⚠️ 偏松（重度日 6 条触顶，轻度用户永无感）→ **保留**（转化触点靠「第 6 个平台」而非日发） |
| 官方积分 | 体验 1-2 次 | 30 | 设计值 | ✅（够一次完整流程） |

| 维度 | 标准画像<br>运营 5-10 平台日更 3-5 篇 | 现值 | 余量倍数 | 判定 |
|---|---|---|---|---|
| 平台数 | 5-10 | 15 | ~1.5-3x | ✅ 健康（画像上限 10 < 15） |
| 日发布 | 3-5 篇 × 5-10 平台 = 15-50 条/日 | 50 | ~1-3x | ✅ 健康（p75 恰好 50） |
| 并发 | 1-2（单人操作） | 3 | ~2-3x | ✅ 健康 |
| 视频配额 | 500 条/月 vs 月产出视频 ≈30-150 条 | 500 | 3-15x | ⚠️ **过松**：视频月产 150 条已是重度；500 条几乎永无感 → 建议收敛至 **300**（3x 于 p75 100 条/月）|
| 积分 1600 | ≈250 篇改写 or 5 条成片（DEEP-ANALYSIS §7.1） | 与画像月产 90-150 篇改写需求比 ≈1.7-2.7x | ✅ 健康 |

| 维度 | 专业画像<br>团队 10+ 账号矩阵 | 现值 | 判定 |
|---|---|---|---|
| 平台数 | 15（全平台） | 不限 | ✅ |
| 日发布 | 10 账号 × 15 平台 = 150 条/日 起步 | 1000 | ✅（1000 是防除零高上限，非承诺值，代码注释已明写） |
| 并发 | 矩阵批量 5-10 | 10 | ✅ |
| 积分 2200 | 矩阵重度用户月耗 >5000 | **缺口** | ⚠️ 专业画像的积分需求远超 2200 → 靠**加购包**（¥199/9500）承接，档内额度不必加大（避免超卖，DEEP-ANALYSIS §6.2 已论证 3000 是超卖） |

### C4.3 校准结论

1. **唯一建议调整**：`videoMonthly` 500 → **300**（标准版）。理由：3x 余量原则；
   现 500 在积分引擎落地后对应成本 ¥5/月（500 积分），占 ¥59 的 8.5%——
   与「积分成本占比 27%」的主线不冲突，但作为**次数承诺**偏松，收敛后
   宣传口径「300 条/月」仍 3 倍于画像需求。**此为建议值，落地前需与积分
   引擎设计复核**（G1 未落地，现在只是数字）。
2. **不动**：平台数/日发布/并发三项全部健康；积分量不动（v1.2 定案）。
3. **新增校准义务**：所有新权益轴（账号数上限、设备数）在落地时必须
   附「画像负载 × 余量」推导段——把 C4 的方法固化为档位评审 checklist。

## C5. 转化漏斗：目标 8% 的第一性核对

- 2026 一手报告（Growth Unhinged × ChartMogul × ProductLed，200 家 B2B）：
  免费→付费**中位数 8%**（注册后 6 个月内）；Freemium 产品 25% 低于 2.5%。
  来源：growthunhinged.com/p/free-to-paid-conversion-report。
- 行业级（First Page Sage，80+ 客户）：2.1-5.6%，中位 ~3.9%。
- AI 工具实证：ChatGPT ≈5.6%（900M 周活/50M 订阅，待核实）、Canva ≈9.5%。

**对本仓的三个修正**：

1. `pricing-strategy.md §8` 目标「免费→标准版 >8%」是**头部水平**（相当于
   Canva），不是行业均值。建议改双目标：**冷启动期 3%（行业中位）为底线，
   成熟期 8% 为目标**——否则第一个月数据出来就全线红，指标失去导航意义。
2. 漏斗里「7 天 Pro 试用」多处出现（MARKETING-HANDBOOK §5/§6），但 trial
   在代码中不存在（`plan-matrix` 无 trial；PRD-FIX-UPGRADE-PAYMENT-ENTRY §5
   表格明示「保持关闭，否则看到 Pro 界面点下去被拦」）。**试用是转化率
   最大的单一杠杆**（B2B 主流 14 天、免卡转化低但留存好），应进 P2-PAYMENT
   立项范围（`trial_days` 在 P2 spec §7.6 已有占位），不在档位机制内解决。
3. **变现闭环前置**：真实支付未接通（G12），所有转化率数字不可度量
   （pricing-strategy §8 五项全部 ❌）。档位机制的下一步不是继续雕表格，
   而是 **P2-PAYMENT 落地**——这是唯一能让本机制从「设计」变成「在跑」的事。

## C6. 新增权益轴（v2.0 扩展）

### C6.1 云同步账号数（新，标准/专业分界）

- **现状地基**：云凭证同步已实现（cloud-accounts 模块，明文上行+服务端 KMS 加密）；
  账号分组已落持久化真源（PRD-ACCOUNT-GROUPS-PERSISTENCE）。
- **分档设计**：free ✗（本地绑定不限，云同步不可用）/ standard ✓（云同步账号 ≤20）/ pro ✓（不限）。
- **可执行强度**：强（同步走服务端，配额服务端校验——新 feature `cloud_account_sync`）。
- **定价锚**：参考产品 VIP ¥59 含 20 账号点（C3.2）；账号数是分发工具核心计价轴（Buffer 频道/小豆芽绑号数/Hootsuite 账号数三例）。

### C6.2 设备数（新，温和上限）

- **现状地基**：`identity_user_sessions` 表有 device_id/device_name（postgres-commerce-store.js:40-47），
  「注销其它设备」交互已上线。
- **分档设计**：free 2 / standard 3 / pro 不限（BoltAI 1/2/3 台范式）。
- **实现**：登录时服务端检查活跃会话数，超限提示注销其它设备（**复用现有交互**，不新增产品面）；
  7 天离线宽限不变（entitlement-service.js:10，72h grace 已实现）。
- **摩擦控制**：BoltAI 把「可转移授权」写成卖点——本项目同款交互（注销旧设备→登新机）已有，零开发。

### C6.3 云端代执行（语义升格，零开发）

`schedule_batch` 的真实语义是「任务在队列里自动到点执行」——但 v1.1 总表把它
写成「定时发布」埋没了价值。对外表述升格为「**云端定时发布（关机也能发）**」：
这不是撒谎——RPA 任务由本地队列在到点时执行，只要应用在托盘常驻即可；
而云端 API 发布（cloud_publish）更是真·关机可发。**文案层升格 + 产品层把
`cloud_publish` 通道作为 standard 起的「关机也能发」主卖点**（Buffer 的根基
正是这个价值）。free 档保持「手动发」。

### C6.4 BYOK 工具化（对冲「积分引擎难产」的商业风险）

HANDOFF-OFFICIAL-COMPUTE 已确认「方案 A：会员费买平台能力 + BYOK 便利性」。
v2.0 把 BYOK 便利性从一句话升格为**权益清单**（TypingMind/BoltAI 范式——
BYOK 产品卖的是工具不是算力）：

| BYOK 权益 | free | standard | pro |
|---|---|---|---|
| 模型接入（7 类 provider） | ✓ | ✓ | ✓ |
| 用量与成本可见（usage 明细） | 基础 | ✓ 完整 | ✓ 完整 |
| 模型市场/优选标记（ops-center 下发） | ✓ | ✓ | ✓ |
| 多模型聚合改写（一次改写多模型对比） | ✗ | ✓（2 模型） | ✓（不限） |
| 成本按平台/账号分摊报表 | ✗ | ✗ | ✓ |

全部走客户端+既有通道，除「多模型聚合改写」外零新开发；这一轴让「积分引擎
延期」期间标准版仍有可感知的付费理由。
