## 1. 核心结论：两个 exe 的真实性质

这是本轮最重要的发现——**直接决定了"原生分析"该做到多深**。

| | 融媒宝 WEMedia.exe | 参考产品4.0.exe |
|---|---|---|
| 大小 | 17.3 MB（18,114,584 B） | 196.4 MB（205,909,632 B） |
| PE 格式 | **PE32（32 位）** | PE32+（64 位） |
| Machine | `0x014C` = **I386** | `0x8664` = x86-64 |
| Section 数 | 5 | **14** |
| `.text` 段 | **12.4 MB** | **165.5 MB** |
| `.rdata` | 2.1 MB | 33.0 MB |
| 特殊段 | — | **`LZMADEC`(4.6KB) / `malloc_h` / `prot` / `CPADinfo` / `_RDATA`** |
| ImageBase | `0x00400000` | `0x140000000` |
| EntryPoint | RVA `0x005D5B2A` → VA `0x9D5B2A` | RVA `0x04D7AF80` |
| 导入目录 | **不可读**（25 个描述符，名称 RVA 全空） | **不可读**（16 个描述符，名称 RVA 全空） |
| 加壳判定 | **是** | **是（LZMA 自解压）** |
| .NET 托管 | **否**（`cli-directory-absent`，无 CLI 数据目录） | 否（超 128MB 快照预算，无法托管检查） |

### 1.1 参考产品 exe = LZMA 自解压壳

**证据链**：

1. 段名 `LZMADEC`（LZMA 解码器，4,593 B）+ `malloc_h` + `prot` + `CPADinfo` — 典型自解压壳结构
2. `.text` 165 MB / `.rdata` 33 MB — 远超 Electron 运行时的实际需求
3. 全文件 ASCII 扫描命中 `LZMA` 签名
4. 导入目录不可读
5. 同目录有 `resources/app.asar`（9.5 MB，已完整分析）— 业务代码在 asar 里，不在 exe 里

**结论**：196 MB 的 exe 里绝大部分是**压缩后的 Electron 运行时**。反编译它的壳没有业务价值——**真正的业务代码已在 asar 分析中完整覆盖**（566 个 webpack 模块、285 个类[含第三方库]、47 个 IPC 通道）。

### 1.2 融媒宝 exe = 加壳的 32 位原生程序

**证据链**：

1. **导入目录不可读**：ImportDir RVA `0xdd0ef8` size=520，解析出 25 个描述符但**所有 DLL 名 RVA 指向的位置都没有 ASCII 字符串**——导入表被加密/重定位
2. **UTF-16 中文串全部乱码**：扫出 51,555 个含中文的 UTF-16 串，但内容是 `桔獩瀠潲牧浡挠湡潮`、`懷爮慤慴` 这类乱码——字符串表被混淆编码
3. 但 **ASCII 串完全可读**（URL、API 路径、库名都清晰）— 说明是**部分加密**（仅加密 Unicode 字符串表）

**这是一个关键的技术判断**：融媒宝只混淆了 Unicode 字符串（可能是为了防中文界面文案被直接提取），ASCII 部分未加密。所以：
- ✅ 能读到：URL、API 路径、DLL 名、英文标识符
- ❌ 读不到：中文界面文案、中文提示信息

## 2. 融媒宝技术栈确认（来自字符串特征）

命中 30/55 个特征，技术栈完全清晰：

### 2.1 多 UI 框架混用

| 框架 | 证据 | 用途判断 |
|---|---|---|
| **DuiLib** | `DuiLib.dll`（0.5 MB，独立文件） | 原生窗口框架（主界面） |
| **Qt5** | `Qt5` ASCII 串 | 部分原生模块 |
| **CEF** | `libcef.dll`（148.8 MB） | 内嵌网页（Asset/*.html） |
| **Element UI** | `Asset/AgComment/assets/js/element-ui.js`（649 KB） | CEF 内前端（Vue 2） |
| **Element Plus** | `Asset/dist/assets/js/element-plus@2.9.6.min.js`（980 KB） | CEF 内前端（Vue 3） |

**这是一个"混合架构"**：原生 DuiLib/Qt 做壳，CEF 加载 HTML 做业务界面，同一产品内混用 Vue2 和 Vue3。

### 2.2 音视频栈

| 组件 | 证据 |
|---|---|
| **VLC** | `libvlc.dll` + `libvlccore.dll`（2.6 MB）+ `plugins/` 下 100+ 个 VLC 插件 DLL |
| **FFmpeg** | `avcodec`（UTF-16）+ `ffmpeg` + **`download.17van.com/plugin/ffmpeg_7_1.zip`**（运行时下载） |
| **MediaInfo** | `MediaInfo.dll`（4.4 MB）+ `MediaTaskMgr.dll`（10 MB） |

**FFmpeg 按需下载**这个设计值得注意：`ffmpeg_7_1.zip` 和 `peiyin/ffmpeg.zip`（配音用）都是运行时从 CDN 拉取，不打包进安装包——减小了安装体积。

### 2.3 网络栈

`libcurl.dll` + `libeay32.dll`（OpenSSL 1.0.x）+ `ssleay32.dll` + `libssh2.dll` + `zlib.dll` — 经典 OpenSSL 1.0.x + curl + ssh2 组合。**注意用的是 OpenSSL 1.0.x（libeay32/ssleay32 命名）**，这是较老的版本。

### 2.4 其他

- `sqlite3`（ASCII+UTF-16）— 本地数据库
- `MediaInfo.dll` — 媒体元数据
- 翻译能力：`fanyi.baidu.com/v2transapi` + `translate.google.cn` — **接了两家翻译 API**
- OCR：`ocr`（UTF-16）
- TTS/ASR：`tts` / `asr`

## 4. Ghidra 原生反编译的可行性评估

### 4.1 尝试记录

| 尝试 | 参数 | 结果 |
|---|---|---|
| 1 | `rea analyze WEMedia.exe --provider ghidra`（默认 330 s） | ❌ `provider_timeout` |
| 2 | `REA_GHIDRA_STARTUP_TIMEOUT_MS=1800000`（30 min） | ❌ `provider_timeout` |
| 3 | `REA_GHIDRA_STARTUP_TIMEOUT_MS=3600000`（60 min） | ⏳ 运行 30+ 分钟，Ghidra 进程持续消耗 CPU（2439 s CPU / 1.35 GB 内存），未卡死但未完成 |
| 4 | `rea decompile WEMedia.exe 0x9D5B2A`（仅入口，40 min 超时） | ⏳ 仍在运行 |

### 4.2 根因

`.text` 段 **12.4 MB**（32 位 x86 代码）。Ghidra 的完整 auto-analysis 是 O(代码量) 的，12 MB 机器码需要分析数百万条指令。且**加壳会显著拖慢分析**（大量间接跳转、自修改代码、混淆控制流，导致分析器反复重试）。

### 4.3 结论与建议

**结论：融媒宝主程序 exe 不适合做 Ghidra 全量分析，但换目标即可成功。**

**✅ 已验证的可行路径（第 3 轮实测成功）**：改攻 `MediaTaskMgr.dll`（10 MB，媒体任务引擎）。

```powershell
rea analyze "D:\Program Files (x86)\融媒宝\MediaTaskMgr.dll" --provider ghidra
# → 成功：66,199 个函数 / 13,120 个字符串 / 8 个段
```

结果远超预期：还原出**任务引擎完整类层次**（30+ 任务类）、**15 种 ffmpeg 操作**、
**1,338 个平台 API 端点**、**TTS 三家供应商**。详见 [原生层分析报告.md](原生层分析报告.md)。

**为什么 WEMedia.exe 不行但 DLL 行**：

| | WEMedia.exe | MediaTaskMgr.dll |
|---|---|---|
| `.text` 段 | **12.4 MB** | 8.2 MB |
| 加壳 | ✅ 加壳（导入表不可读 + UTF-16 串乱码）| ❌ 未见加壳 |
| 保护强度 | 高（分析器反复重试）| 低 |
| Ghidra 结果 | ❌ 三档超时（330 s / 30 min / 60 min）| ✅ 成功 |
| 业务价值 | 低（窗口/IO/调度）| **高（任务/API/上传/ffmpeg）** |

**不建议继续投入 WEMedia.exe**，理由：

1. **业务逻辑不在 exe 里** — 融媒宝的业务界面全在 `Asset/*.html` + JS 里（266 个 JS，已完整分析）
2. **加壳导致反编译质量差** — 即使跑完，看到的也是壳代码 + 混淆控制流
3. **时间成本不成比例** — 30+ 分钟换来看壳代码
4. **同类信息已在 DLL 中获取** — 任务/API/上传/ffmpeg 逻辑都在 `MediaTaskMgr.dll` 里

**若将来仍需 exe**，备选路径：

```powershell
# 方案 A：用 snapshot 分批导入，避免重复全量分析
rea decompile <exe> <addr> --provider ghidra --snapshot "D:\analysis\wemedia.json"

# 方案 B：直接用 Ghidra GUI 打开（可视化，可控分析范围）
#   GHIDRA_INSTALL_DIR 已配置；手动打开后只分析 EntryPoint 附近
```

## 5. 本轮净增知识点

相比第 1 轮报告，新增：

1. **参考产品 exe 是 LZMA 自解压壳**（段名 `LZMADEC`/`malloc_h`/`prot`/`CPADinfo` 是铁证）— 反编译 exe 无价值，业务在 asar
2. **融媒宝 exe 是加壳 32 位原生程序** — 导入表不可读 + UTF-16 字符串全乱码，但 ASCII 可读（部分加密）
3. **融媒宝完整后端 API 架构**（59 个 URL）— 包括原创度检测、Word 转 HTML、FFmpeg 运行时下载、词语替换双接口
4. **融媒宝是多 UI 框架混合架构**（DuiLib + Qt5 + CEF + Vue2/Vue3 混用）
5. **融媒宝上传用七牛云**，翻译接百度+谷歌两家
6. **Ghidra 对 12 MB 加壳 32 位代码不可行**（实测 30+ 分钟未完成）

## 6. 对项目的最终建议（增量）

在第 1 轮报告基础上，补充三条：

### 6.1 原创度检测考虑服务端化

融媒宝把原创度检测做成 `api.17van.com/other/getOriCheck` 服务端 API。本项目 `content-quality-gate.js` 是本地规则引擎。

**建议**：若原创度算法需要持续迭代（词库、模型更新），**服务端 API + 本地兜底**的双层方案更优。本地兜底保证离线可用（符合本项目定位）。

### 6.2 平台分类映射表支持远程更新

融媒宝 `download.17van.com/plugin/media_class_set.txt?_t=` 远程下发分类配置。本项目的分类数据在 `config/platforms.yaml`（本地）。

**建议**：把**平台分类映射**（易变、与平台运营策略相关）做成可远程更新的轻量配置，本地打包默认值兜底。这比每次平台改分类都发版更灵活。

### 6.3 不要改 FFmpeg/Chromium 为按需下载

融媒宝的 FFmpeg 按需下载是为减小安装包。但本项目 AGENTS.md 明确要求"安装包自带 Chromium（~170MB），无需代理"——**离线可用是本项目的产品定位**。不要学这一点。
