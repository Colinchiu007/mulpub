# 案例：门禁判据「出路④纯回填」恒不可达 —— 双会话平行修复

> 记录时间：2026-10-13
> 性质：**工程过程复盘**（非竞品分析）。本仓（mulpub）门禁缺陷的完整生命周期。
> 涉及：PR #3473（本人，已关闭）、PR #3434 + #3478（他会话，已合并）
> 证据锚点：`scripts/check-pr-exec-record.js`、`.quality-gates.md`、`openspec/records/fix-pure-backfill-autostaged.md`（已随分支删除，内容存于 PR #3473）

---

## 0. 一句话

一条门禁判据（`check-pr-exec-record.js` 的「出路④纯回填」）**自 2026-10-12 起再也无法成立**，却**整整 7 天零信号**。根因是**两个特性相隔 7 天独立落地后互相矛盾**，而 CI 以「恒 exit 0」的 advisory 模式调用它 —— **判据死了，但没人看得见**。

最终由**两个互不知情的会话各自修复**：他会话的方案（#3434）更严格，我的方案（#3473）被关闭为冗余。

---

## 1. 缺陷是什么

`scripts/check-pr-exec-record.js` 是「PR 必须携带执行记录」的门禁。它给了四条合法出路，其中**出路④「纯回填」**的定义是：

> 变更集**全部**是既有记录/台账载体的 `M`，且至少含一篇 `openspec/records/*.md` 的 `M`

实现即：

```js
function isPureBackfillChangeSet (statuses) {
  return Array.isArray(statuses) && statuses.length > 0
    && statuses.every((e) => e.status === 'M' && CARRIER_RE.test(e.file))   // ← 全部必须是 M
    && statuses.some((e) => e.status === 'M' && RECORDS_RE.test(e.file))
}
```

**症状**：任何只改记录/台账的回填型 PR，跑 `--mode=enforce` 一律被判「本 PR 未携带执行记录」。

---

## 2. 第一性原因（QM-5 ①：git blame 溯源）

| 事件 | 提交 | 日期 |
|---|---|---|
| 出路④「纯回填」判据引入（要求变更集全部是载体的 `M`） | `e77977892`（PR #2928） | **2026-10-05** |
| pre-commit 自动 `git add` 判定记录 `.ccg/reviews/<sha>.json`（状态 **A**） | `aee1ebc9b`（PR #3396） | **2026-10-12** |

第二个特性**晚 7 天**落地，其提交信息自述为「防 `.ccg/reviews` 未跟踪堆积的**根治**」。

此后任何走 pre-commit 的 PR 都**必然**带一个 `A` 状态文件 ⇒ `every(e => e.status === 'M')` **再也无法成立**。两个 PR 各自全绿，**合起来判死了第三条出路**。

**实测影响面**：真实历史 PR 在 `--mode=enforce` 下逐笔复现 —— **#3465 / #3466 / #3470 三笔回填 PR 全部 `不通过：1 条理由`**。

---

## 3. 逃逸分析（QM-5 ②：四层全逃）

| 层 | 为什么没拦住 |
|---|---|
| **单元测试** | 判据有独立单测，但**无一条用例带 `.ccg/reviews/` 的 A 文件**；夹具全是手搓 statuses、**不经过真实钩子** ⇒ 判据在单测里恒真 |
| **CI** | `quality-gate.yml:120` 以 **`--mode=advisory`** 调用，该模式 **恒 `exit 0`** ⇒ 判据死了也不出声 |
| **端到端** | CLI e2e 构造临时 git 仓库，**不经过 pre-commit**，永远产不出那个目录 |
| **人工** | AGENTS.md 判据 4 明文要求 `--mode=enforce` 为 OK，但**没人跑过** |

**四层里没有任何一层会红。** 这不是「测试不够」，而是「**测试面与真实链路完全不相交**」。

---

## 4. 系统性漏洞（QM-5 ③）

1. **夹具与真实链路脱节** —— 钩子产物从未进入被测面。
2. **advisory 模式让死判据静默** —— 判据失效与判据通过，在 CI 上**外观完全相同**。
3. **无「新特性是否让既有判据恒不可达」的交叉检查** —— 相隔 7 天的两个 PR 各自全绿，没人问「后者是否破坏了前者」。
4. **文档判据（enforce）与实际执行（advisory）从不互校**。

---

## 5. 两条平行修复

### 5.1 我这条（PR #3473，已关闭）

```js
const AUTO_STAGED_RE = /^\.ccg\/reviews\/[^/]+\.json$/
function excludingAutoStaged (statuses) {
  return Array.isArray(statuses) ? statuses.filter((e) => !AUTO_STAGED_RE.test(String(e.file))) : statuses
}
function isPureBackfillChangeSet (statuses) {
  const relevant = excludingAutoStaged(statuses)
  return Array.isArray(relevant) && relevant.length > 0
    && relevant.every((e) => e.status === 'M' && CARRIER_RE.test(e.file))
    && relevant.some((e) => RECORDS_RE.test(e.file))
}
```

思路：**判形态前先把钩子自动产物剔除**。豁免面只开给 `.ccg/reviews/*.json`（不放 `.ccg/**`），配 5 条反向边界断言。

### 5.2 他这条（PR #3434，已合并）

```js
const AUDIT_ARTIFACT_RE = /^\.ccg\/reviews\/[0-9a-f]{40}\.json$/
function isPureBackfillChangeSet (statuses) {
  return Array.isArray(statuses) && statuses.length > 0
    && statuses.every((e) => (e.status === 'M' && CARRIER_RE.test(e.file))
                       || (e.status === 'A' && AUDIT_ARTIFACT_RE.test(e.file)))
    && statuses.some((e) => e.status === 'M' && RECORDS_RE.test(e.file))
}
```

思路：**放行**匹配白名单的 `A` 文件。

### 5.3 对照 —— 他的更严格

| | #3434（已合并） | #3473（已关闭） |
|---|---|---|
| 正则 | `/^\.ccg\/reviews\/[0-9a-f]{40}\.json$/` **精确 40 位小写 hex** | `/^\.ccg\/reviews\/[^/]+\.json$/` **宽松** |
| 短 sha / 大写 / 非 sha | **仍拒绝** | 会被放行 |
| 状态维度 | 必须 `A` | 不分状态一律剔除 |
| 专测 | 4 条（ok 35-38） | 7 断言 |

**合入我的方案等于把他刚收紧的口径又放开。** 故关闭，不自辩。

## 6. 我犯的一个错（必须记录）

**在核实「他的修复是否有效」时，我在共享根跑了 `require('./scripts/check-pr-exec-record.js')`。**

但**共享根 HEAD 落后 `origin/main`**，拿到的是**修复前的旧版**（`AUDIT_ARTIFACT_RE === undefined`）。据此我得出：

> ❌「#3478 仍 exit=1，main 的修复不完整」

**这是错的。** 改用 `origin/main` 的真实版本重测后：

```
#3476  exit=0 OK      #3478  exit=0 OK      #3432  exit=0 OK
#3466  exit=0 OK      #3465  exit=0 OK      #3470  exit=0 OK
```

**6/6 全过。** 若没发现，我会向用户报告一个**不存在的缺陷**。

**根因**：把「我手边的副本」当成「被测对象」。**修复前必须先确认取到的是目标版本**（`git rev-parse` 对账，或直接从 `origin/main` 取 blob）。

## 7. 流程教训

### 7.1 我该在开工前先搜「是否已有人在做同一修复」

我这条路径全程约 3 小时（含两次 45 分钟 CI），**最终完全作废**。

讽刺的是：**两条独立路径得出同一根因**（#2928 引入判据 → #3396 破坏它 → advisory 让死判据静默 7 天），这本身是该归因可靠性的**强证据** —— 但**重复劳动本可避免**。

**可执行的改法**：开工前跑 `git log origin/main --since=<7天> --grep=<关键词>` + 搜 `openspec/records/` 是否已有同题记录。

### 7.2 冲突是信使，不是障碍

这次发现平行修复，**不是因为我去找它**，而是因为**最终 rebase 时 `scripts/check-pr-exec-record.js` 出现冲突** —— 我原本的目标文件被别人改了。

**如果当时图省事直接「两侧都保留」解掉冲突就合**，会合入一份**回退他人收紧**的补丁。

**教训**：**冲突出现在「我以为只属于我」的文件上时，先查清对方改了什么，再决定怎么解。**

### 7.3 真 A/B 的做法

验证我的修复时，用了**同一 worktree、同一 commit、只换脚本**的方式（`git stash push -- <file>`），而不是把脚本复制到别处 —— 后者会因缺少同级模块而崩溃（实测踩过）。

---

## 8. 刻意未做（避免越权）

1. **不把 CI 从 `--mode=advisory` 改成 `enforce`** —— 会让所有存量 PR 立刻受判、影响面未评估，属独立决策。
2. **不改 AGENTS.md 判据正文** —— 判据 4 在修复后才真正可达，修复是让文档与实现重新一致，而非改判据。
3. **不追溯前 7 天历史欠账** —— 那批回填 PR 确携带了记录，「OK」结论本身没错，只是判据没跑。

---

## 9. 残余观察（不构成行动项）

`.ccg/reviews/` 下有 **49 个已跟踪的非 40-hex 文件**（如 `95063141c.json`、`2429ce1a3-logic.json`、`brief-archive-dedup-logic.md`）。#3434 的精确正则**不匹配**它们。

经查这些是**历史遗留**、非 pre-commit 产物（钩子只写 `<40 位 sha>.json`），故当前无实际影响；仅在未来出现**非钩子来源**向该目录写入并被 stage 时才可能复发。**只作留档，不建议改判据。**

---

## 10. 可复用的一般判据

从本案例可提炼出四条，适用于任何「多特性叠加」的仓库：

1. **新特性若改变了某判据的输入形态，必须回答「既有判据是否仍可达」。** 相隔数天的两个 PR 各自全绿，不构成这句话的答案。
2. **任何「恒 exit 0」的校验模式，都必须配一条「它是否还在跑」的元检查** —— 否则失效与通过外观相同。
3. **测试夹具必须至少有一条路径经过真实入口**（这里是 pre-commit 钩子），否则判据在测试里恒真。
4. **冲突发生在意料外的文件上 ⇒ 先取证再解**，不要「两侧保留」了事。
