## 0. 一句话结论

> **参考产品的「RPA」不是 Playwright/Puppeteer 式无头自动化，而是「一个专用于创作者后台的多标签浏览器」**：
> 每个账号绑定一个**独立的持久化 session 分区**，标签页加载真实的 `mp.*` / `creator.*` 页面，
> 「自动化」通过在**这些真实页面**里执行脚本、读 localStorage 取凭证来完成。

**四条独立证据**：

| # | 证据 | 说明 |
| --- | --- | --- |
| ① | IPC 频道 **34 个里 27 个是 `page-manager:*`** | 核心能力是多标签管理器（create/switch/close/split tab、go-back、navigate、reload）|
| ② | **RPA 词汇 0 命中**（`puppeteer`/`playwright`/`cdp`/`chromedriver` 全无）| 不引无头框架 |
| ③ | `getPartitionForTab(tab)` → `persist:auth-${accountId}` | **每个账号一个持久 session** = 账号隔离 |
| ④ | `new WebContentsView({...})` + `ses.clearCache()` | 用 Electron 30+ 的 `WebContentsView` 承载真实页面 |

> ⚠ 自查：首轮用正则扫 `rpa` 得到 **376 次命中**，看起来像「大量 RPA 代码」。
> 逐条看上下文后发现**全是 IP 地址库里的 `in-addr.arpa`**（`Address4.fromHex` / `fromArpa`）—— 假阳。
> 留档是因为它是「宽正则命中数当结论」的典型踩坑，与本目录
> `方法论-度量工具的五次同族错误.md` 描述的是同一类病。

## 2. 账号隔离方案（可直接借鉴）

```javascript
getPartitionForTab(tab) {
  if (tab.extra && tab.extra.accountId) {
    return `persist:auth-${tab.extra.accountId}`   // 按账号
  }
  return `persist:auth-${tab.tabId}`               // 兜底按标签
}
```

**三个可借鉴点**：

| 设计 | 为什么这么做 | 对本项目 |
| --- | --- | --- |
| `persist:` 前缀 | 会话**落盘**，重启后登录态仍在 | 我们的账号存储也要落在「重启不丢」的位置 |
| 按 `accountId` 分分区 | 同平台多账号的 cookie 互不污染 | 若做多账号，**必须按账号分分区，不能只按平台分** |
| 兜底到 `tabId` | 未绑定账号的临时标签也有隔离 | 临时标签不污染正式账号 |

同一份代码里还有 `ses.clearCache()` 在切分区时调用 —— 说明他们处理过「换账号后拿到旧缓存」的问题。

### 4.1 一个必须说清的矛盾

`socket.io` **server 与 client 都在依赖里**，主进程也有 `serverSocketManager` 字段，
但**没有找到 `new Server(...)` 或 `io('...')` 的调用**（各 0 命中）。

三种可能，**未验证**：
1. 由 minify 后的别名创建，字面量正则没覆盖；
2. 该能力在另一个进程/另一个产物里；
3. 依赖是历史遗留（dead weight）。

⇒ 本文**不声称**「参考产品用 socket.io 做 RPA 通道」，只记录「依赖与字段存在、调用点未找到」。

## 5. 与融媒宝的架构差异（决策用）

| 维度 | 参考产品 4.0 | 融媒宝 3.1 | 本项目 |
| --- | --- | --- | --- |
| 形态 | Electron（React 19）| 原生 DuiLib + CEF | Electron + Vue |
| 发布方式 | **驱动真实创作者后台页面** | **调平台 API**（1,327 端点）| 以 API 为主 |
| 账号隔离 | **每账号一个 `persist:auth-<id>` 分区** | 见 `SetLoginUserInfo`（宿主注入）| 需自查 |
| 多账号交互 | **同屏分屏**（10 个 split 频道）| 未取证 | — |
| 签名 | 在真实页面里跑（复用平台自己的 JS）| 内嵌/搬运签名实现（`sign2/` 18.7 MB）| — |
| RPA 框架 | **无**（不引 puppeteer/playwright）| 无（原生 C++ 引擎）| Playwright |

### 5.1 ★ 最有价值的一条

参考产品用「真实页面」**绕开了签名逆向**这个最难的问题 ——
页面里平台的签名 JS 自己就在跑，它们只需 `executeJavaScript` + `waitForLocalStorage` 取结果。

这是**用架构规避算法**的典型案例。代价是：慢、脆（页面改版即失效）、必须有人工登录态。

对本项目的含义：**如果我们在某个平台被签名卡住，值得评估「走真实页面」这条退路**，
但要先算清「脆性成本」（页面改版频次 × 每改一次的重修成本）是否低于「逆向成本」。
