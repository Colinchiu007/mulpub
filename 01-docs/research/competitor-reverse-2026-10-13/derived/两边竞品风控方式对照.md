## §1 一句话结论

**两边走的是同一条「主进程发 HTTP + 签名外包」路线，但外包对象不同——融媒宝把签名算法外包给「平台页面」（原生组装输入 → 注入 JS 到 CEF 页面 → 页面算签名 → 桥回调原生）；参考产品把签名算法外包给「自家远端签名服务」（`qianming.refproduct.cn:<端口>` 的 `/Sign/GetSign`，按平台分端口路由），主进程 bundle 里零平台签名算法实现。** 两者都拒做「本地复刻平台签名算法」；都不如本项目（mulpub）已有的「①②族本地实现 + ④族页面求签」双轨架构自主。

补充修正一处既有认知：**参考产品此前被记录为「有本地签名（clientSign 逐行等价本项目）」，本轮全 bundle 取证后修正为——`createSign` 本地实现仅 3 处，全部服务于抖音 ticket-guard（`create_v2` 路径）与视频号私信一条链；其余 9 个平台的签名全部走远端服务。**「参考产品=本地签名」是以偏概全，它是一个「远端为主、抖音链本地兜底」的混合体，且其抖音本地链与本项目一样面临 `__security_mc_*` 命名失配风险（既有文档《关键缺陷-抖音签名cookie名不匹配.md》已证它不认识新命名）。

- **自研** = bundle 内有该签名的完整算法实现（哈希/加密常量 + 轮循环）。


- `cookie` 字段实际装的是**待签 payload**（小红书是 `[url, encodeURIComponent(body)]` 数组、

### 2.4 `executeJavaScript`（32 处）与签名无关——注入式被排除的关键证据

32 处命中全部落入三类（抽样判读 @2880166 / @2880898 / @2881883 / @2882077）：
① `waitForLocalStorage`（轮询等登录材料落地）；② `waitForLoginFinish`（登录完成检测）；

## §4 对本项目（mulpub）的可借鉴点

### 4.1 值得抄的

| # | 做法 | 出处 | 为什么值得抄 |
| --- | --- | --- | --- |
| 1 | **签名请求失败先 `Task.Delay(1500)` 重试 3~4 次再放弃** | 参考产品 `getSign$7` @600621 等 9 处同构 | 本项目 Tier-B provider 已有失败限流（≤3 次异常降级），但没有「签名服务瞬断时的退避重试」。抄它的**退避节奏**（1500ms 间隔、3-4 次、端口轮换）作为 Tier-B 的重试参数基线，比自定拍脑袋值有依据。 |
| 2 | **payload 摘要做签名缓存 key** | `getSign$5`/`getSign$2`：`md5(payload)` 命中即返回缓存 | 同一 payload 重复发布（如草稿重发、重试链）时省一次签名往返。本项目 Tier-A 是纯计算无此需求，但 Tier-B 页面求签每次都要建页/往返——**加一层 md5(payload)→签名 的进程内缓存**，边界是只缓存确定性签名（时间戳参与的字段要剔除或短 TTL）。 |
| 3 | **端口/实例轮换 + `portIndex>1e5` 归零防溢出** | `portIndex$N++` / `S%T.length` | 若本项目未来部署多签名 worker，这是现成的负载分配模式（无需负载均衡器）。 |
| 4 | **`executeJavaScript` 只用于登录态轮询，不用于签名** | @2880166 区 | 印证本项目「页面求签走专用签名页 + bridge 白名单」的隔离设计是对的——参考产品把 executeJavaScript 限制在登录检测域，签名面完全不进页面，等于从架构上杜绝了页面篡改签名面。 |
| 5 | **风控头命名不拘泥于 sign/a_bogus 字面** | 网易 `X-NR-Trace-929`、拼多多 `Anti-Content` | 本项目 `config/platforms.yaml` 若未来扩平台，头名清单应包含这类「伪装成 trace/内容字段的风控头」，不要只搜 sign 字样。 |

### 4.2 要避开的坑（参考产品已踩实）

| # | 坑 | 证据 | 本项目的对应防线（已有，勿拆） |
| --- | --- | --- | --- |
| 1 | **签名失败静默吞掉后带空签名硬发** | `getSign$7` 的 `catch(M){} return ""`，9 处同构；URL 模板里 `&a_bogus=`（空值）照发 | 本项目 registry fail-closed（未知 command 抛错）、Tier-B 非空校验（拒对象/null）——**空签名应阻断发布而不是硬发**。带空签名硬发 = 直接喂给平台风控一个「程序化请求」特征。 |
| 2 | **远端签名服务是单点 + 域名硬编码 + 端口表散落** | `qianming.refproduct.cn` ×3 处 + 9 平台端口表内联在 `getSignServerUrl` | 本项目已把远端签名服务退役（0 残留），此坑已绕开；**未来若任何功能要引远端服务，签名类依赖必须可配置 + 可降级**（`MP_SIGNER_BASE` 式环境变量 + 明确的 no-go 边界）。 |
| 3 | **`catch{}` 静默吞错**贯穿全部签名链 | 9 个 `getSign$N` 全部 `catch(M){}` / `console.debug` 吞错 | 本项目错误处理规范（fail-closed + 脱敏日志）。参考产品的 `console.debug("获取签名失败", O)` 会把含 cookie/payload 的对象打进控制台——**日志泄密**，本项目 douyin-ticket-guard 头注释已明令禁止序列化私钥。 |
| 4 | **bundle 里同时存在两代命名取材料** | `security-sdk/s_sdk_*`（28+32 处字面）vs 平台实际 `__security_mc_1_*` | 既有《关键缺陷-抖音签名cookie名不匹配.md》已在本项目修复（`\d+` 代际号正则）。**参考产品没修**——它的抖音本地链大概率一直在静默失败。本项目不要因「参考产品这么做」回退到裸字面量匹配。 |
| 4b | **字段名撒谎的 API 设计**：远端服务请求里 `cookie` 字段实际装 payload/md5 | §2.2 契约 | 本项目 IPC/服务契约命名要与语义一致，否则下一个人读代码会像本轮一样花时间澄清「cookie 字段为什么装的是 payload」——文档里每处都要点名。 |
| 5 | **`window.` 全局前缀命中 298 处**（库/页面操作混用，无法区分签名域） | JSON 证据 | 对本项目无直接坑，但提示：**bundle 级 grep `window.` 不可作签名定性判据**，必须以「页面函数名 + 回调桥名」成对取证。 |
