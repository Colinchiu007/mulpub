## 2. ★ 技术债：加密/网络/渲染三层全部冻结在旧版本

| 组件 | 交付版本 | 时间 | 现状 | 风险面 |
| --- | --- | --- | --- | --- |
| **OpenSSL** | **1.0.2g** | 2016-03 | **EOL 2019-12-31** | 该分支后续修复了数十个 CVE（含多个高危）；1.0.2 系列已不再维护 |
| **libcurl** | **7.47.1** | 2016-02 | 2016 年后累计修复 30+ CVE | 协议解析、TLS 校验、重定向处理 |
| **Chromium / CEF** | **109** | 2023-01 | 此后约 3 年的 Chromium 安全修复未覆盖 | 渲染引擎与 JS 引擎是最大攻击面 |
| **zlib** | 1.2.8 | 2013 | 后续有 CVE-2016-9841/9842/9843、CVE-2018-25032 | 解压路径 |
| **MediaInfo** | 0.7.78 | ≈2013 | 解析器历史漏洞 | 处理**外部媒体文件**时风险最高 |
| **VLC** | 3.0.16 | 2021 | 3.0.17.x 起修复了若干解析类 CVE | 同上 |
| **MSVC 运行时** | VS2010 SP1 | 2011 | 已停止支持 | 运行时库漏洞无补丁 |

### 2.1 三条判读（写给决策用，不是安全报告）

1. **他们的工程重心不在安全升级**，而在功能迭代（版本号 3.1.0.7433 说明迭代很密）。
   对本项目：**「依赖新版 + 定期升级」是可写进对比表的客观差异**，但要能拿出自己的升级节奏证据。
2. **MediaInfo + VLC + dwebp 三个解析器都处理外部文件** —— 这是他们真实的攻击面，
   也是「用户导入素材」这条路径的固有风险。对本项目：素材解析同样走这条路，
   **不要只比功能，要比「解析器版本 + 沙箱边界」**。
3. **OpenSSL 1.0.2g 会限制可用的 TLS 特性**（如 TLS 1.3 不支持）⇒ 若某平台强制 TLS 1.3，
   他们这条老 `libcurl` 链路会失败。这可能是「某些平台偶发发布失败」的**结构性原因之一**（**未验证**）。

## 3. 架构判读：三层 UI 与两条媒体链路

### 3.1 UI 是「原生为主 + CEF 为辅」

| 证据 | 含义 |
| --- | --- |
| `DuiLib.dll` **1,959 个导出** | 腾讯 DuiLib 是**原生 Windows UI 框架**，主窗口/对话框是原生 |
| `Asset/` 下 316 个 js + `CefBrowser.dll` | CEF 承载**功能页**（编辑器、评论运营、智能剪辑等）|
| `cef_browser_*` 处理器在 `WEMedia.exe` 内 | 桥接层在主程序，不在 DLL |

⇒ **不是 Electron 式「全前端」，也不是纯原生**：主框架原生（DuiLib），业务功能页用 CEF。
这与参考产品（纯 Electron）是**完全不同的架构选择**，可直接进横向对比表。

### 3.2 两条媒体链路并存

| 链路 | 组件 | 用途推断 |
| --- | --- | --- |
| **VLC 系** | `libvlc` / `libvlccore` 3.0.16 | 播放 / 转码 / 时长探测 |
| **自研 + 库混合** | `LQMedia.dll`（自研，2 导出）+ `MediaInfo` + `dwebp` + `CxImage`（在 MediaTaskMgr 内）| 元数据 / WebP / EXIF / 图像处理 |

⇒ 他们**既引 VLC 又自研 LQMedia**，说明「媒体处理」是他们认定必须自己控的部分。
对本项目（Remotion / ffmpeg）：**不必跟，但要能解释为什么不必跟**。

## 5. 加壳判据：27 个组件**全部干净**

| 结论 | 证据 |
| --- | --- |
| 命中已知壳字符串 | **0 个组件命中**（VMProtect / Themida / ASPack / `UPX!` / PECompact / NsPack）|
| 入口点前导 | 全部是正常编译器序言（`55 8b ec` = `push ebp; mov ebp,esp`，或 `83 ec 1c` = `sub esp,1Ch`）|
| 节名完整性 | 27/27 完整（含 `.00cfg`、`/4` 这类合法但少见的名字）|
| 架构 | 27/27 全部 **PE32 / x86**（无 64 位组件）|

⇒ **整个产品是 32 位应用**。这与「`.text` 12.4 MB 导致 Ghidra 分析不完」无关（是体量，不是架构）。

## 6. ★ 本轮修掉的一个自身假阳（留档）

第一版判据把 **8 个组件错判为「需人工」**：

| 组件 | 被误判原因 | 真相 |
| --- | --- | --- |
| `chrome_elf` / `libEGL` / `libGLESv2` / `libcef` / `vk_swiftshader` / `vulkan-1` | 节名 `.00cfg` 不匹配旧正则 | `.00cfg` 是 MSVC **CFG 控制流保护**节，完全正常 |
| `libvlc` / `libvlccore` | 节名 `/4` 不匹配旧正则 | `/4` 是 VLC 链接器 `/merge` 指令生成的合法节名 |
| `libcef.dll` | 字符串命中 `Enigma` | `Enigma` 是 148 MB Chromium 里的普通英文单词，**纯噪声** |

**修法**：节名判据放行数字开头与 `/` 前缀；把 `Enigma`/`Obsidium` 这类通用词移出整文件扫描面。
**回归锁**：`dump-pe-tables.test.js` 5 个用例（含「这 8 个不得再被判需人工」「壳签名表不得含通用词」）。

**为什么留档**：假阳比漏检更坏 —— 它训练人忽略告警。这与本仓
`check-unwired-tests` / `check-mask-coverage` 反复踩的「宽判据抓不到 / 窄判据抓错」是同一类病。
