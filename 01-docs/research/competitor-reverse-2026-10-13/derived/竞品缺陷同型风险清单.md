## 3. 三类高危展开（为什么它们比看起来更值得防）

### 3.1 R1 转义表不同步 —— 静默、必然、用户可感知

竞品那个 bug 的形状极简：**字符类写全了，映射表漏了一个键**。JS 的 `String.replace` 回调返回 `undefined` 时会被转成字符串 `"undefined"`，
所以它不抛错、不告警，只在**每一处**命中该字符时插入一段垃圾文本。

**我们的自查点**：`escapeHtml` 一族（8 个文件）是否也有「字符类 `[&<>"'/]` 之类」与「map 键」分头手写的结构。
**这类问题可以完全机械化检测**：解析源码拿到字符类与 map 键集，断言后者 ⊇ 前者。见 §4-L1。

### 3.2 R3 无界重试 —— 现状安全，但**安全是靠人写的，没有锁**

我们 10 处 `while(true)` 本轮**全部**有界（含 `videogen-stages.js` 的 10 分钟 deadline +
终态判断 + 超时文案）。但**没有任何测试会阻止**后来者加第 11 处无界循环。
竞品的 C2/C3 就是「一开始只是想重试一下」演化成「每秒打服务端且按钮永久置灰」。
⇒ 现状 ✅ 但需锁（§4-L2）。

### 3.3 R6 测量 ≠ 渲染 —— 我们是**对的**，原因值得写下来

竞品 X-C3 的三个成因（不插 icon / `_noMarginTop` 只在一侧 / 「首项」语义不同）本质是同一条：
**同一个布局规则被抄成两份代码**。
我们把「测量（必须 DOM）」与「决策（纯计算）」拆成两半（`card-paginator-core` 不 require 任何 DOM），
再加 8 例 parity 对账 ⇒ 结构上就**不存在**「两套公式」的土壤。
这条经验应作为**任何分页/排版需求的默认架构**，而不是本项目特例。

## 4. 锁清单（三批落地：L1-L4 / R5+R9a / R7+R11）

> **落地状态**（2026-10-18，三批共 **8 条锁**，全部挂 `quality-gate.yml` changes job 的 **Gate 2c6**，
> CLI `node scripts/check-same-type-risk-locks.js` 汇总；共享屏蔽抽至 `scripts/lib/code-mask.js`）：

| 锁 | 判据 | 批次 | 变异反证 |
| --- | --- | --- | --- |
| **L1** 转义表完整性 | `replace(/[...]/g, m=>map[m])` 字符类 ⊆ map 键集 | 一 | 删 map 一个键 ⇒ 红 |
| **L2** `while(true)` 必有出口 | 循环体内须有 `break`/`return`/`deadline`·`timeout` | 一 | 加无出口循环 ⇒ 红 |
| **L3** catch 不得自递归 | catch 内不得调用「包住该 catch 的函数自身」 | 一 | catch 改自递归 ⇒ 红 |
| **L4** 组件定时器必须清理 | 同文件 `setInterval(` ⇒ 必须 `clearInterval(` | 一 | 删 clear ⇒ 红 |
| **R5** loading 复位 | 函数内置 true 无复位 ⇒ 红；finally 外复位/跨方法状态机 ⇒ 出声 | 二+四 | 删 finally 复位 ⇒ 红；第四批修「单行 finally 漏判」判据缺陷 |
| **R9a** 假进度心跳 | 定时器窗口内对进度赋字面量 ⇒ 红 | 二 | 加假进度条 ⇒ 红 |
| **R7** mime↔后缀单一真源 | 同对象字面量内 `image/jpeg` 与 `.jpg`/`.png` 对 ⇒ 红 | 三 | 新抄一张映射表 ⇒ 红 |
| **R11** 模块级状态累积 | 模块级 Map/Set 有写无清 ⇒ 出声 | 三 | （审计面，不拦截）|

**写法要求（沿用本仓既有纪律）**：
1. 每条锁必须**先制造一次红**（变异反证），并把「红了什么」写进测试注释与执行记录；
2. 锁的判据要**打印命中条数并对下界断言**（0 命中会让「解析失败」伪装成「全部合规」）；
3. 不做「靠命名猜语义」的启发式 —— 本仓实测宽判据的假阳性比真阳性多（见 `方法论-度量工具的五次同族错误.md`）；
4. **R8（await 无兜底）明确不锁**：2,527 处抽样全误报（见 §2 R8 行）。

### 4.1 八条锁的**公共底座**：`scripts/lib/code-mask.js`（2026-10-18 补）

八条锁全部建立在同一个 `maskNonCode` 之上（先把注释/字符串/正则掩成空白，再在"只剩代码"的文本上判定）。
**底座错一次 = 八条锁一起瞎**，而"看不见"与"没有违规"在输出上完全同形。

本轮实测它确实瞎过：该库只识别「行注释 / 块注释 / 引号字符串」三种词法形态，**没有正则字面量**，
于是 `const re = /["']/g` 里的 `"` 被当成字符串起点，一路扫到下一个引号 ——
中间整段代码被当字符串内容掩掉。

| 量化指标（源码面 3089 文件，扫 apps/packages/scripts/.github）| 读数 |
| --- | --- |
| 含「正则字面量内出现引号」的文件 | **311** |
| 其中掩码后可见字符保留率 < 0.55（被打穿）| **164** |
| 最坏单文件 | `rewrite-engine/src/knowledge-base.js` **0.03**（522 / 17196）|
| 其它重灾 | `content-quality-criteria.js` 0.04、`asset-generator.js` 0.05、`rich-text-processor.js` 0.06、`check-hardcoded-secrets.js` 0.07、`logger.js` 0.08 |

**修复后的实证**（A/B 逐文件对比旧实现）：**174 个文件可见字符增加、0 个回归**；
八条锁读数同步扩大 —— R7 对象 63,951 → **67,034**（+4.8%）、R9a 定时器 812 → **816**，
而 R7 独立映射 / R5 无复位 / R9a 字面量进度仍全部为 **0**（可见面扩大但零新增违规）。

**这条取证手段已固化为工具**（2026-10-18）：`node scripts/check-mask-coverage.js --base origin/main` 逐文件对比
可见字符数，输出「增加 / 不变 / **减少（回归，必须为 0）**」三分类，rc=1 即不许合入。
改动 `maskNonCode` 的任何 PR 都应先跑它并附读数 —— 它把「证明判据能看见」从一次性的临场发明变成可重复动作。

**教训（已写入 `01-docs/learnings.md`）**：抽共享库时只做「与旧实现逐字节等价」的断言**不构成正确性证明** ——
等价只能证明"错得一样"；必须同时为库的**每种词法形态**建责任边界测试。
`scripts/lib/code-mask.test.js`（14 例）+ Gate 2c6 接线即为该口径的落地。

### 4.2 R11 审计面 13 条的分类登记（2026-10-18，逐条读过声明与全部成员调用）

修掉漏检守卫后 R11 从「2 条」变成「13 条」。这 13 条**不是新缺陷**，是原先被藏起来的审计面。
按「为什么只增」分类：

| 分类 | 条目 | 判定 |
| --- | --- | --- |
| **登记表 / 幂等保护**（key 有界，**必须**只增）| `window.js` `_completedIpcRegistrars`（key 只来自 `IPC_REGISTRAR_NAMES` 常量表 ≤10，clear 会破坏 R28 幂等）· `auth-partition-reclaim.js` `livePartitions` / `capturedPartitions`（文档原注「进程级、随会话增长、量级可忽略」）| ✅ 可接受 |
| **平台/适配器注册表**（key = 平台或类型，有界）| `platform-metrics/index.js` `registry` · `rpa-engine/publish-signer.js` `adapters` · `PlatformOverridePanel.vue` `fieldsCache` · `publish-overrides.js` `overrideFieldsCache` | ✅ 可接受 |
| **限流桶**（过期即原地覆盖，单 key 不累积）| `notify.js` `rateBuckets`（key 另受 `isKnownMessageKey` 前缀白名单约束）| ✅ 可接受 |
| **测试 mock** | `test-setup.js` `mockRegistry` | ✅ 可接受 |
| **真实无淘汰缓存** | `story2video-image-retry.js` `llmRewriteCache` / `llmRewriteCallCount` | ✅ **已于 2026-10-18 有界化**（见下行）|
| **有界/单 key 缓存**（评估后确认不增长）| `story2video-paths.js` `_lastImportedMediaGcByBaseDir`（生产仅单 baseDir，注释明说）· `tag-suggest/compliance-filter.js` `_blocklistCache`（key = 单一默认 dataDir）| ✅ 可接受 |

**有界化处置（2026-10-18）**：`llmRewriteCache` / `llmRewriteCallCount` 的 key 是**原始 prompt 的 SHA-256**
（用户每写一个新 prompt 就是新 key ⇒ 无界），而 Electron 主进程**常驻**（不随单次生成任务结束重启）⇒ 单调增长。
原作者注释已自承「模块级，仅单次运行内有效」但没定上限。
修法：**插入序上限** `LLM_REWRITE_CACHE_MAX_ENTRIES = 500`（Map 天然保序，超出删最早那条）。
语义不变 —— 同 key 命中直接复用的缓存收益完整保留，正常使用远不到 500 个 key 所以永不触发淘汰。
证据：既有 vitest **49/49** 全绿、新增回归锁 4 例、R11 审计面 13 → 11（这两条不再是无淘汰缓存）。

> 结论：13 条中 **11 条可接受**（有界或有意只增）、**2 条已于 2026-10-18 有界化处置**。
> 判据只出声不拦截，因此这些条目不会卡 CI；它们的风险是「进程长时间运行后 Map 缓慢变大」，
> 需按实际调用基数评估 —— 本轮对其中 2 条完成该评估并落地修复，见 `openspec/records/cache-bound.md`。
