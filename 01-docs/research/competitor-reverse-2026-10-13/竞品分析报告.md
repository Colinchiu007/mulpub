## 2. 两个产品的技术架构

> **原生层分析结论（第 2-3 轮）**：两个 exe 均经过加壳/自解压保护，但**换目标后原生分析成功**。
> 完整结果见 [原生层分析报告.md](原生层分析报告.md) 与 [原生层分析补充报告.md](原生层分析补充报告.md)：
> - **参考产品 exe = LZMA 自解压壳**（段名 `LZMADEC`/`malloc_h`/`prot`/`CPADinfo`），
>   196 MB 里绝大部分是压缩的 Electron 运行时，**业务代码全在 asar（已完整分析）**，
>   反编译 exe 无价值。
> - **融媒宝 exe = 加壳 32 位原生程序**（导入表不可读 + UTF-16 中文串全乱码，
>   但 ASCII 可读）。`.text` 段 12.4 MB，Ghidra 三档超时（330 s / 30 min / 60 min）
>   全部失败，且业务界面全在 `Asset/*.html` + JS（266 个 JS，已完整分析）。
> - ✅ **`MediaTaskMgr.dll`（融媒宝的媒体任务引擎，10 MB）Ghidra 分析成功**：
>   66,199 个函数 / 13,120 个字符串，还原出**任务引擎类层次**、**15 种 ffmpeg 操作**、
>   **1,338 个平台 API 端点**、**TTS 三家供应商**。

**⭐ 一个必须先纠正的认知：参考产品本质是个「浏览器」**


**它不是表单式应用，而是「浏览器外壳 + 平台内嵌页 + 自动化注入」**：
用户在应用内直接打开平台网站、登录、浏览、发布；外层提供标签页/分屏管理与 RPA。

这解释了 `page-manager` 为什么有 **29 个 IPC 通道**（含完整的 split-view 分屏能力），

**这个认知很重要**：它意味着**参考产品与本项目的架构本质同构**
（Electron 外壳 + 内嵌浏览器 + RPA），差异在工程细节而非范式。
详见 [参考产品-完整拆解.md](参考产品-完整拆解.md) §2。

**对比本项目**：`platform-definitions.js` 是**单一数据源**（URL + 检测模式），逻辑集中在 `auth-view-manager.js`。参考产品是**每平台独立类**。

**评估**：本项目的数据驱动方案在 15 个平台下更简洁；若平台数涨到 40+，参考产品的类方案更容易承载平台差异逻辑。**混合方案最优**：保留数据源，但把"登录完成判定"这类平台特有逻辑抽成可插拔策略对象。

### 3.3 ⭐ 抖音登录态检测（高价值）

这是本次分析**最有技术价值的具体发现**：

```javascript
class DouYinAuthorizeConfig extends PlatformAuthorizeConfig {
  waitForLoginFinish(views, params, abortSignal) {
    return Promise.allSettled(views.map(async (view, idx) => {
      // 1. 先记录当前值作为基线
      const baseline = await view.webContents.executeJavaScript(
        "localStorage.getItem('security-sdk/s_sdk_sign_data_key/web_protect')"
      );

      // 2. 竞速：10 秒硬超时 vs 正常检测
      const timeoutRace = new Promise((resolve, reject) =>
        setTimeout(async () => {
          if (!abortSignal.aborted) {
            const sdk = await view.webContents.executeJavaScript(
              "localStorage.getItem('security-sdk/s_sdk_crypt_sdk')");
            const sign = await view.webContents.executeJavaScript(
              "localStorage.getItem('security-sdk/s_sdk_sign_data_key/web_protect')");
            if (sdk && sign) resolve();
            else reject(new Error(`视图 ${idx} 超时：10秒内未找到 key`));
          }
        }, 10000)
      );

      // 3. 正常检测：等待 key 出现 + 相对基线发生变化
      const normalCheck = (async () => {
        await waitForLocalStorage(view, ["security-sdk/s_sdk_crypt_sdk"], abortSignal);
        await waitForLocalStorageDifferentFrom(
          view, {"security-sdk/s_sdk_sign_data_key/web_protect": baseline}, abortSignal);
      })();

      return Promise.race([timeoutRace, normalCheck]);
    }));
  }
}
```

**技术要点**（本项目可直接借鉴）：

1. **双 key 判定**：`s_sdk_crypt_sdk`（出现即登录）+ `s_sdk_sign_data_key/web_protect`（值相对基线变化才算完成）——比单纯 URL 跳转检测可靠得多
2. **基线快照**：登录前先读一次值，避免"页面本来就有旧值"的误判
3. **Promise.race 硬超时**：10 秒兜底，防止无限等待
4. **`Promise.allSettled`**：多视图并发检测，任一成功即算完成（见代码末尾 `if (!M.some(U => U.status === "fulfilled"))`）
5. **`AbortSignal`**：全程可取消

**本项目的现状**：`auth-view-manager.js` 已有 `waitForPostLoginSession` + `_checkLoginCompleted(url)` 做 URL 模式检测，并持久化 cookies/localStorage/IndexedDB。**缺的正是"平台特定 localStorage key 检测"这一层**。

**但这是一个值得用一次真机复核解决的分歧**——

```javascript
clientSign = (cookie) => {
  // ① 从 cookie 提取 EC 私钥（平台自己下发的密钥材料）
  const ecKey = JSON.parse(JSON.parse(decodeURIComponent(
    cookie.split("security-sdk/s_sdk_crypt_sdk=")[1]?.split(";")[0]?.trim()
  )).data).ec_privateKey;

  // ② 取 ticket 与 ts_sign
  const M = JSON.parse(JSON.parse(decodeURIComponent(
    cookie.split("security-sdk/s_sdk_sign_data_key/web_protect=")[1]?.split(";")[0]?.trim()
  )).data);

  // ③ 构造待签串
  const ts = parseInt(String(Date.now() / 1000));
  const payload = `ticket=${M.ticket}&path=/web/api/media/aweme/create_v2/&timestamp=${ts}`;

  // ④ SHA256 + EC 私钥签名（Node 内置 crypto）
  const sign = crypto.createSign("SHA256");
  sign.update(payload); sign.end();
  const reqSign = sign.sign(crypto.createPrivateKey(ecKey), "base64");

  // ⑤ 组装请求头 bd-ticket-guard-client-data
  return JSON.stringify({ ts_sign: M.ts_sign, req_content: "ticket,path,timestamp", req_sign: reqSign, timestamp: ts });
}
```

**为什么这对本项目价值最高**：

1. **~~本项目明确规划过 P1 本地签名，但未实现~~** → ⚠️ **作废**：本项目**已实现**（`packages/api-publish-engine/src/signer/`）。参考产品这份的价值是**可作对照**，不是「补本项目空缺」
2. **不需要逆向密钥算法**：密钥材料是平台通过 cookie 下发的（`ec_privateKey`）
3. **不需要第三方库**：Node 内置 `crypto`（`createPrivateKey` + `createSign("SHA256")`）即可
4. **待签串格式简单**：`ticket=<ticket>&path=<路径>&timestamp=<秒>`

**建议**：
在 `publish-signer.js` 注册 `douyin_local` 适配器，按上述方式实现。

**现状**：本项目 `auth-view-manager.js` 的 `_checkLoginCompleted(url)` 基于 URL 模式匹配。参考产品已演进到 **localStorage key 检测**。

**问题**：URL 匹配在很多平台不可靠——抖音登录成功后会跳回 `creator.douyin.com/`，但 URL 变化不等于登录态建立（可能只是打开了登录页）。

**⭐ 关键洞察**：参考产品等的 `s_sdk_crypt_sdk` / `s_sdk_sign_data_key/web_protect`
**不是普通登录标记**，而是**字节 security-sdk 下发给页面的签名密钥材料**
（就是优先级 0 里 `clientSign` 的输入）。
所以它等的不是「登录成功」，而是**「具备签名能力」的那一刻**——
这比等 URL 跳转精确得多，因为登录后不一定立刻跳转，但密钥一定会注入。

**建议**：在 `platform-definitions.js` 增加可选的 `loginStateProbe` 字段：

```javascript
// platform-definitions.js 新增
const PLATFORM_LOGIN_STATE_PROBES = {
  douyin: {
    // 出现即视为登录态建立
    appearKeys: ['security-sdk/s_sdk_crypt_sdk'],
    // 值相对基线变化才算完成（防误判）
    changeKeys: ['security-sdk/s_sdk_sign_data_key/web_protect'],
    timeoutMs: 10000
  },
  kuaishou: { appearKeys: [/* 快手的 key */], ... }
}
```

然后在 `auth-post-login-redirect.js` 里实现 `waitForLoginStateProbe(view, probe, signal)`，与现有 URL 检测**并行竞速**（`Promise.race`），任一成功即算完成。

**工作量**：约 100-150 行 + 测试。**收益**：登录成功率提升，减少"以为登录了实际没有"的静默失败。

### 优先级 11：CDP 响应体拦截（第 4 轮新增，谨慎评估）

参考产品有一套基于 `webContents.debugger`（Chrome DevTools Protocol）的通用拦截器：

```javascript
// 拦截指定 URL 模式的响应体，解析 JSON 后交给 processor
await view.webContents.debugger.sendCommand("Fetch.enable", {
  patterns: [{ urlPattern: `*${pattern}*`, resourceType: "XHR", requestStage: "Response" }]
});
// 监听 Fetch.requestPaused → Fetch.getResponseBody → 解析 JSON
```

**核心手法**：**让平台页面自己发请求（自带签名/cookie），应用只拦截读取结果。**

三条技术路线对比：

| 路线 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| **A. 搭乘页面请求**（CDP 拦截）| 参考产品 | 抗改版强；不用逆向签名 | 必须在页面上下文；页面不开就没数据 |
| **B. 页面内 SDK 调用** | 本项目 `hostSdkAdapter` | 不用自己逆向算法 | 依赖页面暴露 SDK |
| **C. 本地签名** | 参考产品 `clientSign`；**本项目已实现**（`ticket-guard`，~~P1 待做~~ 已否证）| 可无人值守、快 | 算法变了要跟；风控风险最高 |

**⚠️ 代价**：
- `debugger.attach()` 会触发页面顶部「正在被调试」提示，**可能被平台前端反调试检测发现**
- `Fetch.enable` 拦截会**显著拖慢页面**（每个响应过一次 JS 回调）

**建议**：**优先保持本项目现有路线**（`account-metrics/adapters.js` 直接带 cookie 调平台 API，
比 CDP 拦截轻量）。仅在「平台 API 必须页面上下文签名」时才考虑 CDP。

**成本**：中。**风险**：中（可被检测）。**建议**：暂不实施，登记为备选方案。
