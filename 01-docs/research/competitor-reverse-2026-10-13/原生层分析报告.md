## 0. 为什么是 MediaTaskMgr.dll

融媒宝的主程序 `WEMedia.exe`（17.3 MB，32 位，加壳）**Ghidra 全量分析实测不可行**：
`.text` 段 12.4 MB，默认 330 s / 30 min / 60 min 三档超时全部失败，单点反编译入口也超时
（Ghidra 必须先完成完整导入 + auto-analysis 才能反编译任何函数）。

**改用 `MediaTaskMgr.dll`**——它是融媒宝的**媒体任务引擎**，体积 10 MB 可分析，且承载了
「内容同步 / 发布 / ffmpeg 处理 / 平台 API 调用」这些**最有复用价值的逻辑**。

`MediaTaskMgr.dll` 与 `MediaTaskMgr_1.0.0.257.dll`（旧版本残留）版本号对比：

| 文件 | ProductName | 版本 | 说明 |
|---|---|---|---|
| `MediaTaskMgr.dll` | 自媒体助手1.0 | **1.0.0.264** | 当前生效 |
| `MediaTaskMgr_1.0.0.257.dll` | 自媒体助手1.0 | 1.0.0.257 | 组件热更新的旧载荷 |

> **发现**：媒体引擎是**独立版本化的组件**（「自媒体助手」，版权方「自媒体工作室」，2020-2025），
> 与主程序（「融媒宝3.0」，上海生趣网络科技有限公司，2017-2030）**不是同一版本线**。
> 配合之前发现的 `ApiSoftware/CheckComponent` 接口 + 旧版本残留文件，
> 可确认融媒宝采用**组件级热更新**机制：下载 `MediaTaskMgr_<版本>.dll` → 替换生效。

## 2. ⭐ 原生任务引擎的类层次（RTTI 还原）

MSVC 的 RTTI 类型描述符（`.?AV...@@` 形式）完整保留了类名，据此还原出任务引擎的**完整架构**。

### 2.0 ⭐ 导出 API —— 主程序与引擎的集成契约

`rea search --kind procedures` 从符号表还原出 **5 个导出函数**（DLL 的公开接口）：

| 导出函数 | 地址 | 职责 |
|---|---|---|
| `InitMediaTaskMgr` | `0x101D69A0` | 初始化任务引擎 |
| `UnInitMediaTaskMgr` | `0x101D6EA0` | 反初始化（释放资源）|
| `GetMediaTaskMgr` | `0x101D6E90` | **获取单例**（C 风格，非 COM）|
| `SetMediaTaskMgrPostMsgCallback` | `0x101D6990` | **注册消息回调**（任务完成/进度回传）|
| `SetTaskMgrIdleCallback` | `0x101D6F50` | **注册空闲回调**（引擎空闲通知）|

**架构判读**：这是一个**极简的 C 风格导出契约** ——
`Init` → `Set*Callback`（双向通信）→ `Get*`（单例取用）→ `UnInit`。
主程序 `WEMedia.exe` 通过这 5 个函数把媒体任务引擎嵌入自己的消息循环：
任务进度与结果经 `PostMsgCallback` 回传，空闲时经 `IdleCallback` 通知。

**对比本项目**：本项目的任务系统是 Node.js 内的
`task-queue.js`（EventEmitter + 通道调度）+ `task-pool.js`，
通过 `progress-emitter.js` 上报进度。**架构形态不同但设计目标一致**：
都是「引擎 + 回调上报 + 单例调度」。本项目用 EventEmitter 比 C 回调函数指针更灵活
（支持多监听者、异步、Promise 化），**不需要改**。

> 这说明融媒宝的媒体引擎**预留了替换实现的扩展点**——同一套宿主代码可对接不同的任务管理器实现。
> 这是成熟的原生组件设计（接口隔离 + 依赖倒置）。

+ `task-pool.js` + `progress-emitter.js`。设计目标一致（引擎 + 进度上报 + 单例调度），
但本项目用 Node 的 EventEmitter 而非 C 回调函数指针——**支持多监听者、异步、Promise 化，更灵活**。
两侧都有的「幂等初始化」与「接口/实现分离」本项目同样具备（`container.js` 依赖注入），**不需要改**。

### 2.1 基类与基础设施


## 6. ⭐ TTS 三家供应商（语音合成）

原生层实现了**三路 TTS**：

```
阿里云:  https://nls-gateway.cn-shanghai.aliyuncs.com/rest/v1/tts/async
         begin AliTextToAudio. / end AliTextToAudio.

微软:    https://chinaeast2.tts.speech.azure.cn/cognitiveservices/v1
         http://public.17van.com/voice/MicrosoftToken      （自有代理取 token）
         http://public.17van.com/voice/Synthetic           （自有代理合成）
         begin MicrosoftTextToAudio. / begin MicrosoftTextConvertAudio.

自有:    https://interface.17van.com/voice/rmbDuration       时长预估
         https://interface.17van.com/voice/rmbGetToken       token 下发
```

**微软 TTS 的 SSML 模板**（提取到真实片段）：
```xml
<speak version='1.0' xml:lang='zh-CN'
       xmlns='http://www.w3.org/2001/10/synthesis'
       xmlns:mstts='http://www.w3.org/2001/mstts'>
  <voice name='...'>
    <mstts:backgroundaudio src='...'/>
    <mstts:express-as ...>          ← 情感/风格
      <prosody volume='...'>...</prosody>
      <mstts:silence type='Leading-exact' value='...'/>
      <mstts:silence type='Tailing-exact' value='...'/>
    </mstts:express-as>
  </voice>
</speak>
```

配置项：`voicerole` / `voicestyle` / `voicestyledegree`（角色 / 风格 / 风格强度）

**此外还有**：`begin AudioSilenceRemove.`（静音段移除，独立能力）

### 与本项目对比

| 维度 | 融媒宝 | 本项目 |
|---|---|---|
| TTS 供应商 | **阿里云 + 微软 Azure + 自有代理** 三路 | 见 `tts-voice-catalog.js` / `tts-voice-clone.js` |
| 情感/风格控制 | ✅ `voicerole` + `voicestyle` + `voicestyledegree` | 需核对 |
| SSML 精细控制 | ✅ 背景音 + 情感 + 音量 + 前后静音 | 需核对 |
| 静音段移除 | ✅ `AudioSilenceRemove` | ❌ 未见 |
| ASR | — | ✅ `baidu-stt.js`（百度语音识别）|

**可借鉴**：
1. **多供应商降级**（阿里 ↔ 微软 ↔ 自有），单点故障时可切换
2. **自有代理取 token**（`public.17van.com/voice/MicrosoftToken`）——避免在客户端硬编码云厂商密钥
3. **SSML 的前后静音控制**（`mstts:silence type='Leading-exact'/'Tailing-exact'`）——控制配音节奏
4. `AudioSilenceRemove`（自动移除录音静音段）

## 9. 结论与可复用清单

### 9.1 直接可用（零风险）

| 项 | 价值 |
|---|---|
| `amix=...dynaudnorm=f=500:g=30:p=0.8:m=20` | 经实战调优的**混音+动态归一化**参数 |
| 视频号上传三段式协议 | 本项目已实现且一致，**作为正确性佐证** |
| `/api/upload/resume` 断点续传端点设计 | 补齐本项目上传器的续传语义 |
| 微软 TTS SSML 模板 | 前后静音控制表达式 |
| 新榜 / 搜狗微信 两个热点源 | 补进 `hot-topics-service.js` |

### 9.2 值得研究后实现

| 项 | 说明 | 成本 |
|---|---|---|
| **发布前双重预检** | `ArticleCheckRiskTask`（风险）+ `checkTitle`（标题查重）| 中 |
| **自动回复策略体系** | 5 个策略管理任务 + 评论/私信自动回复 | 高（需 PRD）|
| **账号未读数聚合** | 5 个账号任务中的 `UnReadCount` | 低 |
| **平台活动/任务广场抓取** | 头条 + 百家号 4 个端点 | 低 |
| **多路 TTS 降级** | 阿里 ↔ 微软 ↔ 自有代理 | 中 |
| **音频静音段移除** | `AudioSilenceRemove` | 低 |
| **腾讯云点播 UGC 上传** | `vod2.qcloud.com ApplyUploadUGC` | 中 |
| 快手作品诊断三维度 | diagnose / traffic/source / trending | 低 |
| 百度榜额外 3 个 board | 融媒宝用 5 个，本项目用 2 个 | 低 |

### 9.3 明确不建议

- 照搬原生任务类架构（本项目 Node.js 侧已有 `task-queue` + `task-pool`，架构更现代）
- 自动回复的**默认开启**（平台合规风险，且本项目 AGENTS.md 有「风控即停、绝不自动换号绕过」的红线）
- 大批量验证码对抗

### 复现命令

```powershell
# 环境（每个新 pwsh 进程都要重新导出）
$env:GHIDRA_INSTALL_DIR = [Environment]::GetEnvironmentVariable('GHIDRA_INSTALL_DIR','User')
```
