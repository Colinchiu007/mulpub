## 2. ⭐ 本项目与参考产品：逐行等价（已交叉验证）

本项目的 `douyin-ticket-guard.js` 与参考产品 bundle 的 `clientSign` **逐行等价**：

| 步骤 | 参考产品 `clientSign` | 本项目 `clientSign` |
|---|---|---|
| 取私钥 | `JSON.parse(JSON.parse(decodeURIComponent(cookie.split("security-sdk/s_sdk_crypt_sdk=")[1].split(";")[0].trim())).data).ec_privateKey` | `decodeSecuritySdk(cookieValue(cookie, 'security-sdk/s_sdk_crypt_sdk=')).ec_privateKey` |
| 待签串 | `` `ticket=${M.ticket}&path=/web/api/media/aweme/create_v2/&timestamp=${L}` `` | `` `ticket=${sd.ticket}&path=${CREATE_V2_PATH}&timestamp=${ts}` `` |
| 签名 | `crypto.createSign("SHA256").sign(U, "base64")` | `crypto.createSign('SHA256').sign(keyObj, 'base64')` |
| 输出 | `JSON.stringify({ts_sign, req_content:"ticket,path,timestamp", req_sign, timestamp})` → base64 | **同字段同序** |
| ree 公钥 | plain `bd_ticket_guard_client_data` 优先，否则 `_v2` | **同** |
| web-version | `ticket.startsWith("hash") ? "2" : "1"` | **同** |

**本项目的实现更严谨**：

| 维度 | 参考产品 | 本项目 |
|---|---|---|
| 错误处理 | `catch {}` 静默吞掉 | **fail-closed 抛错 + 脱敏**（`账号信息缺失，请重新授权此账号再试`，不回显私钥/cookie 片段）|
| 合规约束 | 无 | 代码注释写明：**纯本地 crypto，无 HTTP 客户端、不读远程签名环境变量后门；私钥/ticket 只存内存与请求头，禁止日志序列化** |
| 注册机制 | 直接函数调用 | registry + fail-closed（未知 command 抛错，不静默继续）|
| 测试 | 无 | 单测覆盖三层结构、`req_content` 契约、秒级单调、**公钥可验签**、材料缺失/PEM 非法 fail-closed |

## 3. ⭐ 决策框架：按「签名族」分类，而不是按平台

这是本次分析最重要的方法论结论。**「要不要本地实现签名」不取决于平台，取决于密钥的可得性**。

| 族 | 特征 | 本地实现可行性 | 代表 |
|---|---|---|---|
| **① 密钥下发型** | 平台**主动把密钥材料下发给页面**（cookie/localStorage 里就有私钥或 secret）| ✅ **可行，成本低** | **抖音** `bd-ticket-guard`（`ec_privateKey` 直接从 cookie 取）|
| **② 简单 HMAC 型** | 签名 = 明文拼接 + 标准 HMAC/哈希，密钥来自账号配置 | ✅ **可行** | CSDN（appSecret）、视频号（Content-MD5）|
| **③ 加密常量型** | 算法 = 固定 key/iv 的对称加密，常量从公开逆向资料可得 | ⚠️ **部分可行，有陷阱**（见 §4）| 小红书 XYW_（AES-128-CBC + 硬编码 key/iv）|
| **④ 混淆 VM 型** | 算法藏在混淆的 JS VM 里（无密钥下发）| ❌ **成本极高，不建议** | 头条 `tt-anti-token`（`byted_acrawler`）、小红书 `_webmsxyw` |

### 3.1 族的判据（可直接套用）

```
密钥材料能否从已登录会话中直接读出？
├─ 能（cookie / localStorage / 页面全局变量）
│   └─ 算法是否只是标准密码学原语（EC/HMAC/哈希）？
│       ├─ 是 → ① / ② 族 → ✅ 本地实现
│       └─ 否（自定义混淆）→ ③ 族 → ⚠️ 先小范围验证，见 §4
└─ 不能（藏在混淆代码里）
    └─ ④ 族 → ❌ 不本地实现，改「调页面 SDK」
```

### 3.2 项目自己的结论（2026-09-30 分析报告原文）

> **核心判断：逆向混淆 SDK 的正解不是"读它的代码"，而是"找到它的调用点、直接调用它"。**

三条路线的评估（该报告 §7）：

| 路线 | 可离线 | 成本 | 结论 |
|---|---|---|---|
| P0 页面内模拟点击原生提交控件 | 是 | 低 | 可用；受 DOM/弹窗/校验干扰 |
| **P0.5 页面内调宿主 SDK 取签 → 自行发 API** | 是（仅借 SDK）| 低-中 | **推荐**：不依赖 DOM、参数可控、无需复刻算法 |
| P1 剥离 secsdk 离线运行 / 纯本地复现 | **否** | **极高** | **不建议**：仍需逆混淆 VM + 持续跟随改版 |

> ⚠️ **注意这里有术语陷阱**：该报告的「P1」专指 **④ 混淆 VM 族**的本地复现（所以「不建议」是对的）。
> 而**① 密钥下发型**（抖音）不需要逆 VM，成本完全不同——这才是 W2 落地抖音本地签名的原因。
> **两份文档不矛盾，是「本地签名」这个词覆盖了成本差几个量级的两种东西。**

## 4. ⭐⭐ 最重要的实证教训：小红书的三次反转

项目在小红书签名上**被真机打脸过一次**，这个教训直接适用于抖音。

### 4.1 三次决策演进

| 时间 | 决策 | 依据 |
|---|---|---|
| 原始 | **依赖外包签名服务**，「本波只留 provider 槽不激活链」 | 未知算法 |
| **2026-10-06** | 改为 **`localAlgorithm`**（本地 XYW_ AES）| 实测 XYW_ 是纯 AES-128-CBC；对照 `Cloxl/xhshow`(MIT) + `tamnd/xiaohongshu-cli`（Go 版独立复现同常量）；不需浏览器 VM；不引入隐藏窗口崩溃面 |
| **2026-10-09** | **切回 `browser` 形态**（页内 `_webmsxyw`）| **真机 CDP 抓 28 条请求实证**：note 端点要求 `XYS_` 代签名，**本地 XYW_ 被 HTTP 406 拒绝** |

`signer-assembly.js` 的原话：

```
// 2026-10-09 更新（note-406-signature-report.md）：真机取证证明 note 端点
// 已要求 XYS_ 代签名（Base64 JSON 信封，页内 window._webmsxyw 生成），
// 本地 XYW_ AES 形态被 406 拒绝 —— 小红书切回 browser 形态。
```

结果：**406 → 401「无登录信息」⇒ 签名关已过**（401 是凭据问题，不是签名问题）。

### 4.2 教训（三条）

| # | 教训 | 对抖音的含义 |
|---|---|---|
| 1 | **「本地实现看着对」≠「发布端点接受」** | 抖音的本地签名**目前只在单测里验证过**（公钥可验签），**没在 `create_v2` 端点上验证过** |
| 2 | **轻接口验证会给出假阳性** | 小红书本地签名在轻接口是通的，到 note 端点才 406。抖音链路里各步（getAuthKey / upload / finish / cover / create_v2）都可能各自要求不同的签名材料 |
| 3 | **逆向资料的时效性会过期** | `signer-local.js` 里「XYS_ 已被拒」的记载**本身就已过时**（当时验证面是轻接口）。平台会改 |

> **这三条合起来说明：抖音本地签名的单测全绿，不构成「它能发布成功」的证据。**

## 8. 我的判断与建议

### 8.1 直接回答「要不要做」

### 8.2 为什么建议做抖音活体裁决

| 理由 | 说明 |
|---|---|
| 1 | **代码已经在了，不验证等于背着一个未知数** | 2026-09-25 进仓，闸门 10-06 已开，随时可能在生产被触发。**未知的失败比已知的失败危险** |
| 2 | 与小红书不同，抖音是 ① 族（密钥下发），**不需要逆混淆 VM** | 成本已经付过了（对比：小红书 ④ 族最后仍回到页内）|
| 3 | 失败代价低 | 私密内容、单条、18min 间隔；风控即停不降级 |
| 4 | 失败也有价值 | 若 406/风控，说明 `bd-ticket-guard` 也要走页内——那就把 `douyin` 的 `publishMode` 回拨 `dom-only`，**消掉一个潜在的生产事故** |
| 5 | 决策成本低 | W2 tasks 已把活体裁决的步骤、间隔、证据要求全部定义好 |

### 8.4 什么情况下**不该**继续投入本地签名

| 情形 | 判据 | 正解 |
|---|---|---|
| 算法是 ④ 混淆 VM 型 | 密钥不可从会话读出，算法藏在混淆代码 | **调页面 SDK**（P0.5），不要复刻 |
| 平台未提供密钥下发 | cookie/localStorage 里找不到密钥材料 | 同上 |
| 该平台发布频率极低 | 投入产出比不划算 | 留在 `dom-only` |
| 只需要「能发」不需要「快/无人值守」 | 页面路径已够用 | 留在 `dom-only` |

### 8.5 什么情况下**应该**继续投入本地签名

| 理由 | 说明 |
|---|---|
| **无人值守/后台发布** | 页面 SDK 需要页面存活；本地签名不需要 |
| **并发发布** | 页面是**有状态**的（登录态、DOM 状态），本地签名是无状态的纯计算 |
| **速度** | 省掉一次隐藏页创建 + 页面往返（`signer-page-manager` 的页面池也是资源）|
| **减少隐藏窗口崩溃面** | `signer-assembly.js` 注释明确提到要避免 `wechat_mp/baijiahao` 那种隐藏窗口原生崩溃面 |
