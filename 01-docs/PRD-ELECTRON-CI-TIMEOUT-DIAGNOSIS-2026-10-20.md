# electron-ci 单 worker 单测超时：诊断与方案（2026-10-20）

**状态：诊断完成，方案待人工决策。本文不改任何 workflow。**
**动因**：PR #4048 合并后 main push 的 `Electron CI` failure，`exit code 124`（超时）。此前该现象已被记为"既有问题"，本文把数据、根因边界与可选方案一次说清。

## 1. 现象与数据

| 项 | 读数 |
|---|---|
| 失败作业 | `electron-ci.yml` → `electron-tests` → `Unit tests (Vitest, non-Electron, single-worker deterministic)` |
| 失败形态 | **`exit code 124`**（`timeout` 掐断），**不是断言失败** |
| 本次实测耗时 | **36m44s ≈ 2204s** |
| 步骤级预算 | `BUDGET_SECONDS=2100`（35 分钟） |
| 工作流注释记录的健康耗时 | **794s**（run 36380533567 / main push `bef5fb72`，自证行 `elapsed=794s budget=2100s rc=0`） |
| main 上同形态历史 | 从 `528acaa0`(07:32Z) 起**连续 8 个** run 全部 failure，其中 **6 个发生在 #4048 合并之前** |

**关键比例**：健康 794s → 预算 2100s（2.6 倍余量）→ 本次实际 2204s（**健康耗时的 2.8 倍**）。

即：不是测试变慢到了贴着墙，而是**同一批测试在该 runner 上被放大了 2.8 倍**。这与工作流注释里的既有判断一致（「真实红因是 runner 负载把步骤耗时放大到越过旧墙，而不是'自然耗时已贴着墙'」）。

## 2. 边界：这个步骤到底是什么

工作流里的三条自我说明（原文摘录）：

1. `if: github.event_name != 'pull_request'` —— **PR 侧本就跳过**，因为「同一批桌面测试已由 QG desktop-shards 分片执行」；
2. 它的存在价值是「保留**单 worker 串行确定性模式**的 CI 覆盖与**第二次独立运行的 flake 检出**」；
3. 注释已把根因写成「**按 `--shard` 把这一轮切开（issue 档 2）**」，并明确「2100s 属**单调放宽**，不是修好了根因」。

所以这不是"某次改动引入的红"，而是一个**已识别、已登记、被临时放宽过的容量问题**。

## 3. 为什么最直觉的方案不可行：`--shard` + matrix

`--shard` 确实能把一轮切成 N 份并行跑。但用 GitHub Actions 的 **matrix** 承载它与本仓的 required status check 存在**结构性冲突**（AGENTS.md「取证口径」节已实测记录）：

- matrix 把作业报成 `electron-tests (1)`、`electron-tests (2)`…；
- required context 要的是**不带后缀**的作业名；
- 于是**全绿也判 `base branch policy prohibits the merge`**；
- 已实测两种补名写法都不可行：① 另加一个 `name` 等于该 context 的汇入作业 ⇒ 整份 workflow 被判不可解析（幻影 `push` run + 0 job）；② 只给 matrix 作业加静态 `name` ⇒ 解析正常但 check 名仍带 `(1)`。

**结论：matrix 方案在本仓不可用**，除非同步改多条按 job 名/needs 断言的结构性锁并接受一次 required-check 迁移 —— 那是独立工程，不该夹带在修超时里。

## 4. 可选方案对比

| 方案 | 做法 | 预期效果 | 风险 / 代价 | 是否改「谁来守门」 |
|---|---|---|---|---|
| **A. 抬预算** | `BUDGET_SECONDS` 2100 → 3600，同时抬 job 级 `timeout-minutes`（当前 70） | 直接消红 | **治标**。掩盖"runner 放大 2.8 倍"这一事实；下次负载更高时仍会越墙 | 是（作业规模） |
| **B. matrix + `--shard`** | 4 分片并行 | 理想 4× | **与 required check 结构性冲突**（见 §3），本仓不可用 | 是 |
| **C. 单 job 内并行 N 个 shard 进程** | `for i in 1..N; do vitest --shard=$i/$N & done; wait`，汇总各分片 rc | 总时长 ≈ 794/N + 启动开销；N=2 时约减半 | ① N 个 vitest 抢 4 vCPU，单分片变慢，实际加速 < N；② 内存压力（每进程 1–2 GB）可能 OOM；③ 日志需分片落盘再汇总；④ **不再严格串行** ⇒ "单 worker 串行确定性"的原意被削弱 | 是（作业规模 + 语义） |
| **D. 降级触发面** | 改为只在 `workflow_dispatch` 跑，main push 不跑 | 彻底消红 | 失去 main push 的第二道独立覆盖（这正是它存在的理由） | 是（覆盖范围） |
| **E. 只加可观测性** | 保留现状，但把 `elapsed/budget` 比值写进日志并在 > 1.5 时 `::warning`（不失败） | 不改红绿，让"runner 变慢"被看见 | 不解决失败本身 | 否（仅日志） |
| **F. 修 runner 负载** | 自托管 runner / 更大规格 | 根治 | 基础设施决策，非本仓代码 | 是（成本） |

## 5. 推荐

**短期（消红且不掩盖）**：**A + E 组合**。

- 预算抬到 3600s（`BUDGET_SECONDS` 与 job 级 `timeout-minutes` **必须一起抬**——工作流注释明确警告过：只抬一个等于把"不可归因的超时"从 `timeout(1)` 换成 Actions 的 job killer，那正是本 issue 的失效模式）；
- 同时把 `elapsed/budget` 比值打进自证行并在 > 1.5 时输出 `::warning`。这样"放宽"是可观测的：下次若比值继续恶化，日志会直接说出来，而不是等到再次越墙。

**中期（真正减时）**：方案 **C**（单 job 内并行分片），但需先实测两件事才有意义：
1. 4 vCPU 上 N=2 / N=4 的**真实加速比**（很可能不是 2× / 4×）；
2. 峰值内存是否触顶。

**不建议**：B（本仓不可用）、D（削弱覆盖）。

## 6. 需要人工决策的点（这就是我没有直接动手的原因）

1. **A 的时长上限取多少**？3600s 是"健康 ×4.5"，还是先取 3000s（×3.8）观察一轮？
2. **是否接受"放宽 + 告警"**，还是要求必须先有真实减时（方案 C）才允许消红？
3. 若选 C，**N 取 2 还是 4**、以及是否接受"不再是严格串行"这个语义让步？
4. 这次改动**属"改谁来守门"**，按 AGENTS.md 须人工过目、不走 agent 自动合并 —— 是否授权我实施并走普通 PR（CI 全绿后仍**不自动合并**，等你确认）？

## 7. 一个附带的可观测性缺口（顺手记下，不在本议题修复）

本次失败的 `attempt` 日志里**没有** `[electron-ci-timeout-budget] elapsed=… rc=…` 这一行。工作流在 2026-10-20 已为此加过 `set +e`（注释写明「`timeout` 返回 124 时 `-e` 会立刻退出步骤，于是后面的 PIPESTATUS 与整段自证诊断一次都不会执行」），但本次现场仍然没有该行 —— 说明那段修复**没有覆盖本次的失败路径**（可能是另一步先失败，或 `set +e` 的作用域没兜到）。

这条值得单独查：**没有自证行的超时，和一个原因不明的红无法区分**。建议在实施 A/C 时一并复核 `set +e` 的实际生效位置（`grep -c 'electron-ci-timeout-budget' <失败日志>` 应为 1）。
