# PRD：小红书图文草稿「硬证据」确认（取代页面文本正则）

> 分支 `xhs-draft-only-hard-evidence`｜日期 2026-10-15｜变更类型：运行时代码（Electron 主进程）
> 关联：`PRD-XHS-DRAFT-PUBLISH-2026-10-07.md`、Python 侧 #3469（`xiaohongshu_dom.py` 确认链）

## 1. 背景与问题（2026-10-15 真机实测）

在应用里发布一条小红书图文草稿，**应用报「发布成功」，平台草稿箱却没有新增**。

日志时间线（`app-2026-10-15.log`）：

```
16:11:54  uploading image... → image uploaded
16:11:58  filling title... / filling content...
16:11:58.651  saving draft...
16:12:00.6    页面控制台连报：获取某个数据失败 / 请求失败（×5）
16:12:01.668  draft-only done saved=true        ← 只等了 3 秒
16:12:01.672  draft saved
16:12:01.674  publish done ... draft=true       → 报成功
```

直接读取执行发布的那个窗口：草稿箱计数仍是 **1**（唯一一条是 10-08 的人工存草稿取证稿），
编辑页是**空的**（无图、无标题、无正文编辑器）。

**根因**：Electron 侧 `draftOnly` 的 `draftSaved` 判据是**页面文本正则**
（`/编辑于\s*\S{1,12}|已保存|保存成功|自动保存/` 匹配 `document.body.innerText`），
不是落库证据。3 秒即命中的是页面**静态文案**，同一时刻页面正在报「请求失败」。
2026-10-07 曾把该正则从「`/编辑于|已保存|草稿/`」收紧过（去掉恒真的裸「草稿」），
但**收紧字符形状没有改变「用页面文案当落库证据」这一本质**。

## 2. 目标 / 非目标

**目标**：把 `draftOnly` 的成功判据换成**硬证据**——草稿箱计数增量、保存接口成功响应、
草稿箱整页重载后的计数复核，三者皆不可达时 **fail-closed 报失败**，绝不假成功。

**非目标（明确不做）**：
- 不改内容填写阶段的判据（`PUBLISH_DRAFT_CONTENT_NOT_FILLED` 那套保留）。
- 不改视频轨的 fail-closed 拒绝（`XHS_VIDEO_REFUSAL_MESSAGE`）。
- 不改 Python 侧的确认链（#3469 刚落，本 PR 只补 Electron 侧）。
- 不改「不点发布按钮、只落草稿箱」的产品行为。
- **不用**「标题匹配单独确认成功」这条更宽松的写法（理由见 §3）。

## 3. 功能逻辑：硬证据确认链

与 Python 侧 #3469（`xiaohongshu_dom.py` + `xiaohongshu.py` 的 `_confirm_saved`）**同构**。
**能单独确认成功的只有 ①②两条**：

| 通道 | 判据 | 说明 |
|---|---|---|
| ① 草稿箱计数**增量**（主） | **写入内容之前**读基线 `N`，点存草稿后等计数变成 `>N` | 自动保存落库有延迟，等待条件是「增量本身」而非「节点出现」 |
| ② 保存接口**成功响应**（次） | 监听保存端点 `/web_api/sns/v2/note` 的响应，且**必须 HTTP 200** | 监听在点击**之前**挂上（该实现只监听注册之后完成的响应、不回放历史）；主判据不可达时启用 |
| ③ 草稿箱整页重载后的复核（兜底） | 重载后**再读计数增量**；标题命中只作辅助证据上报 | 前两条都不可达时才跑（贵，一次整页 goto）。**不新增确认权** |

**三条全不可达 ⇒ `success:false` + `errorCode:'PUBLISH_DRAFT_UNCONFIRMED'`**，
错误文案明说「未获确认」，不伪装成成功。

### 3.1 ②：端点表必须是「窄路径」，且必须校验 HTTP 200

- **窄路径**：宽词子串（例如拿「草稿」「保存」这类二字词去 `url.includes(...)`）会命中发布页
  **自身的**草稿列表查询、埋点等无关 200 响应 —— 主判据超时后这些响应就会被读成「本次已落库」，
  **与 2026-10-15 的真机假成功同形**。取值直接对齐 Python 侧已真机确认的
  `DRAFT_SAVE_RESPONSE_PATTERNS = ["/web_api/sns/v2/note"]`，**不自行猜测**。
- **必须校验 `statusCode === 200`**：本仓的 `_waitForResponse` 在超时兜底分支里会把
  **非 200** 的命中也 `resolve` 出来（`rpa-view-helpers.js` 的 `fallbackTimer`），
  所以「resolve 非空」**不等于**「落库成功」；非 200 只记 warning。

### 3.2 ③：标题匹配不给确认权（与 Python 侧的**有意分歧**）

标题是**精确匹配**，历史同名草稿会误命中。若允许它单独确认成功，「计数没涨（很可能真没保存）」
就会被一条旧草稿翻案成成功 —— 仍是假成功。故确认权归**计数增量**，标题命中只通过
`titleSeen` 上报，并在失败文案里写明「见到了同名条目但不据此判成功」，让用户知道为什么报失败。

与 Python 侧的差异是**有意**的：Python 的 `recheck_draft_box` 允许标题命中单独返回 True。
收紧的理由是风险不对称 —— **误报成功会静默丢数据，误报失败用户可重试**。

### 3.3 关键不变量（对齐 Python 侧）

1. **基线未知 ≠ 没增长**：读不到基线（`null`）时，**不得拿 0 顶替**（那会把上一次
   失败写成的一切当成基线），直接判该通道不可用。
2. **基线必须在写入内容之前读**：平台会在填写阶段自动保存，晚读会把本次草稿吃进基线，
   此后永远看不到增量 ⇒ 主判据常态失效。故此读发生在「导航完成、清理弹窗之后，
   上传/填写之前」（与 Python 侧「导航后、上传前」同位置）。
3. **单次探测异常不中断轮询**：探测抛错时保持上一读数继续等，不把「读数坏掉」
   当成「没增长」。
4. **回查抛错 fail-closed 但留痕**：整页重载失败判未确认，落 warning——它是被真机
   证实过的判据，「为什么没确认」必须能在日志里查到。
5. **存草稿入口只点一次**：平台给出显式按钮时点它；没有按钮则依赖平台自动保存
   （活体取证 2026-10-08：图文编辑器**没有**存草稿按钮）。重复点击会带来重复提交风险。

### 3.4 判据选址（针对「草稿箱是否分区本地」疑点）

小红书草稿箱页面自述「草稿存储于当前使用的浏览器本地」。实测确认：
`DRAFT_BOX_URL`（`xiaohongshi_selectors.py`）与发布页**是同一个 URL**
（`publish/publish?from=menu&target=image`），草稿箱入口就在发布页**侧边栏**
（选择器 `.draft-title`）。因此：

- 计数读取落在**同一个 RPA 分区、同一个页面**上，不需要另开窗口；
- 兜底通道的整页 `goto` 也仍在本分区内（登录态一致、草稿箱内容一致）；
- **不存在跨分区看不到草稿箱的问题**——这正是选址必须落在同一分区内的原因，
  若换到别的窗口/分区读，登录态不同，草稿箱内容就不同，判据会失真。

## 4. 数据校验与显示项

- **数据面**：只读页面 DOM 文本（草稿箱计数节点、草稿列表标题）与 XHR 响应；
  不读取、不写入任何 Cookie/凭据。
- **失败时用户看到什么**：发布结果区显示失败，`errorCode='PUBLISH_DRAFT_UNCONFIRMED'`，
  发布历史里该条记为失败（不再出现「报了成功但草稿箱空」）。文案分两种，区别只在
  「列表里是否见到了同名条目」，因为这两种情形用户该做的事不一样：
  - 一般情形：「草稿保存未获确认（草稿箱计数无增量、保存接口无成功响应、草稿箱重载复核仍无增量），
    已按失败处理以避免假成功」；
  - 列表里见到了同名条目：「草稿保存未获确认（草稿列表见到了同名条目，但草稿箱计数没有增量、
    保存接口也没有成功响应；同名旧草稿会被误认，故不据此判成功），已按失败处理以避免假成功」。
      —— 后一种必须解释清楚，否则用户会问「列表里明明有这条，为什么说没保存」。
- **成功时**：与现状一致（draft 成功），并新增 `draftEvidence` 字段回传「哪条通道确认的」：
  `counter-increment`（①页内增量）/ `save-response`（②接口 200）/
  `counter-increment-after-reload`（③重载后增量）；失败路径不带该字段。
  真机验证时可直接看判据健康度。
- **日志**（诊断用，也是「为什么没确认」的唯一线索）：
  `draft-only done saved=<bool> evidence=<...> baseline=<N|null> titleSeen=<bool> url=<...>`；
  基线读不到、响应非 200、重载复核无增量各自都有独立 warning/info。
- **进度提示**：`saving draft...`（90%）不变；确认失败时进度推到 100% 但结果为失败
  （`draft unconfirmed`），不再显示 `draft saved`。

## 5. 交互逻辑

无新增交互。发布流程对用户完全不变：填内容 → 提交 → 等结果。
唯一差别是**结果可能是「未确认」的失败**——这是本 PR 的目的（把假成功变成真失败）。

证据：改后 `verify-security` 扫描**通过（0 发现）**；抖音与小红书三套测试 **21/21** 全绿

### 7.1 实现过程中发现并修掉的一处隐式耦合（如实登记）

`douyin-rpa-create-v2-pattern.test.js` 用正则 `/_waitForResponse\(win,\s*\[([^\]]*)\]/`
抽取**源码中第一处**等待调用的端点数组，以此断言抖音的端点形态。本 PR 新增的
小红书等待调用（字面量数组）排在抖音之前 ⇒ 该锁被劫持变红。

两轮排查才定位：**第一轮**只把端点数组提为命名常量，仍红——因为**注释里复述了该调用的
字面形状**，而那个正则连注释一起匹配。**第二轮**同时改写注释（不再复述形状）后转绿。

处置：端点提为命名常量 `XHS_DRAFT_SAVE_PATTERNS`；注释改为只描述意图、不复述调用形状；
并在常量注释里写明这个坑，防止后来者再加同形注释。这条属于「既有锁按位置抽取」的
脆弱性，不在本 PR 扩修（改锁的抽取方式属独立改动），只在 PRD 与执行记录登记。

## 8. CCG 跨家族深度评审与处置（2026-10-15）

驱动：`node <adversarial-review-loop>/scripts/ccg-deep-review.js --sha 8fe885f57`，
跨家族校准 **proposer=opencode / critic=claude**。产出 7 条发现、4 个维度
（correctness 4 / security 9 / performance 7 / maintainability 5）。

**评审确实改了本 PR 的设计**，不是走过场：初版把「保存接口响应」的端点写成宽词子串
（`'draft'` / `'save'`），并把「`_waitForResponse` resolve 非空」当成功 —— 两者叠加后，
主判据超时期间页面**自身**的草稿列表查询或埋点响应（乃至一次 500）就会被读成「本次已落库」，
**与真机缺陷完全同形**。这条被定为 Critical。

| # | 级别 | 发现（要点） | 处置 |
|---|------|--------------|------|

## 9. 遗留与后续（登记，不假装闭合）

- **`DRAFT_BOX_ITEM_SELECTOR` 仍未取证**（Python 侧已登记的同一问题）：本 PR 把它降级为
  **辅助证据**（不再给确认权，见 §3.2），因此它失明的后果从「可能假成功」变成「少一条诊断信息」
  ——这正是收紧的收益。仍登记排期取证。
- **`DRAFT_BOX_COUNTER_SELECTOR`（`.draft-title`）同样只有单点取证**，而收紧后**计数增量是唯一的
  确认权来源**，于是这个单点选择器的风险从「少一条通道」变成「平台改显示形态即整体 fail-closed」。
  这是**有意的取舍**（误报成功静默丢数据 vs 误报失败用户可重试），但它是本 PR 最脆的一环：
  下一刀应把它做成多候选（`.draft-title` / `[class*="draft"] [class*="count"]` / aria 属性等）
  并活体取证，否则一旦平台改版，用户会看到「每次都说未确认」。本轮已把「节点在但解析不出」
  变成可查现场（info 日志点名 sel 与收到的文本条数）。
- **其它平台的 `draftOnly` 仍是旧判据（本刀**有意**不动，属独立改动）**：头条在带
  `publishTime` 时会走 `draftOnly` 的 DOM 轨（`packages/rpa-engine/src/toutiao-direct-bridge.js`
  的注释与 `toutiao-schedule-intent.test.js` 都写明「只存草稿、绝不点发布」）。它们**同样**
  有「页面文案当落库证据」这个假成功面，但本刀只换小红书：把别的平台一并切到小红书专用链
  会让它们的基线恒为 `null`、主判据永久失效，把「本来能报成功的草稿」变成「恒失败」
  （CCG 第二轮评审 i2）。**处置**：调用方按 `platform === 'xiaohongshu'` 分流，非小红书平台
  保留既有行为（内容闸 + 原页面文本判据）；接线锁相应**只锁小红书子分支**。
  下一刀：让头条等地复用本模块的计数通道（选择器与计数节点形态需各自活体取证）。
- **②的端点若变化会静默失效**（不会假成功，只会少一条通道）：端点值取自 Python 侧的
  真机取证值，本轨未独立取证；`_waitForResponse` 也只按 URL 子串匹配、**不支持按 HTTP 方法
  过滤**（CCG 第二轮评审 i1）。日志里「非成功码」warning 与 `evidence` 分布可用于发现它失效。
  返回形状已对着真实 helper 锁定（`{url, statusCode, matchedUrls}` 平铺，见 H10 用例）。
- **失败文案未入 i18n**：`PUBLISH_DRAFT_UNCONFIRMED` 的文案目前是主进程直出的
  `error` 字符串（与 `PUBLISH_DRAFT_CONTENT_NOT_FILLED` 同款既有做法）。若产品要求
  多语言，需按 locale 成对规则补 zh/en——那会触 i18n-content-sync 门禁，属独立改动。
- **确认链最长耗时约 40s**（①20s → ②窗口收尾 → ③重载复核 8s），且 ③ 的整页重载发生在
  点击后 ≥30s，理论上仍可能打断极慢的保存请求（CCG 第二轮评审 i5）。当前选择是
  **宁可慢也不误报失败**；若真机发现「保存成功却报未确认」，应改为 ①/② 并发取先到者。
  ① 确认成功后 ② 的监听不再被 await，但它自身窗口最多存活 30s 后自行清理（评审 i8）。

  发布结果为成功且 `draftEvidence=counter-increment`；再构造一次「主站不授会话」
  场景（如断网）确认报「未确认」失败而非假成功。**这一条决定了「基线在填写前读」的假设是否成立**
