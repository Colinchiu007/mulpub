## 逐条评审问题

### 【完整性】问题 1: 设计令牌的具体值缺失 ❌

**批评**: 方案中仅提到 `colors.json`、`typography.json` 等文件，但未给出任何具体示例值。例如：
- Primary 色板的 50-900 具体是什么颜色？
- 字体大小是 14px/16px/18px 还是其他？
- 间距单位是 4px 的倍数吗？

**影响**: 开发团队无法直接执行，需要额外时间定义这些值。

**证据等级**: L2（约束性问题）

**建议**: 
- 在 PRD 阶段就应提取现有页面的 CSS 变量作为基线
- 或至少给出一个完整的示例片段

---

### 【完整性】问题 2: 组件 API 设计过于笼统 ❌

**批评**: 方案中提到"Button 组件含 Props、Events、Slots"，但未说明具体有哪些 Props：
- `variant` 支持哪些值？（primary/secondary/danger/text？）
- `size` 支持哪些值？（small/medium/large？）
- 是否支持 `icon-only` 模式？
- Slot 名称是什么？（default？prefix？suffix？）

**影响**: 开发者无法评估 API 是否足够灵活，可能导致后期重构。

**证据等级**: L2（约束性问题）

**建议**: 
- 为每个 P0 组件提供完整的 Props/Events/Slots 签名
- 参考现有组件库（如 Element Plus/Ant Design Vue）的 API 设计

---

### 【完整性】问题 3: 视觉回归测试配置缺失 ❌

**批评**: 方案中提到"Playwright Pixel Matching"，但未说明：
- 如何生成基线截图？（首次运行自动保存？）
- 允许的像素误差阈值是多少？（1%？3%？）
- 如何处理动态内容（时间戳、用户头像）？
- CI 环境中如何运行？（Headless Chrome？）

**影响**: 视觉回归测试可能流于形式，无法真正发现问题。

**证据等级**: L2（约束性问题）

**建议**: 
- 补充 Playwright 配置示例
- 说明基线截图管理策略（存储在哪个分支？如何更新？）

---

### 【一致性】问题 4: npm 发布策略不明确 ⚠️

**批评**: 方案中提到 `packages/ui-design-tokens` 要"发布 npm 包"，但未说明：
- 是私有 npm 仓库还是公共仓库？
- 版本号如何管理？（手动 bump？自动化？）
- 依赖关系如何同步？（ui 和 ui-business 同时发布？）
- Workspace 引用与 npm 发布如何共存？

**影响**: 可能导致依赖混乱，本地开发与生产环境不一致。

**证据等级**: L3（权衡性问题）

**建议**: 
- 明确声明使用私有 npm 仓库（如 Verdaccio）
- 或使用 pnpm workspace 的 local 链接（不发布 npm）

---

### 【可行性】问题 5: 时间估算过于乐观 ❌

**批评**: 方案总工期 10 天，但实际工作量远超此：
- **基础组件 5 个** × 3 天/个（实现 + 测试+Storybook+ 迁移）= 15 天
- **业务组件 3 个** × 2 天/个 = 6 天
- **E2E 测试配置** = 2 天
- **性能优化** = 5 天（内存泄漏排查需要深度分析）
- **总计**: ~28 天，而非 10 天

**影响**: 团队可能因时间压力而牺牲质量。

**证据等级**: L1（反例：参考历史 Sprint 数据）

**建议**: 
- 重新评估每个子任务的时间
- 或拆分到多个 Sprint 中完成

---

### 【可行性】问题 6: 未考虑团队学习曲线 ❌

**批评**: 方案假设团队成员熟悉：
- Storybook 组件文档编写
- Vitest 测试框架
- Playwright E2E 测试
- TypeScript 高级类型

**影响**: 前期可能需要培训时间，拖慢进度。

**证据等级**: L3（权衡性问题）

**建议**: 
- 预留 2-3 天培训时间
- 或指定专人（Tech Lead）先掌握再推广

---

### 【安全性】问题 7: XSS 防护完全缺失 🔴

**批评**: 方案中**完全没有提及**：
- 组件是否需要转义用户输入？（如 Input 组件的 v-model）
- 是否禁用 `v-html` / `dangerouslySetInnerHTML`？
- 是否启用 CSP（Content Security Policy）？
- 是否对 HTML 内容进行 sanitize？

**影响**: 可能导致 XSS 攻击漏洞。

**证据等级**: L1（反例：安全是底线要求）

**建议**: 
- 在 PRD 中增加安全需求章节
- 为每个组件添加 XSS 防护说明

---

### 【安全性】问题 8: IPC 通信权限校验缺失 🔴

**批评**: Electron 的 IPC 通信是常见攻击面，方案中未提及：
- Renderer → Main 调用是否需要权限校验？
- 是否限制某些敏感 API 的调用？
- 是否记录 IPC 调用日志用于审计？

**影响**: 可能导致恶意插件或渲染进程提权攻击。

**证据等级**: L1（反例：Electron 安全最佳实践）

**建议**: 
- 参考 [Electron Security Checklist](https://github.com/electron/electron/blob/main/docs/tutorial/security.md)
- 在测试规范中加入 IPC 权限测试用例

---

### 【清晰度】问题 9: 迁移指南过于简略 ⚠️

**批评**: MIGRATION.md 仅一句话带过，未说明：
- 旧组件如何废弃？（Deprecation Warning？）
- 过渡期多久？（2 个版本？）
- 是否有自动迁移脚本？（codemod？）

**影响**: 团队成员可能不敢使用新组件库，担心破坏现有代码。

**证据等级**: L3（权衡性问题）

**建议**: 
- 提供详细的迁移步骤示例
- 或编写 codemod 脚本自动替换 import 路径

---

### 【完整性】问题 10: 未考虑暗黑模式支持 ❌

**批评**: 现代桌面应用普遍支持暗黑模式，但方案中未提及：
- Design Tokens 是否包含暗黑主题变量？
- 组件是否支持 `theme="dark"` Prop？
- 是否自动检测系统偏好（`prefers-color-scheme`）？

**影响**: 后续需要返工修改组件库以支持暗黑模式。

**证据等级**: L2（约束性问题）

**建议**: 
- 在 Design Tokens 中增加 `color-scheme: dark` 变体
- 组件支持 CSS 变量切换主题
