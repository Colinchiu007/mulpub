refactor(desktop): 滚动高亮与帧调度整体下沉 composable + 补 cancelAnimationFrame

## 为什么

两条原因叠在一起：

1. **门禁**：`ResultView.vue` 是 max-lines 的 targets 点名还账对象（零增长容差）。
   上一提交追加 `cancelSegmentScrollFrame` 后门禁报
   `TARGET_GREW … 现 1909 行已超过点名目标 1890 行（超 19）`。
2. **架构**：滚动帧调度 + 高亮计算本来就不是"页面"的职责——它是纯的
   「读 DOM → 算下标」逻辑，放进 composable 才能单测。

所以不是"为了过门禁塞东西"，而是把它放到该在的位置。宿主 **1909 → 1847 行**。

## 改了什么

`composables/useSegmentNavigation.js` 新增四个导出：

| 导出 | 职责 |
| --- | --- |
| `computeActiveSegmentIndex(vm)` | 遍历已挂 ref 求当前分段（含视口裁剪提前退出） |
| `cancelScrollFrame(vm)` | 取消待执行帧（rAF / setTimeout 两种回退都能取消） |
| `tickSegmentScroll(vm)` | 滚动入口：前沿节流（本帧首次立即算） |
| `recalcSegmentHighlight(vm)` | 程序化重算：不受节流影响 |

宿主只留 3 个一行委托 + 回顶显隐。

## 顺带修掉 QM-6 深审 i5 的真实部分

评审说「`onSegmentScroll` 不取消前一个 rAF ⇒ 并发两个 rAF」——**这条不成立**：
`if (this._segmentScrollFrame) return` 保证同一时刻最多一个待执行帧。

但顺着查出一处**真**问题：`recalcSegmentHighlight` 只把 `_segmentScrollFrame` 置 null，
旧 rAF 的回调稍后仍会执行并把**新**标记清掉 ⇒ 程序化重算后同一帧可能多算一次。
已在 `recalcSegmentHighlight` 里先 `cancelSegmentScrollFrame()`（现 `cancelScrollFrame`）。
